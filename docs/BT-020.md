# BT-020 / Issue #20 — 보낸·받은 요청 실시간 조회·취소

담당 D. `feature/request-BT-019`의 생성 계약을 기반으로 `feature/request-BT-020`에서 작업했다.
두 브랜치의 PR 대상은 develop이며 BT-019를 먼저 통합한다. BT-020은 BT-019 커밋을 포함하므로 선행 PR 병합 전에는 누적 변경이 보인다. 이슈가 일부 구현된 단계이므로 PR은 `Related #19` / `Related #20`으로 연결하고 자동 종료하지 않는다. Firebase 배포는 이번 범위에 포함하지 않는다.
초기 계약·Mock·Emulator에서 BT-017 서버 후보 어댑터 통합까지 보완했다. #84가 선행 #88·#89를 통합한 변경도 포함한다. 실제 검색 후보를 verified draft로 공급하는 A의 BT-018 호출부, 승인된 개발 환경 배포와 두 계정 앱 검증 전에는 #19/#20 전체 완료로 판정하지 않는다.

## 조회·화면 계약

- `FirebaseRequestRepository`가 `matchRequests`를 `fromUid == authUid`, `toUid == authUid`로 각각 조회하고 `createdAt DESC`로 정렬한다.
- 참여자별 문서를 메모리에서 합쳐 PENDING 발신/수신과 ACCEPTED 목록으로 표시한다. 취소·거절된 문서는 보낸/받은 대기 목록에서 사라지지만 서버 원본은 보존한다.
- Callable 생성/취소 응답과 목록 스냅샷은 `RequestItemCache`의 동일한 병합 규칙을 사용한다. 같은 요청 ID의 ACCEPTED/REJECTED/CANCELED를 확인한 뒤 도착한 오래된 PENDING은 무시하며, Callable 성공 콜백에도 병합된 상태를 반환한다. 이는 요청 ID 재사용 및 종결 상태→PENDING 전이가 없는 서버 계약을 따른다. 새 요청은 새 ID로 별도 저장하며 시간 스냅샷은 다시 계산하지 않는다.
- `RequestTabsController`가 View Lifecycle STARTED에서 구독하고 STOPPED에서 해제한다. 마지막 구독이 없어지면 Firestore/Auth 리스너와 로딩 타이머를 해제한다. 이전 구독의 콜백은 세대 번호로 무시한다.
- 로그인 UID가 바뀌거나 로그아웃되면 기존 구독을 해제하고 메모리 목록을 비운다. 다른 계정의 요청으로 복원하지 않는다.
- 최초 서버 응답 전 로딩, 빈 목록, 권한/통신/형식 오류와 재시도를 기존 `StateView`로 표시한다. 서버 응답 없이 캐시만 도착하면 10초 후 연결 오류와 재시도를 표시한다.
- BT-031에서 요청 목록에 B의 공개 프로필 이름·학과/학년·성별·소개·태그를 연결했다. `users`가 아닌 `publicProfiles`만 조회하고 실제 요청 카드에 Mock 이름/관심사/AI 이유를 붙이지 않는다. 조회 전/실패 시 대체 안내와 요청 스냅샷을 유지한다. 실제 프로필 상세·받은 요청 팝업의 전체 흐름은 별도 연동 범위다.
- BT-031에서 Firebase 수락/거절 버튼을 비동기 `respondToMatchRequest`에 연결했다. 처리 중에는 중복 조작을 막고 서버 최종 상태에 따라 성사 확인/상태 안내를 표시한다. 공개 프로필 이름·학과·성별·소개·태그를 조회하며 Mock 정보로 대체하지 않는다. 상세/팝업과 채팅 준비 상태의 완전한 연결은 후속 범위이며 현재 구현·검증은 [BT-031](./BT-031.md)을 따른다.
- Firebase 요청 항목의 `matchStatus`는 아직 null이다. ACTIVE로 가정해 채우지 않는다. BT-031에서 `matches/{requestId}.status`를 원본으로 완료 탭과 채팅의 매칭됨/매칭종료를 맞춘다. 수락 시 `purpose`·`dayOfWeek`도 복사하고 반대 방향 PENDING 정리를 검증한다.
- 카드·시간 요약·칩·확인창·빈 상태는 기존 컴포넌트를 재사용한다. `ConfirmDialog`에 결과 Bundle 전달만 추가해 새로 생성된 요청과 회전 후에도 같은 요청 ID로 취소한다.

## 취소 Callable

`asia-northeast3`의 `cancelMatchRequest({requestId})`.
`requestId`는 생성 API가 반환한 64자리 소문자 hex다. 추가 UID/상태/시간 입력은 거절한다.
토큰 UID가 `fromUid`인 경우만 허용하며, PENDING → CANCELED와 서버 `updatedAt`만 변경한다.
생성·취소 모두 #87의 `checkSchoolEmail`로 검증된 학교 이메일과 허용 도메인 설정을 검사한다. 취소는 현재 후보를 다시 계산하지 않으므로 시간표가 바뀌어도 기존 PENDING 요청을 취소할 수 있다. 이미 생성/취소 중인 항목에 대한 중복 호출도 오류 콜백을 돌려준다.
동일 요청 취소 재시도는 같은 결과를 반환한다. 수신자·제3자는 취소할 수 없고 ACCEPTED/REJECTED도 바꾸지 않는다.
원본 문서를 읽고 갱신하는 Firestore 트랜잭션으로 동시 취소 및 미래 수락 API와의 경합을 보호한다.
목적·날짜·시작/종료·겹침·생성 시각은 유지한다. UI는 서버 성공 응답 또는 리스너 반영 이후에만 목록을 갱신한다.

## 인덱스·보안 영향

`firestore.indexes.json`에는 요청 컬렉션의 `(fromUid ASC, createdAt DESC)`, `(toUid ASC, createdAt DESC)`와 #84의 `matches(participantUids ARRAY_CONTAINS, meetingDate ASC)`를 모두 보존한다. 총 3개이며 matches 인덱스는 #84 요청 생성의 충돌 검사부터 필요하다.
Emulator는 운영의 복합 인덱스 존재 여부를 검증하지 않는다. 실제 개발 환경 연동 때 인덱스 생성 완료를 별도로 확인해야 한다.
프로필·시간표·공강·매칭 설정과 기존 BT-019의 요청 참여자 읽기/클라이언트 쓰기 금지 Rules를 통합 보존한다. 요청 목록·취소 고유 변경은 다른 경로의 권한을 확대하지 않는다.
새 API와 인덱스는 D 범위이며 A/B/SM과 통합 검토가 필요하다.
