# BT-048 (Issue #48) 시간표 이미지 인식 시각 정확도 (초안)

## 목적

실제 시간표 이미지에서 수업 시작·종료 시각이 어긋나는 문제를 줄이고, 틀릴 가능성이 있는 수업에만 '확인 필요'가 붙게 한다.

- 이번 PR(1~2단계): 정답 fixture와 프롬프트 수정. 출력 스키마·verify·앱 계약은 바꾸지 않는다.
- 서버 코드: `functions/src/ai/tasks/analyzeTimetable.ts`의 `PROMPT`만 수정.
- 테스트: `functions/test/analyzeTimetable.test.ts`, 정답 데이터 `functions/test/fixtures/timetable-truth.json`.

## 평가 기준선 (2026-11-24, 수정 전 프롬프트)

AVD(emulator-5554)에서 실제 `analyzeTimetable` 서버(`gemini-3.5-flash-lite`)로 에브리타임 이미지 7장을 한 장씩 분석하고 검수 화면을 정답표와 비교했다.

- 전체: 정답 72개, 인식 72개, 일치 46개, 시각 오류 26건.
- 이름·요일·건물·호실·null 처리·수업 수는 모두 맞았다. 요일 밀림, 12시간제 오인, 수업 병합 오류, 누락은 0건이다.
- 틀린 26건은 모두 시작 또는 종료 시각이 30분 칸 기준으로 어긋난 경우다. 가장 크게 어긋난 쪽 기준으로 30분 18건, 60분 7건, 약 70분 1건이다.
- 평균 분석 시간은 11.8초(9.2~14.1초)다.

장별 결과(정답/인식/일치, 분석 시간):

- IMG_3466: 12/12/9, 14.1초
- IMG_3461: 12/12/12, 13.1초
- IMG_3464: 13/13/1, 13.6초
- IMG_3465: 12/12/5, 10.3초
- IMG_3467: 8/8/4, 9.2초
- IMG_3448: 10/10/10, 13.0초
- IMG_3463: 5/5/5, 9.2초

표시 문제:

- 틀린 수업에는 '확인 필요'가 하나도 붙지 않았다. IMG_3464·3465·3467의 배지는 모두 "확인 필요 0개"였다.
- 모두 맞은 IMG_3448은 10개 전부 "확인 필요 · 인식 신뢰도 50% · 강의실 없음"으로 표시됐다.
- IMG_3448·IMG_3463에는 시각이 모두 맞았는데도 "시간을 읽을 수 없는 수업이 있습니다." 안내가 붙었다.

## 원인 가설

1. 시간축 오해: 에브리타임 시간축은 `9, 10, 11, 12, 1, 2 …`처럼 12시간제 정시 숫자만 있다. 예전 프롬프트의 "교시 번호만 있고 시각 표시가 없으면" 규칙 때문에 모델이 이것을 교시로 보고 "교시 기준으로 변환/추정했다"는 안내를 내거나 근거 없이 위 고정 문구를 붙인다.
2. 정시에 붙이기: IMG_3464는 1시간이 135px이고 정시 선이 y=62, 197, 332 … 에 있다. 수업 A(가명) 블록 위쪽 y=668은 (668-62)/135 = 4.49시간, 곧 13:30인데 모델은 13:00으로 읽었다. 블록 경계를 가장 가까운 정시 선에 붙인 것이다. 픽셀 비례로 계산하면 수업 B(가명) 아래쪽 y=1387은 18:49로 정답 "약 18:50"과 맞는다.
3. confidence 기준 부재: 예전 프롬프트는 "흐리거나 잘렸거나 칸 경계가 애매하면 낮게"라고만 해서, 모델 confidence가 실제 정확도와 상관이 없다. 앱은 0.7 미만이면 '확인 필요'를 붙이므로(`RecognitionReview.LOW_CONFIDENCE`) 표시가 엉뚱한 곳에 붙는다. IMG_3448의 50%는 강의실이 없어서 낮춘 것으로 보인다.
4. 해상도는 원인이 아니다: 7장 원본은 1242x1005~1410px이라 앱이 축소하지 않는다(긴 변 2048px 초과일 때만 축소). 모델 쪽 media resolution 기본값의 영향은 확인하지 않았다(E 요청).

## 이번 변경 (1~2단계)

### 정답 fixture

- `functions/test/fixtures/timetable-truth.json`: 7장 72개 수업의 요일과 정답 시작·종료 분.
- 수업명은 `C1, C2 …`, 장소는 `P1, P2 …` 가명이다(이미지 안에서 같은 수업·장소는 같은 가명). 장소가 없으면 `null`.
- 근사값(블록 끝 "약 18:50" → 1130)은 `endApprox: true`, 원본에서 글자가 잘린 필드는 `truncated`로 표시한다.
- 이미지 파일은 repo에 넣지 않는다.

### 프롬프트

- 시간축: 세로축에 `9, 10, 11, 12, 1, 2, 3 …` 숫자만 있으면 교시가 아니라 12시간제 정시 눈금이고, 12 다음의 1, 2, 3 … 은 13시, 14시, 15시 … 라고 명시했다. 각 숫자는 그 정시의 가로 눈금선을 가리킨다.
- 비례 읽기: 블록 위·아래 경계를 두 정시 눈금 사이의 비율로 읽는다(가운데 → :30, 4분의 1 → :15). 가장 가까운 정시에 맞추거나 정시·30분으로 반올림하지 않는다. 블록 안에 시각 글자가 있으면 그 글자를 쓴다.
- 교시 규칙 축소: '1교시'처럼 교시 표기가 실제로 있고 시각 표시가 전혀 없을 때만 수업을 빼고 "시간을 읽을 수 없는 수업이 있습니다."를 넣는다. 정시 숫자 눈금에는 적용하지 않고, 모든 수업의 시각을 읽었으면 이 문장을 넣지 않는다.
- confidence 기준: 눈금선과 대조해(또는 시각 글자로) 시작·종료를 확정했고 이름이 잘리지 않았으면 0.9 이상. 눈금 사이를 비율로 추정했거나 이름·강의실 글자가 잘렸거나 흐리면 0.6 이하. 그 밖은 0.6~0.9. 강의실이 보이지 않는다는 이유만으로 낮추지 않는다.

예상 영향: 30분 위치에서 시작·종료하는 블록(눈금 사이 추정)은 confidence 0.6 이하가 되어 검수 화면에 '확인 필요'가 붙는다. 이번 오류가 몰린 블록이 바로 이런 블록이므로 의도된 동작이다. 대신 '확인 필요' 수가 늘 수 있다.

- 앱 코드와 앱 계약(응답 필드). 앱은 수정 없이 그대로 동작한다.
- `docs/BT-026.md` 10.3절(프롬프트 설명)은 이번에는 갱신하지 않았다.

## 평가 스크립트 (3단계 전 실험용, CI 제외)

`functions/scripts/eval-analyze-timetable.mjs`는 앱과 같은 요청을 이미지 한 장씩 Gemini에 직접 보내고, 서버와 같은 기준으로 검사한 뒤 정답 fixture와 비교한다. 채점 함수는 `functions/scripts/eval-scoring.mjs`에 있고, 단위 테스트는 `functions/test/evalAnalyzeTimetable.test.ts`(실제 API 호출 없음)다.

### 무엇이 서버와 같고 무엇이 다른가

- 같은 것
  - 요청 본문: `analyzeTimetableTask.buildRequest`를 그대로 불러 만든다(PROMPT, 안내 문장, `이미지 0:`, inlineData, temperature 0, maxOutputTokens 8192).
  - 응답 스키마: `toGeminiSchema(output, "typesOnly")`.
  - 응답 검사: 서버와 같은 zod output 스키마와 `verify`.
  - 호출 제한 시간: `analyzeTimetableTask.timeoutMs`(이번 변경으로 30초 → 55초. E의 비교는 30초일 때 실행했다).
- 다른 것
  - `gemini.ts`·`gateway.ts`를 거치지 않고 `@google/genai`를 직접 부른다. 그래서 `--thinking`, `--resolution`을 실험할 수 있다.
  - 하루 횟수 차감과 재시도(최대 2회)가 없다. 실패는 그대로 기록한다.
  - 앱은 업로드 전에 JPEG 품질 90으로 다시 인코딩하지만, 스크립트는 원본 파일을 그대로 보낸다(이번 7장은 크기를 줄이지 않으므로 해상도는 같다).
- 시작하기 전에 `lib/`의 컴파일 결과를 불러오므로 `npm run build`가 먼저 필요하다.

### 인자

- `--images <폴더>` (필수): `IMG_xxxx.jpeg` 파일이 있는 폴더. repo 안이면 거부한다. 파일명(IMG_xxxx)으로 fixture 항목과 연결하고, 짝이 없는 파일·항목은 건너뛰고 알린다.
- `--out <폴더>` (필수): 결과 저장 폴더. repo 안이면 거부한다(결과에 실제 과목명이 들어갈 수 있다).
- `--model <모델 ID>` (필수): 예 `gemini-3.5-flash-lite`.
- `--truth <파일>`: 기본 `functions/test/fixtures/timetable-truth.json`.
- `--thinking <값>`: `default`(설정 안 보냄, 기본) / `off`(thinkingBudget 0) / `minimal`·`low`·`medium`·`high`(thinkingLevel) / 정수(thinkingBudget).
- `--resolution <값>`: `default`(기본) / `LOW`·`MEDIUM`·`HIGH`(요청 설정 mediaResolution) / `ULTRA`(이미지 part 단위 `MEDIA_RESOLUTION_ULTRA_HIGH`). 모델이 지원하지 않는 값이면 API 오류로 기록된다.
- `--repeat <횟수>`: 같은 이미지를 몇 번 보낼지(1~20, 기본 1).
- `--only <키,키>`: 일부 이미지만(예 `IMG_3464,IMG_3465`).
- `--yes`: 외부 전송 동의. 없으면 "이미지 N장을 외부 API로 보냅니다" 안내만 출력하고 아무것도 보내지 않는다.

### 환경 변수

- `GEMINI_API_KEY`만 읽는다. 키는 출력·저장하지 않고, 오류 문구에 키가 섞이면 `[KEY]`로 바꾼다. `.secret.local` 등 파일은 읽지 않는다. 없으면 안내 후 종료한다.

### 출력

- 콘솔: 장별·반복별 정답/인식/일치 수, 시작·종료 어긋난 분 분포, 누락·초과, 호출 시간(초), 입력·출력 토큰 수, 맞은 수업 중 confidence 0.7 미만 비율, 틀린 수업 중 0.7 이상 비율, 5분 단위가 아닌 시각 값 개수, 그리고 합계.
- 파일: `--out` 폴더에 `eval-analyze-timetable-<시각>.json`(설정, 프롬프트 해시, 장별 인식 결과와 채점, 합계)과 같은 이름의 `.txt`(콘솔 요약).
- 일치 기준: (요일, 시작, 종료)가 정확히 같아야 일치. `endApprox` 항목은 종료 ±30분 허용. 수업명은 비교하지 않고, 일치를 먼저 묶은 뒤 남은 것을 요일별 시작 순서로 짝지어 어긋난 분을 잰다.

### E가 돌릴 때의 절차

1. 비용 승인을 받는다. 7장 × 설정 수 × 반복 수만큼 호출된다(예: 설정 4개 × 반복 2회 = 56회).
2. 이미지 7장을 repo 밖 폴더에 둔다(C 담당에게 받는다).
3. 키는 파일에 쓰지 않고 현재 셸에만 설정한다.
   - PowerShell: `$env:GEMINI_API_KEY = "<키>"` (끝나면 `Remove-Item Env:GEMINI_API_KEY`)
   - bash: `export GEMINI_API_KEY=<키>` (끝나면 `unset GEMINI_API_KEY`)
4. `cd functions && npm run build`
5. 먼저 `--yes` 없이 실행해 대상과 호출 횟수를 확인한다.
6. 기준선부터 돌린다: `--thinking default --resolution default --repeat 2`
7. 바꿔 가며 돌린다: `--resolution HIGH`, `--resolution ULTRA`, `--thinking low`, `--thinking off` 등. 한 번에 하나씩만 바꾼다.
8. 결과 폴더의 `.txt`·`.json`을 C 담당에게 전달한다. 3단계(좌표 출력과 서버 계산) 진행 여부를 이 결과로 정한다.

## 모델 비교 결과(E, 2026-11-25)

E가 위 평가 스크립트로 실행한 결과다.

- 규모: 7장 × 6개 설정 × 2회 = 84회 실행, 비용 약 $0.3.
- `gemini-3.5-flash-lite`: thinking·해상도를 바꿔도 시각 일치 47~56%로 비슷했다. thinking 끄기(budget 0)는 이 모델에서 400으로 거부됐다.
- `gemini-3.8-flash`: 성공한 호출 기준 94% 일치. 평균 15~20초, 14회 중 5회는 30초 제한에 걸려 실패했다.
- 틀린 수업은 모든 설정에서 confidence 0.7 이상이라 '확인 필요'가 붙지 않았다.
- 비교용 이전 AVD 측정(`gemini-3.5-flash-lite`, 이전 프롬프트): 72개 중 46개(64%) 일치, 한 장 9~14초.

### 방향 제안

- 운영 모델을 `gemini-3.8-flash`로 바꾼다. 환경 설정(`GEMINI_MODEL`)과 함수 제한 시간은 E가 맡는다.
- 모델 호출 제한 시간은 C가 늘린다(아래 "모델 호출 제한 시간" 절).
- 남는 오류는 검수 화면에서 원본 이미지와 대조해 보완한다(5단계, 별도 이슈).

### 남은 위험과 미정 사항

- confidence가 정확도와 무관해서 '확인 필요' 경고를 믿을 수 없다.
- 지연이 15~20초이고, 여러 장을 한 번에 보내면 더 길어질 수 있다.
- 5장 동시 분석 시간은 측정하지 않았다.
- 새 프롬프트의 효과는 확인되지 않았다. 같은 채점 기준으로 이전 프롬프트를 돌린 비교가 없다.

## 모델 호출 제한 시간 (30초 → 55초)

- 정하는 곳: `functions/src/ai/tasks/analyzeTimetable.ts`의 `analyzeTimetableTask.timeoutMs` 하나다. `gateway.ts`가 이 값을 그대로 `client.generate({ timeoutMs })`로 넘기고, `gemini.ts`는 받은 값으로 AbortController 타이머와 SDK `httpOptions.timeout`을 건다. 그래서 `gemini.ts`·`gateway.ts`·`types.ts`는 바꾸지 않았다.
- 처음에는 90초로 올렸다가(a2674a9) 아래 재시도 계산 때문에 55초로 낮췄다.
- 평가 스크립트도 `task.timeoutMs`를 쓰므로 이후 평가는 55초 제한으로 돈다.
- 테스트: `analyzeTimetable.test.ts`의 요청 본문 테스트가 `timeoutMs` 55000과 `timeoutMs × 2 + 500 < 120000`을 확인한다.

### 시간 계산

- 앱 제한 130초(`FirebaseTimetableRecognitionRepository`), 함수 제한 120초(`functions/src/index.ts`의 `timeoutSeconds: 120`), 모델 한 번 호출 55초.
- 모델 시간 초과는 `AI_TIMEOUT`이 아니라 504로 끝난다. `@google/genai`가 `httpOptions.timeout`을 `X-Server-Timeout` 헤더(초)로도 보내서, Gemini 서버가 앱 쪽 타이머보다 먼저(마감 직전) 504 `DEADLINE_EXCEEDED`를 돌려준다. E 결과에서도 3.8-flash 실패 5회가 모두 28.3~28.8초(30초 제한)의 API 504였다.
- `gemini.ts`의 `classify`는 5xx를 일시적 오류(`AI_UNAVAILABLE`, transient)로 분류하고, 게이트웨이는 일시적 오류를 0.5초 뒤 한 번 더 부른다(`config.ts`의 `MAX_ATTEMPTS = 2`). 그래서 최악값은 제한의 약 2배다.
- 계산식: 최악 = 호출 전 작업(인증·하루 횟수 차감·Storage 이미지 읽기, 몇 초) + 제한 × 2 + 0.5초 + 응답 검사.
  - 55초: 55 × 2 + 0.5 = 110.5초 + 호출 전 작업 → 함수 120초 안(여유 약 9초에서 호출 전 작업을 뺀 만큼), 앱 130초 안.
  - 90초였다면: 90 × 2 + 0.5 = 180.5초 → 함수 120초를 넘어 함수가 끊기고, 앱은 `AI_TIMEOUT`이 아닌 함수 시간 초과 오류를 받으며 하루 횟수는 이미 차감된다.
  - 30초(이전): 60.5초. 함수 안에 들어가지만 3.8-flash의 느린 이미지는 두 번 모두 실패했다.
- 한 번에 성공하는 경우 3.8-flash 성공 호출은 7~27초(평균 15.5초)라 55초 안에 든다. 30초에서 실패한 5회가 55초 안에 끝나는지는 아직 모른다.
- 남는 위험: 호출 전 작업이 9초를 넘으면 재시도 경로가 120초를 넘을 수 있다(이미지 5장·14MiB 읽기 시간은 재지 않았다).

### 90초로 올릴 수 있는 조건

E가 마감 초과 504의 재시도를 멈추고(예: `gemini.ts`의 `classify`에서 마감 504를 `AI_TIMEOUT`으로 분류) 함수 제한을 늘리면 90초로 올릴 수 있다. 그때는 이 값과 테스트, 앱 제한 130초를 함께 맞춘다.

### E에게 요청할 것

- (우선) 모델 시간 초과로 온 504 `DEADLINE_EXCEEDED`를 재시도하지 않게 하는 방법. `gemini.ts`·`gateway.ts`·`config.ts`는 E 담당이라 이번에 바꾸지 않았다.
- 또는 `gateway.ts`에서 남은 시간을 보고 재시도를 생략하는 방법(작업별 전체 시간 예산), 또는 analyzeTimetable만 재시도 1회로 줄이는 방법 검토.
- 운영 모델 변경 시 `analyzeTimetable` 함수 제한(현재 120초)을 늘릴지 결정. 늘리면 앱 제한 130초도 함께 늘려야 한다(앱 쪽은 C가 맞춘다).
- 55초 제한으로 3.8-flash를 다시 돌려 30초 초과 실패가 사라지는지, 최대 소요 시간이 얼마인지 확인.

## 5단계 최소 버전: 검수 화면 원본 보기

틀린 수업에도 '확인 필요'가 붙지 않으므로(confidence 0.7 이상) 사용자가 원본과 직접 대조할 수 있게 했다. 행마다 원본 이미지를 매핑하는 기능은 이번 범위가 아니다.

- 검수 화면 상단의 [원본 보기]: 올린 이미지 전체를 전체 화면(`OriginalImagesDialog`)으로 보인다. 좌우로 밀거나 [이전]·[다음]으로 넘기고, 두 손가락으로 확대(1~5배)·확대 중 끌어서 이동·두 번 탭으로 확대/원래 크기(`ZoomImageView`, Android 기본 `ScaleGestureDetector`·`GestureDetector`, 새 라이브러리 없음).
- 이미지 전달: 업로드할 때 만든 압축 JPEG(모델이 받는 것과 같은 이미지)를 앱 캐시 `cacheDir/timetable_originals/{batchId}/{i}.jpg`에 저장하고 그 경로를 검수 화면에 넘긴다(`RecognitionImageCache`, `TimetableImageUploader.LocalCopy`). 사진 선택기 Uri는 넘기지 않는다.
- 삭제: 검수 종료(저장·뒤로 모두 `onReviewFinished`), 선택 변경·화면 종료(`discard`), 다시 분석(새 묶음 시작) 때 지운다. 프로세스가 끝나 지우지 못한 사본은 업로드 화면을 새로 열 때 지운다(`clearAll`).
- 파일이 없으면(앱 재시작 뒤 정리 등) 버튼을 숨기고, 누르는 순간 없으면 안내 후 숨긴다. 사본 저장이 실패해도 업로드·인식은 계속하고 버튼만 숨긴다.
- 저장되는 `Course`·Firestore 필드, 서버는 바꾸지 않았다.
- 이미지 디코딩은 background 스레드에서 화면 긴 변의 2배 이하로 줄여 읽는다(업로드 화면 썸네일과 같은 `inSampleSize` 방식).
- 테스트: `RecognitionImageCacheTest`(순서·삭제·경로 이탈 이름 거부·실패 시 되돌림·남은 사본 정리·없는 파일 걸러내기), `TimetableImageUploaderLocalCopyTest`(업로드 시 저장, 검수 종료·discard·재시작 시 삭제, 늦게 끝난 준비 결과 삭제, 저장 실패해도 업로드 계속, 잘못된 이미지면 저장 안 함), `ZoomMathTest`(확대 범위, 가장자리, 넘기기 판정, 페이지 범위).
- AVD 확인은 아직 하지 않았다.

### 시작·종료 ±30분 빠른 조정

- 인식 검수 행마다 [시작 30분 앞/뒤], [종료 30분 앞/뒤] 버튼. 행의 시각만 바꾸고 바로 목록을 다시 그려 겹침·수정 필요·확인 버튼 상태를 다시 계산한다(`RecognitionDrafts.canShift`·`shift`).
- 0분 미만·1440분 초과, 종료가 시작과 같거나 앞서는 조정은 버튼을 막는다. 시각을 읽을 수 없는 행(수정 필요)은 [수정] 화면으로만 고친다. 기존 [수정] 화면은 그대로다.
- 조정해도 인식 신뢰도 표시는 그대로 남는다. 기존 시간표 수정 화면(`forEditing`)에는 버튼이 없다.
- 테스트: `RecognitionDraftsShiftTest`(±30분, 0·1440 경계, 종료가 시작 앞으로 가지 않음, 읽을 수 없는 시각·잘못된 행, 조정 뒤 겹침 생김/사라짐, 다른 행·신뢰도 유지).
