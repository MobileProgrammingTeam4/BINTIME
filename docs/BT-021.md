# BT-021 / Issue #21 — 채팅 데이터 모델·채팅방/메시지 실시간 구독

채팅은 Realtime Database(RTDB)에 저장한다. BT-021(#21)은 **RTDB 데이터 모델·구독(읽기)·보안 규칙**, BT-022(#22)는 **메시지 전송·읽음·화면 연결·메시지 트리거**다. 경로·필드는 [BT-012](./BT-012.md) RTDB 절과 PR #77 합의를 따른다.

- RTDB 인스턴스: `bintime-mobile-default-rtdb` (**asia-southeast1**). 앱은 `google-services.json`의 `firebase_url`을 그대로 쓰고 주소를 코드에 넣지 않는다. 실제 RTDB로 테스트하기 전에 [아래 확인](#google-servicesjson-확인)을 먼저 한다.
- 보안 규칙: 저장소 루트 `database.rules.json` (`firebase.json`의 `database.rules`)
- 실제 프로젝트에는 **이 규칙이 게시되어 있다**(#90 병합 후 B 게시). 2026-11-13 BT-022에서 실제 규칙을 CLI로 읽어 저장소 `database.rules.json`과 같음을 확인했다. 규칙 변경은 PR로만 하고, 병합 후 게시한다([7장](#7-실제-프로젝트-반영-승인-후)).

## 1. 데이터 구조

```text
chatRooms/{matchId}/members/{uid}:     { joinedAt }
chatRooms/{matchId}/messages/{pushId}: { senderId, content, createdAt }
userChatRooms/{uid}/{matchId}:         { otherUid, lastMessage, lastMessageAt, lastMessageId, recentMessageIds, unreadCount, status, hidden }
```

| 항목 | 계약 |
|---|---|
| `matchId` | `matches/{matchId}` 문서 ID = `requestId`(64자리 hex). 별도 roomId 없음 |
| `messageId` | RTDB push 키. 노드 안에 저장하지 않고 snapshot key로 읽는다 |
| `senderId` | 필수. Rules에서 `=== auth.uid` |
| `content` | 문자열 **1~1000자**, 공백(스페이스·탭·줄바꿈)만 있으면 거부. **최대 1000자는 이 이슈에서 확정** |
| `createdAt` | 서버 시각(`ServerValue.TIMESTAMP`)만 허용. 앱 모델은 epoch ms `long` |
| `userChatRooms` | 서버가 갱신(BT-034 채팅방 생성, BT-022 메시지 트리거). 앱은 본인 `unreadCount`를 0으로만 쓸 수 있다 |
| `lastMessage`·`lastMessageAt`·`lastMessageId` | 메시지 트리거가 두 멤버 모두에 쓴다. `lastMessageId`(push 키)는 **BT-022에서 추가**: 같은 시각이면 키가 큰 쪽이 마지막 메시지다. 앱은 읽지 않는다 |
| `recentMessageIds` | **BT-022에서 추가(PR #96 리뷰 2)**. `{ messageId: createdAt }`, 멤버별로 트리거가 처리한 최근 50개. 안읽음 증가와 같은 트랜잭션에서 기록해 이벤트 재전달(at-least-once)·순서 뒤바뀜·부분 실패 후 재처리에서 같은 메시지를 두 번 세지 않는다. 서버 전용, 앱은 읽지 않는다 |
| `unreadCount` | 메시지 트리거가 **보낸 사람이 아닌 멤버**만 +1(트랜잭션, 이미 처리한 메시지면 건너뜀). 앱은 방을 보고 있을 때 0으로 쓴다(`markRead`) |
| `status` | Firestore `matches.status`(`ACTIVE`/`ENDED`)를 서버가 복사한 값. 원본은 Firestore |
| `hidden` | 채팅방 나가기(BT-043). ENDED 검사가 필요해 Callable에서 서버가 쓴다 |

## 2. 보안 규칙 요약 (`database.rules.json`)

| 경로 | 읽기 | 쓰기 |
|---|---|---|
| 루트·`chatRooms/{matchId}` 전체 | 거부 | 거부 |
| `chatRooms/{matchId}/members` | 그 방의 멤버 | 거부(서버 전용) |
| `chatRooms/{matchId}/messages` | 그 방의 멤버 (`.indexOn: createdAt`) | 멤버가 **새 메시지만** 생성. 수정·삭제 금지, 필드 3개 외 금지 |
| `userChatRooms/{uid}` | 본인 | 거부. 예외: 본인·기존 항목의 `unreadCount = 0` (삭제는 거부) |

- ENDED 방에서도 전송할 수 있어야 하므로 **규칙은 매칭 상태를 검사하지 않는다**(종료는 차단이 아님).
- 서버(Admin SDK)는 규칙을 우회하므로 BT-034 채팅방 생성 함수 안에서 참여자를 직접 검증해야 한다.
- RTDB 규칙의 정규식은 `\s`·`\S`를 지원하지 않고, 정규식 안의 `\t`·`\n`도 공백 문자로 해석되지 않는다. 그래서 공백 검사는 `replace(...)` 후 길이로 한다.

## 3. Android 구조 (`chat/`)

| 클래스 | 역할 |
|---|---|
| `ChatRepository` | 기존 인터페이스 그대로(BT-009·010). 콜백 + `Registration` |
| `ChatRepositories.get(context)` | 저장소 선택. Firebase가 초기화되면 `FirebaseChatRepository`, 아니면(CI·`google-services.json` 없음) `MockChatRepository.shared()`. 로그인 UID가 바뀌면 새로 만든다 |
| `FirebaseChatRepository` | `observeRooms`(`userChatRooms/{uid}`), `observeRoom`(`userChatRooms/{uid}/{matchId}`), `observeMessages`(`messages` `createdAt` 순 최근 100개). 해제 후 늦은 콜백 무시. 권한 거부·RTDB 주소 없음·로그인 전은 `onError` |
| `ChatRtdbMapper` | RTDB 값 ↔ `ChatMessage`·`UserChatRoomEntry`·`ChatRoom`. 형식이 틀린 노드는 건너뛴다 |
| `ChatRoomsCombiner` | 목록 항목에 매칭 스냅샷·상대 프로필을 붙인다. 새로 생긴 방만 구독하고 사라진 방은 해제 |
| `ChatSendPolicy` | (BT-022) 본문 정리(앞뒤 공백 제거, 1~1000자), 재전송 시 같은 push 키 재사용, 거부된 쓰기가 내 메시지인지 판정 |
| `ChatSendAttempt` | (BT-022) 한 번 보내기의 결과 처리. 시간 초과와 서버 응답 중 먼저 온 것만 알리고, 시간 초과 뒤 늦은 성공 응답은 재전송 키를 지우지 않는다(PR #96 리뷰 1) |
| `MatchInfoSource` / `PartnerSource` | 매칭 스냅샷(`matches/{matchId}`)·상대 공개 프로필(`publicProfiles/{uid}`) 출처 |

**아직 연결하지 않은 것**

- `MatchInfoSource`: 지금은 `UNAVAILABLE`. D의 BT-031이 `matches`를 만든 뒤 **BT-034**에서 Firestore 구현을 붙인다. 그 전에는 `meetingDate = null`, 시간 0, 상태는 `userChatRooms.status`.
- `PartnerSource`: 지금은 `UNAVAILABLE`(이름 "상대"). BT-014(#79)는 병합됐지만 `ProfileRepository`에 다른 사용자의 `publicProfiles`를 읽는 메서드가 없어 B와 방식을 맞춘 뒤 연결한다.
- `endMatch`: D의 BT-038. `leaveRoom`: BT-043. 그 전에는 Firebase 모드에서 `onError`(화면은 실패 안내).
- AI 답장 칩(BT-041)·후기(BT-044)는 아직 Mock이다.

**BT-022에서 연결한 것**

- 화면(`ChatListFragment`, `ChatRoomActivity`)은 `ChatRepositories.get`을 쓴다. 내 메시지 판별은 로그인 UID(`currentUid()`)이고, 로그인 전이면 채팅방을 열지 않는다. 고정 UID `"me"`는 Mock 모드에만 남는다. 목록 데모 상태 전환(제목 길게 누르기)도 Mock 모드에서만 동작한다.
- `sendMessage`: push 키 + `{senderId, content, createdAt: ServerValue.TIMESTAMP}`.
  - `.info/connected`가 false면 쓰지 않고 바로 실패한다(RTDB는 오프라인 쓰기를 조용히 대기열에 넣기 때문).
  - 연결돼 있어도 10초 안에 응답이 없으면 실패. 입력 내용은 그대로 남는다.
  - 같은 내용으로 다시 보내면 같은 push 키를 쓴다. 앞선 쓰기가 늦게 반영됐으면 규칙(`!data.exists()`)이 거부하고, 그 키의 값이 내 메시지면 성공으로 본다 → 중복 메시지가 생기지 않는다.
  - 시간 초과 뒤 앞선 쓰기의 성공 응답이 늦게 와도 재전송 키를 지우지 않는다. 화면은 실패로 알고 있어 사용자가 같은 내용을 다시 보내기 때문이다. 그래서 늦은 성공 뒤 같은 문장을 **일부러** 한 번 더 보내면 새 메시지가 아니라 "이미 저장됨"으로 처리된다(앞 메시지는 이미 화면에 보인다).
  - 응답이 올 때까지 전송 버튼을 잠근다. 방마다 한 번에 하나만 보낸다.
- `markRead`: 방을 열 때, 보고 있는 중 새 메시지·안읽음 증가가 올 때 내 `unreadCount`를 0으로. 구독으로 이미 0인 것을 알면 쓰지 않는다.
- 메시지 트리거 `chatOnMessageCreated`(`functions/src/chat/`): `chatRooms/{matchId}/messages/{messageId}` 생성 시 발신자가 멤버인지 확인하고, 각 멤버의 `userChatRooms` 항목을 트랜잭션으로 갱신한다. 항목이 없는 멤버에게는 만들지 않고(BT-034 몫), `hidden`은 건드리지 않는다(BT-043에서 정함).
  - **지역: `asia-southeast1`**(RTDB 인스턴스와 같은 지역, Firebase 권장). 앱이 호출하는 Callable(asia-northeast3)과 무관하다.
  - Functions 에뮬레이터는 RTDB 트리거를 `us-central1`일 때만 실행해서, 에뮬레이터 안(`FUNCTIONS_EMULATOR=true`)에서만 `us-central1`을 쓴다. 배포에는 영향이 없다.
  - 실패 재처리(PR #96 재검토 P2): `retry: true`. 일시 오류(RTDB 읽기·트랜잭션 실패)는 예외를 던져 플랫폼이 다시 보낸다(2세대: 10~600초 지수 백오프, 최대 24시간). 발생 후 **1시간**이 지난 이벤트는 처리하지 않고 오류 로그만 남긴 채 정상 종료해 재시도를 멈춘다(그 메시지의 목록 갱신은 빠지고 메시지 자체는 남는다). 형식 오류·비멤버 발신자는 재시도하지 않는다. 실패 이벤트당 추가 호출은 대략 10회 이내.
  - 중복 집계 방지(PR #96 리뷰 2): 멤버별 `recentMessageIds`(최근 50개)에 있거나, 목록이 가득 찼는데 그중 가장 오래된 것보다 오래된 메시지면 건너뛴다. 멤버마다 따로 기록하므로 한쪽만 반영된 뒤 재처리해도 반영된 쪽은 그대로다. 남은 한계: 새 메시지가 50개 넘게 밀린 뒤에야 처음 도착하면 그 1건은 세지 않는다(안읽음이 늘지 않는 쪽으로만 틀림, 사실상 없음).

## 4. 테스트

```bash
# 앱 단위 테스트(변환기·조립기 포함)
gradlew.bat testDebugUnitTest

# Rules·메시지 트리거 테스트(로컬 RTDB 에뮬레이터, functions/emulator-tests/chat-rules.test.ts·chat-fanout.test.ts)
firebase emulators:exec --project demo-bintime --only database "npm --prefix functions run test:emulator"
```

`npm --prefix functions test`는 에뮬레이터 테스트를 제외한다(`emulator-tests/**`). 에뮬레이터 테스트는 `FIREBASE_DATABASE_EMULATOR_HOST`가 없으면 건너뛰고, 로컬 주소가 아니면 실행을 거부한다.

### google-services.json 확인

실제 RTDB(에뮬레이터가 아닌)로 앱을 테스트하는 사람은 먼저 확인한다. RTDB가 미국 외 리전(asia-southeast1)이라, RTDB를 만들기 전에 받은 `google-services.json`에는 `firebase_url`이 없어 앱이 RTDB에 접속하지 못한다.

1. 앱 모듈의 `app/google-services.json`에서 `project_info.firebase_url` 값을 확인한다.
   ```bash
   grep firebase_url app/google-services.json
   ```
2. 값이 `https://bintime-mobile-default-rtdb.asia-southeast1.firebasedatabase.app`이 아니거나 줄이 없으면, Firebase 콘솔 → 프로젝트 설정 → 내 앱(Android)에서 파일을 다시 받아 덮어쓰고 Gradle Sync를 다시 한다.
3. 이 파일은 계속 커밋하지 않는다(README 7장).

## 5. 에뮬레이터로 채팅방 만들어 보기

실제 채팅방은 BT-034에서 서버가 매칭 수락 후 만든다. 그 전에는 로컬 에뮬레이터에 시드한다. **실제 RTDB에는 쓰지 않는다.**

1. 에뮬레이터 실행 — 앱의 네임스페이스(`bintime-mobile-default-rtdb`)에 규칙이 적용되도록 프로젝트 ID를 맞춘다. 로컬에서만 동작한다.
   ```bash
   firebase emulators:start --only database --project bintime-mobile
   # 메시지 트리거(마지막 메시지·안읽음 수)까지 볼 때: --only database,functions
   ```
   실제 프로젝트 ID를 쓰므로 **반드시 `--only database` 또는 `--only database,functions`로만 띄운다.** `functions`를 함께 띄우면 Gemini·요청 함수도 로드되지만 채팅 화면은 호출하지 않으며, 이 상태에서 그 함수들을 호출하지 않는다(실제 Firestore·Gemini에 닿을 수 있음). 앱은 Auth 에뮬레이터 연결이 없어 로그인은 실제 Firebase Auth를 쓴다(로그인은 RTDB에 쓰지 않음). `--only` 없이 실행하면 `firebase.json`의 Functions 에뮬레이터까지 함께 떠서, 에뮬레이터가 아닌 서비스(실제 Firestore·Gemini 등)를 호출할 수 있다. 앱 연결 없이 Rules·시드만 확인할 때는 1·2단계 모두 `--project demo-bintime`을 쓰고 `--ns`를 생략한다.
2. 시드 — 내 UID는 앱에서 로그인한 계정의 UID(Firebase 콘솔 Authentication 또는 로그)를 쓴다.
   ```bash
   npm --prefix functions run seed:chat -- --me <내 UID> --ns bintime-mobile-default-rtdb
   ```
   진행 중(ACTIVE) 방 1개와 종료(ENDED) 방 1개, 메시지, 양쪽 `userChatRooms`를 만든다. 같은 인자로 다시 실행하면 같은 방을 덮어쓴다. 호스트가 `127.0.0.1`/`localhost`가 아니면 거부한다.
3. 앱 연결(디버그 빌드만) — `app/src/debug/res/values/config_chat_local.xml`을 만들고 커밋하지 않도록 `.git/info/exclude`에 등록한다.
   ```xml
   <resources>
       <!-- 에뮬레이터·실기기 모두: adb reverse tcp:9000 tcp:9000 후 127.0.0.1 -->
       <string name="chat_rtdb_emulator_host" translatable="false">127.0.0.1</string>
   </resources>
   ```
   ```bash
   adb -s <기기> reverse tcp:9000 tcp:9000   # 기기마다, adb 서버를 다시 켜면 다시 실행
   ```
   값이 비어 있으면(기본 `res/values/config_chat.xml`) 실제 RTDB를 쓴다. 릴리스 빌드는 디버그 리소스를 포함하지 않는다.

   **`10.0.2.2`를 쓰지 않는 이유(BT-022 확인)**: RTDB 에뮬레이터는 첫 연결 때 자기 주소를 `127.0.0.1:9000`으로 알려 주고, SDK는 **재연결할 때 그 주소로 접속**한다. Android 에뮬레이터에서 `10.0.2.2`로 붙으면 네트워크가 한 번 끊긴 뒤 `ws://127.0.0.1:9000`(기기 자신)으로만 재시도해서 다시 연결되지 않는다. 실제 RTDB에는 없는 로컬 전용 문제다.

   **오프라인 확인 방법**: `adb reverse`는 기기 네트워크가 아니라 adb를 거치므로 비행기 모드로는 끊기지 않는다. `adb reverse --remove`도 이미 맺어진 연결은 그대로 둔다. 끊으려면 `adb kill-server` 후 `adb start-server`, 복구는 기기마다 `adb reverse`를 다시 실행한다(앱은 최대 약 30초 안에 다시 연결).

> BT-022부터 시드 데이터를 채팅 목록·채팅방 화면에서 확인할 수 있다.

## 7. 실제 프로젝트 반영 (승인 후)

각 단계는 담당자(E) 승인 후 하나씩 진행한다. 서비스 계정 키는 만들지 않는다.

1. **Rules 게시**: 이미 반영됨(#90 병합 후 B 게시, 2026-11-13 저장소와 일치 확인). 이후 규칙을 바꿀 때는 현재 규칙을 먼저 백업하고(`MSYS_NO_PATHCONV=1 firebase database:get /.settings/rules --project bintime-mobile --instance bintime-mobile-default-rtdb`, Git Bash는 경로 변환을 꺼야 함) `firebase deploy --only database --project bintime-mobile`. 문제가 생기면 백업한 규칙으로 되돌린다.
2. **트리거 배포**: `firebase deploy --only functions:chatOnMessageCreated --project bintime-mobile`(다른 함수는 재배포하지 않음). 처음이면 Eventarc 관련 API 활성화 확인이 뜰 수 있다.
3. **테스트 방**: Firebase CLI 로그인 권한으로 `firebase database:update`를 써서 `chatRooms/test_*`와 두 계정의 `userChatRooms`를 만들고, 검증 후 `firebase database:remove`로 지운다.
