# BT-051 / Issue #51 — 신고 화면·사유 제출·검토 가능한 신고 기록

담당 B / P1 / Sprint 4. 선행 BT-045·BT-046(#129)·BT-010(E 신고 화면 목업). 이 브랜치는 BT-046 차단 기능 위에 쌓았다(#129 병합 후 develop 기준으로 정리).

## 1. 팀 결정 (2026-11-25, B)

| 항목 | 결정 |
|---|---|
| 저장 경로 | 서버 Callable `submitReport`만. `reports`는 일반 사용자(신고자·대상 포함) 읽기·쓰기 모두 거부. 검토는 콘솔·Admin |
| 중복 정책 | **같은 신고자·대상·매칭당 1건**(매칭 밖 신고는 `matchId=null`로 따로 1건). 문서 ID를 이 세 값의 해시로 고정해 트랜잭션에서 막는다 |
| 대상 검증 | `matchId`가 있으면 두 사람이 그 매칭의 참여자여야 함. 없으면 대상 사용자가 있어야 함. 자기 자신 신고 거부. 탈퇴한 상대도 함께한 매칭 안에서는 신고 가능 |
| 함께 차단 | 신고 저장 뒤 BT-046 `BlockService.block`. 차단만 실패하면 신고는 남기고 `blocked=false`. 이미 신고한 경우에도 함께 차단을 고르면 차단은 한다(차단 진입점이 신고 화면뿐이라) |
| 상대 알림 | 하지 않는다. 신고 사실은 상대에게 공개하지 않음 |
| 개인정보 | 신고자·대상 UID, 매칭 ID, 사유, 직접 입력(최대 500자)만. 이름·이메일·대화 내용은 저장하지 않음 |

## 2. 데이터와 API

```
reports/{reportId}   // reportId = sha256(JSON [reporterUid, targetUid, matchId|null])
  reporterUid, targetUid, matchId (string|null),
  reasons: ReportReason[] (정렬, 중복 없음, 1~9개),
  detail: string|null (앞뒤 공백 제거, ≤500),
  alsoBlock: boolean, status: "SUBMITTED", createdAt (서버 시각)

submitReport({ targetUid, matchId, reasons, detail, alsoBlock }) → { reportId, blocked }
```

- 리전 `asia-northeast3`, 토큰 UID와 학교 이메일만 신원으로 쓴다. 입력 스키마는 strict라 `reporterUid` 같은 추가 값은 `invalid-argument`.
- 사유 값은 앱 `ReportReason` enum 이름과 같다: `NO_SHOW, NO_CONTACT, ONE_SIDED_CANCEL, ABUSIVE_LANGUAGE, INAPPROPRIATE_MEETING, RELIGION_MLM_PROMOTION, INAPPROPRIATE_PROFILE, IMPERSONATION, SPAM`. 사유를 추가하면 `functions/src/safety/report.ts`의 `REPORT_REASONS`와 함께 바꾼다.
- 오류: `already-exists/ALREADY_REPORTED`(details.blocked 포함), `permission-denied/NOT_PARTICIPANT`, `not-found/USER_NOT_FOUND`, `invalid-argument/SELF_REPORT|INVALID_INPUT`, 그 밖은 `unavailable`(retryable). 로그에는 UID·신고 내용 없이 오류 코드와 requestId만.
- `status`는 검토 단계를 위한 자리다. 검토 처리(조치·반려) 화면과 보관 기간은 후속 합의(SM·신고 담당).

## 3. 앱

| 파일 | 역할 |
|---|---|
| `report/ReportRepository`, `ReportRepositories`, `FirebaseReportRepository`, `MockReportRepository` | 접수. Firebase는 Callable, Mock은 같은 중복 정책과 Mock 차단 |
| `report/ReportSubmitViewModel` | 제출 상태. 회전해도 이어지고 제출 중·완료 뒤 재제출 막음. 실패 안내는 한 번만 |
| `report/ReportActivity` | E의 BT-010 화면을 그대로 쓰고 제출만 연결. 완료 화면 문구를 실제 접수 문구로 교체, 함께 차단 결과·이미 신고 안내 추가 |

진입점(기존): 채팅방 옵션 '신고하기'(`ChatRoomActivity`), 후기 작성의 '만나지 못했어요'(`ReviewWriteActivity`, E). 채팅방은 `ChatRoom.matchId`(BT-034상 실제 방 키 = 처음 연결된 매칭 ID)를 넘기는데, 같은 두 사람의 매칭이라 서버 참여자 검사는 통과한다. 방을 재사용하면 신고 기록의 매칭 ID가 그 방의 첫 매칭이 된다(후속: E와 대표 약속 matchId를 넘길지 확인).

## 4. E(후기 BT-044)와의 연동 계약

- 후기 화면은 `ReportActivity.intent(context, PartnerSummary, matchId)`만 호출한다. 신고 저장·중복·차단은 B가 맡는다.
- 후기와 신고는 서로 독립이다. 신고했다고 후기를 막거나 후기 공개 조건을 바꾸지 않는다(필요하면 BT-044에서 별도 결정).
- 같은 매칭을 후기 화면과 채팅방에서 각각 신고해도 1건으로 합쳐진다(같은 matchId일 때).

## 7. 남은 한계·후속

1. 운영 반영: `submitReport`와 `reports` Rules는 SM 확인 후 BT-046과 함께 배포. 배포 전 실제 앱에서는 접수 실패 안내가 뜬다.
2. 신고 검토 화면·조치(경고·정지)와 신고 기록·보관 방 메시지의 보관 기간은 후속 합의.
3. 신고 남용(여러 매칭으로 같은 사람을 반복 신고)은 매칭 단위로만 막는다. 하루 횟수 제한은 두지 않았다.
