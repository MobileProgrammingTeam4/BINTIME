## 검색 Callable `searchMatches`

리전 `asia-northeast3`. 입력은 없다. 필터는 앱이 저장한 `matchSettings/{토큰 UID}`가 기준이다.

| 단계 | 규칙 |
|---|---|
| 인증 | 토큰 UID 필수(`UNAUTHENTICATED`). 학교 이메일 검사는 #87 `checkSchoolEmail` 재사용(`PERMISSION_DENIED`) |
| 내 상태 | `matchSettings.isMatching`이 false거나 문서가 없으면 `MATCHING_OFF` |
| 기준 공강 | 오늘부터 8일 안에서 **지금 겹치는 공강 우선, 없으면 가장 가까운 미래 공강 하나**. 진행 중인 공강은 지금 시각부터 남은 시간만 쓴다. 남은 길이가 최소 겹침보다 짧으면 건너뛴다. 없으면 `NO_FREE_SLOT` |
| 후보 | `isMatching == true`인 사용자 최대 200명. 상대도 ON, **검색자의 `minOverlapMinutes`** 이상 겹침(README 계약), 목적 AND(빈 목록 = 전체), 양방향 차단 제외 |
| 정렬 | 겹침이 긴 순, 같으면 이른 시작 순. AI 점수 정렬은 BT-028 |
| 실패 | 그 외 예외는 `INTERNAL`(`retryable: true`, `requestId`). 내부 예외·이메일 원문은 로그·응답에 남기지 않는다 |

응답:

```text
{ status: "MATCHING_OFF" | "NO_FREE_SLOT", candidates: [] }
{ status: "OK", reference: {meetingDate, dayOfWeek, startMinute, endMinute},
  candidates: [{candidateId, purpose, meetingDate, startMinute, endMinute, overlapMinutes,
                score?, reasons?, suggestedActivity?}] }   // AI 필드는 BT-027, 상위 5명·성공 시에만
```

`candidateId`는 상대 UID다. 이름·사진·태그는 응답에 넣지 않고 앱이 `publicProfiles/{candidateId}`에서 읽는다(원시 시간표·이메일 비노출).

## 공강 읽기 (`availability/{uid}`, #88 모양)

`parseSlots(availability, timetable)`:
- `availability.sourceRevision != timetables.revision`이거나 시간표가 없으면 빈 목록(오래된 공강으로 매칭하지 않음).
- 30분 경계가 아닌 슬롯은 버리고, 같은 요일에 붙거나 겹친 슬롯은 합친 뒤 60분 미만은 버린다(#88 Rules는 원소가 map인지만 본다).
- 검색 단계는 수업(`courses`)과 대조하지 않는다. 그래서 수업과 맞지 않는 공강의 후보가 카드에 보일 수 있지만 요청 생성 시 D의 `SearchCandidateResolver`가 원본·수업·revision으로 거절한다(`INVALID_CANDIDATE`).

## 매칭 설정 `matchSettings/{uid}`

| 필드 | 값 |
|---|---|
| `isMatching` | bool |
| `minOverlapMinutes` | 60·90·120·150·180 (그 밖의 값은 서버가 60으로 읽음) |
| `purposes` | 목적 문자열 목록, 최대 5개. 빈 목록 = 전체 |
| `preferredTags` | `#` 없이 저장, 중복 제거, 최대 20개 |
| `updatedAt` | 서버 시간(`request.time`) |

Rules: 본인만 읽기·생성·수정, 위 5개 키만 허용, 삭제 불가. 다른 사용자는 읽지 않고 검색 서버(Admin SDK)만 읽는다.
앱은 검색할 때마다 현재 스위치·필터로 이 문서를 저장한 뒤 `searchMatches`를 호출한다(shortcut: 쓰기 1회 추가, 설정 화면이 생기면 그쪽 저장으로 옮김).

## 요청 생성 연결 (D · BT-019)

`resolveCandidate(store, fromUid, candidateId, now)`는 검색과 같은 판정을 후보 1명에 대해 다시 한다. D가 `new FirestoreMatchStore(db, ref => tx.get(ref))`를 넘겨 요청 트랜잭션 안에서 재사용한다. null이면 적격 아님.
