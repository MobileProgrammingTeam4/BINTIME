## 1. 팀 결정 (2026-11-25, B)

| 항목 | 결정 |
|---|---|
| 차단 쓰기 경로 | 서버 Callable `blockUser` / `unblockUser`만. 앱은 본인 차단 목록 읽기만 |
| 검색·요청 | 양방향 차단 쌍은 검색 후보·요청 생성·수락에서 제외(기존 A·D 코드가 `users/{a}/blockedUsers/{b}`를 이미 확인) |

| 기존 채팅 | **기록은 그대로 두고 새 메시지만 막는다.** 양쪽 모두 입력창 비활성. 차단 해제하면 다시 보낼 수 있다 |
| 확정 매칭 | 바꾸지 않는다(ACTIVE면 그대로, 채팅 옵션으로 직접 종료) |
| 차단 진입점 | Figma에 별도 차단 버튼이 없어 **신고 화면의 '함께 차단'(BT-051)**에서 연결한다. 이 PR은 서버·목록·해제·채팅 표시까지 |
| 해제 확인창 | Figma 117:1906에 없어 '해제'를 누르면 바로 해제 |

## 2. 데이터

| 경로 | 내용 | 권한 |
|---|---|---|
| `users/{uid}/blockedUsers/{blockedUid}` | `{ blockedUid, createdAt }` (서버 시각) | 본인 읽기만. 쓰기는 서버 전용. 상대·제3자는 읽기 거부(차단 사실 비공개) |
| `chatRooms/{roomId}/blocks/{blockerUid}` | `true` | 서버 전용(앱 읽기·쓰기 없음). 하나라도 있으면 `database.rules.json`이 새 메시지를 거부 |
| `userChatRooms/{uid}/{roomId}/blockedByMe` | 내가 상대를 차단했으면 `true` | 서버 전용. 앱 표시용 |
| `userChatRooms/{uid}/{roomId}/sendDisabled` | 상대가 나를 차단했으면 `true`. 본인이 읽는 목록이라 이름에 사유를 넣지 않는다(#129 리뷰 E) | 서버 전용. 앱 표시용("지금은 메시지를 보낼 수 없어요") |
| `matchRequests` | 차단 정리 시 일반 취소·거절·만료와 같은 `status`·`terminalReason`·`updatedAt` | 기존과 같이 서버 전용 |

- 차단 표시는 BT-034·038·043이 관리하는 `control`과 **다른 노드**다. 방 연결·종료·나가기 작업이 control을 덮어써도 차단은 풀리지 않고, 차단·해제가 방 상태를 바꾸지도 않는다.
- 대상 방: `chatRoomLinks`에서 `pairId == chatPairKey([a, b])`인 모든 방과 `chatPairs/{pairId}.roomId`. 이미 지워진 목록 항목은 새로 만들지 않는다.
- 서로 차단했으면 한 사람이 풀어도 상대의 `blocks/{uid}`가 남아 전송은 계속 막힌다.
- 차단 상한: 1인당 200명.

## 3. API

```
blockUser({ targetUid })   → { targetUid, blocked: true,  closedRequests, rooms }
unblockUser({ targetUid }) → { targetUid, blocked: false, closedRequests: 0, rooms }
```

- 리전 `asia-northeast3`, 토큰 UID와 학교 이메일 확인(기존 요청 Callable과 같은 방식). 요청 본문의 UID로 신원을 정하지 않는다.
- 오류: `invalid-argument/SELF_BLOCK`, `not-found/USER_NOT_FOUND`, `resource-exhausted/BLOCK_LIMIT`, 그 밖은 `unavailable`(retryable).
- 멱등: 같은 상대를 다시 차단·해제해도 성공한다. Firestore 커밋 뒤 RTDB 반영이 실패하면 오류를 돌려주고, 다시 호출하면 RTDB 반영을 이어서 한다.
- 대기 요청 정리는 `requestUserGuards/{uid}.revision`을 올려 BT-031 생성·수락과 같은 문서에서 경합한다. 생성(후보 재검증)·수락도 같은 트랜잭션에서 `blockedUsers`를 읽으므로 차단이 먼저 커밋되면 다시 실행되어 거부된다. `cooldownUntil`은 건드리지 않는다.

## 6. 남은 한계·후속

1. **운영 반영 전**: Rules(firestore·database)와 Callable 2개는 B/SM 확인 후 배포한다. 배포 전 실제 Firebase 앱에서는 목록 읽기가 권한 거부로 오류 화면이 된다.
2. **연결 중인 새 방**: 수락 직후 방 연결(`ChatLinkService`)이 끝나기 전에 차단하면, 그 뒤에 새로 만들어진 방에는 차단 표시가 없다. 차단 후 수락·요청은 서버가 막으므로 차단 이전에 수락된 매칭 하나에서만 생길 수 있다. 다시 차단을 호출하면 반영된다. **E가 #121 병합 뒤 BT-034 후속으로** 방 연결 완료 시점에 두 사람의 `blockedUsers`를 양방향으로 읽어 새 방에도 `blocks`·목록 표시를 쓰기로 했다(#129 리뷰).
3. **차단 진입점**: BT-051 신고 화면의 '함께 차단'에서 `BlockRepository.block`을 호출한다.
4. **탈퇴**: BT-045 탈퇴 처리에서 본인 `blockedUsers`와 남은 방의 차단 표시를 정리한다.
5. **Firestore만 반영되고 RTDB 반영이 실패한 경우(#129 리뷰 E)**: 차단 기록·대기 요청 정리는 끝났지만 채팅 `blocks`가 없어 메시지는 계속 보낼 수 있는 상태가 된다(해제는 반대로 목록에서는 빠졌지만 채팅은 계속 막힌 상태). Callable은 `unavailable`(retryable)을 돌려주고, 같은 요청을 다시 보내면 문서가 이미 있어도 RTDB를 다시 반영한다(멱등). 앱 안내:
   - 해제: "잠시 후 다시 시도해 주세요." 토스트가 뜨고 그 줄의 '해제' 버튼이 다시 켜져 한 번 더 누르면 된다.
   - 차단(신고의 '함께 차단', #131): 신고는 접수되고 "차단은 하지 못했어요. 다시 신고하면 차단을 다시 시도해요."가 뜬다. 같은 매칭을 다시 신고하면 '이미 신고' 안내와 함께 차단을 다시 시도한다.
6. 실제 두 계정 확인(차단 → 검색 제외·채팅 입력 막힘 → 해제 → 다시 검색)은 배포 뒤 진행한다.
