# BT-016 (Issue #16)

## 목적

수업 사이 공강 목록을 산출하고, 30분 칸 선택을 공강 구간으로 바꾸고, 두 공강의 교집합을 분 단위로 계산하고, 최소 겹침(60·90·120·150·180분)을 판정하는 **순수 계산 로직**을 추가한다. ③ Firestore 저장은 BT-015 PR에서 연결했다(아래 "③ availability 저장").

- 코드: `app/src/main/java/com/team4/bintime/data/availability/` (`SlotGrid`, `FreeTimeCalculator`)
- 테스트: `app/src/test/java/com/team4/bintime/data/availability/`
- 계산 로직 PR에서는 `util/TimeUtils`, `data/model/*`, `timetable/` 은 수정하지 않았다. ③ 저장 코드(`FreeCells`, `Availability`)는 같은 패키지에 추가했다.

## 09:00 기준 행 vs 자정 기준 칸

| 구분 | 기준 | 범위 | 사용처 |
|---|---|---|---|
| 자정 기준 칸 (**팀 결정**) | `칸 = minute / 30` | 0 ~ 47 (하루 48칸) | `SlotGrid`, `timetable/TimetableDraft` (`getStartSlotIndex(0)`, `long` 비트마스크) |
| 09:00 기준 행 (기존) | `행 = (minute - 540) / 30` | 0 ~ 17 (09:00~18:00) | `TimeUtils.minutesToSlotIndex` 등, `TimeSlot.getStartSlotIndex/getEndSlotIndex` |

- 변환식: **`칸 = 행 + 18`** (`BASE_HOUR * 2`). **09:00~18:00 범위에서만 성립**한다.
- 기존 09:00 기준 메서드는 09:00 이전을 0, 18:00 이후를 17로 잘라내므로 범위 밖 정보가 사라진다. 따라서 계약으로 쓰지 않는다.
- 계약(저장·전달·비교)은 언제나 **분 단위**이고, 칸은 공강 선택 UI 단위다. 칸 단위(30분)와 최소 겹침 필터(60분~)는 별개다.
- 변환식은 `SlotGridTest.legacyNineOClockRow_equalsSlotMinus18`에서 확인한다.

## API 요약

### `SlotGrid` (자정 기준 30분 칸)

| 메서드 | 설명 |
|---|---|
| `SLOT_MINUTES=30`, `MINUTES_PER_DAY=1440`, `SLOTS_PER_DAY=48` | 상수 |
| `int slotOf(int minute)` | 0..1439 → 0..47, 범위 밖은 `IllegalArgumentException` |
| `int startSlotOf(int startMinute)` | 시작 칸(내림) |
| `int endSlotOf(int endMinute)` | 종료 칸(올림, exclusive). 1440 → 48 |
| `int slotStartMinute(int slot)` / `slotEndMinute(int slot)` | 칸 → 분 |
| `List<TimeSlot> cellsToSlots(int dayOfWeek, long cellMask)` | 선택 칸(비트 i = 칸 i)을 연속 구간으로 합침. 자정을 넘겨 잇지 않음 |

### `FreeTimeCalculator` (공강·교집합·최소 겹침)

| 메서드 | 설명 |
|---|---|
| `List<TimeSlot> normalize(List<TimeSlot>)` | 유효하지 않은 구간 제거, 같은 요일의 겹침·맞닿음 병합, (요일, 시작) 정렬 |
| `List<TimeSlot> gapsBetweenCourses(List<TimeSlot> courseSlots)` | 수업 사이 공강(분 단위). 첫 수업 전·마지막 수업 후 제외, 수업 0~1개인 요일은 없음 |
| `long selectableCells(List<TimeSlot> courseSlots, int dayOfWeek)` | 수업과 1분도 겹치지 않는 칸만 선택 가능 (예: 10:15 종료 수업 → 10:00 칸 불가, 10:30 칸부터 가능) |
| `List<TimeSlot> intersect(List<TimeSlot>, List<TimeSlot>)` | 같은 요일끼리의 교집합(분 단위) |
| `List<TimeSlot> matchableOverlaps(mine, theirs, int minOverlapMinutes)` | 교집합 중 `>= minOverlapMinutes` |
| `boolean meetsMinOverlap(int overlapMinutes, int minOverlapMinutes)` | `overlap >= min` |
| `List<TimeSlot> matchableFreeSlots(List<TimeSlot> freeSlots)` | 병합 후 60분 이상인 매칭 대상 공강 |

공통 규칙:

- 구간은 반열린 `[start, end)`. 끝=시작으로 맞닿으면 겹침 0분이다.
- `minOverlapMinutes`는 `TimeUtils.isValidMinOverlap` 기준 {60, 90, 120, 150, 180}만 허용하며, 그 밖의 값(0, 30 등)은 `IllegalArgumentException`.
- 비교는 **같은 요일(`dayOfWeek`)끼리만** 한다. 실제 날짜(`meetingDate`)와 "지금 겹치는 공강 우선, 없으면 가까운 미래"는 매칭 검색(BT-017, `searchMatches`) 범위다.
- 반환 `TimeSlot`은 항상 새 인스턴스이며 입력 목록을 변경하지 않는다.
- 재사용: `TimeUtils.overlapMinutes`, `isValidMinOverlap`, `DEFAULT_MIN_OVERLAP`, 모델 `TimeSlot`.
- `TimeSlot`이 `Parcelable`이라 `android.os`를 참조하지만, 새 클래스 자체는 `android.*`를 import하지 않으며 JVM 단위 테스트로 검증한다.

## ③ availability 저장

팀 결정(A, #16 ③)에 따른 구조:

```text
availability/{uid}
  slots: list<{dayOfWeek, startMinute, endMinute}>   matchableFreeSlots 결과(붙은 칸 병합 + 60분 이상)
  sourceRevision: int                                 계산 기준 timetables/{uid}.revision
  updatedAt: timestamp                                serverTimestamp
```

- 분 단위, 반열린 구간 `[start, end)`, 요일 1(월)~7(일). `slots`에는 **사용자가 매칭용으로 고른 공강만** 들어간다(수업 사이 공강 자동 계산값이 아님). `uid` 필드는 두지 않는다(문서 ID가 uid).
- **선택 원본**은 `timetables/{uid}.freeCells`에 따로 저장한다: 요일(월~일)별 48칸 비트마스크 정수 7개, 비트 i = 자정 기준 30분 칸 i. 60분 미만 선택도 원본에는 남으므로 화면 재진입 때 그대로 복원된다(`observeTimetable`의 `Timetable.freeSlots`). 원본은 시간표와 같은 본인 전용 문서에 있고, 길이가 고정이라 규칙으로 전부 검증할 수 있으며, A가 정한 `availability` 스키마를 바꾸지 않는다.
- 코드: `data/availability/FreeCells`(마스크 변환·수업 겹침 칸 제거·매칭 대상 계산), `data/availability/Availability`(문서 변환, `MAX_SLOTS = 40`), `data/repository/FreeSlotValidator`(30분 경계·수업 겹침·상한 검증).

| 쓰기 | 언제 | 내용 |
|---|---|---|
| `saveFreeSlots(selected)` | 등록 완료, 주간 탭 칸 선택(마지막 누름 후 0.8초 또는 탭을 벗어날 때) | 30분 경계·수업 겹침·40개 상한 검증 → 한 트랜잭션에서 `freeCells`(revision 그대로) + `availability`(`sourceRevision = revision`) |
| `replaceCourses(courses)` | 등록 완료(수업 전체 교체) | 같은 트랜잭션에서 새 수업과 겹치는 `freeCells` 칸을 지우고 남은 선택으로 `availability` 재계산(`sourceRevision = 새 revision`) |

- 수업 개별 API(`addCourse` 등)는 revision만 올려 `sourceRevision < revision`(stale)이 된다. 이 상태로 "공강 다시 확인 필요"를 판단할 수 있다. 기존 `matchRequests`·`matches`는 별도 문서의 시간 스냅샷이라 영향을 받지 않는다(BT-047 원칙).
- 40개 상한: 30분 칸으로 만들 수 있는 60분 이상 구간은 하루 최대 16개(2칸 선택·1칸 비움 반복), 월~금 80개다. 규칙에 반복문이 없어 원소를 하나씩 풀어 검사해야 하므로 평가식 상한을 고려해 40개로 정했다(팀 결정). 클라이언트는 40개를 넘으면 저장 전에 안내하고 거부한다.
- **한계(BT-036에서 현재 동작으로 고정)**: `replaceCourses`는 새 수업과 겹친 칸을 지운 **뒤** 40개 상한을 검사한다(Mock·Firestore 동일). 수업이 긴 공강 블록을 60분 이상 두 블록으로 쪼개면 40개가 41개가 될 수 있고, 이때 **수업 교체 자체가 `TOO_MANY_FREE_SLOTS`로 거부**된다. 쪼개진 한쪽이 60분 미만이면 개수가 늘지 않아 허용된다. 상한 40은 Rules와 `searchMatches`에도 걸린 팀 결정이라 정책 변경은 BT-036 범위가 아니다. 테스트: `MockAsyncTimetableRepositoryTest.replaceCourses_splittingBlockOver40_rejectedAndUnchanged`.
- 수업 개별 API(`addCourse` 등)는 `freeCells`를 정리하지 않으므로 겹친 칸이 원본에 남는다. 이 칸을 그대로 다시 저장하면 거부되며, 주간 탭은 받은 값에서 수업과 겹친 칸을 먼저 지우고 저장한다(`TimetableDraft.discardOccupiedFreeSlots`, 아래 BT-036).

### Rules (`availability/{uid}`)

- 읽기: 본인만. 다른 사용자 읽기 금지(매칭 검색 서버 함수가 Admin SDK로 읽는다).
- 쓰기: 본인만. 키 `slots, sourceRevision, updatedAt`만. `slots`는 list이고 40개 이하이며 **각 원소는 map인지만** 검사한다(`availSlotsAreMaps`). `existsAfter(timetables/{uid})`이고 `sourceRevision == getAfter(timetables/{uid}).data.revision`(같은 트랜잭션에서 쓴 뒤의 부모 revision). `updatedAt == request.time`. 삭제 불가.
- **슬롯 상세 검증은 규칙이 아니라 클라이언트와 서버가 맡는다.** 규칙의 식 평가 한도(요청당 1000식) 때문이다. B의 규칙 에뮬레이터 측정에서, 원소마다 `validSlot` + 30분 경계 + 60분 이상을 검사하던 이전 규칙은 **slots 6개 이상에서 한도를 넘어 저장이 거부**됐다(5개까지 통과).
  - 클라이언트: `FreeSlotValidator`·`FreeCells` — 요일 1~7, `0 <= start < end <= 1440`, 30분 경계, 수업과 겹침 없음, 붙은 칸 병합 후 60분 이상만 저장, 40개 상한.
  - 서버(`searchMatches`, A): `slots`를 읽을 때 다시 정규화한다 — 형식·범위가 틀린 원소 제외, 30분 경계·60분 이상 확인. 규칙을 우회해 쓴 값(예: 범위 밖 분, 60분 미만)은 여기서 걸러져야 한다.
- 규칙의 한계: 수업과 공강의 겹침, 슬롯 값 범위는 규칙으로 검사하지 않는다. 규칙이 보장하는 것은 소유자·키 집합·개수 상한·원소가 map·`sourceRevision` 일치·`updatedAt`뿐이다.
- 수정 후 규칙의 대략적 평가식 수(추정, `docs/BT-015.md`의 계산 방식): 40개 모두 채워도 약 620식, B 측정으로 보정하면 약 670~730식으로 한도 안이다. **수정 후 규칙은 아직 에뮬레이터로 다시 측정하지 않았다** — B에게 0·6·40개 재측정을 요청한다.

## BT-036 경계값·재선택 검증

기준은 이 문서와 [BT-012](./BT-012.md) ①의 시간 규칙이다. 이슈 완료 조건을 받으면 빠진 항목만 보완한다.

| 경계 | 테스트 |
|---|---|
| 59/60/61분, 필터 60·90·120·150·180의 최솟값−1/최솟값/최솟값+1 | `FreeTimeCalculatorTest` (`meetsMinOverlap_boundaryTable`, `meetsMinOverlap_61_andMinPlusOne`, `matchableOverlaps_59_60_61`, `matchableOverlaps_filterBoundaries`, `matchableOverlaps_filterMinPlusOne`) |
| 맞닿음(끝=시작) vs 겹침, 30분 칸 병합 후 교집합, 빈칸은 잇지 않음 | `intersect_touching_none`, `matchableOverlaps_adjacentCellsMergedBeforeIntersect_gapNotBridged` |
| 자정(0분)·마지막 칸(1410~1440)·하루 전체 | `SlotGridTest`, `intersect_dayBoundaries_0And1440`, `selectable_midnightStartCourse_blocksFirstCellOnly`, `FreeCellsTest.fullDay_roundTrip_isOneSlot`, `lastCells_60Matchable_30NotMatchable` |

| 칸 선택→해제→재선택 | `TimetableDraftTest.toggle_*`, `FreeCellsTest.reselect_sameCellsAfterClear_restoresSameMask`, `LatestValueSaveQueueTest.selectDeselectReselectDuringSave_endsWithReselectedValue`, `deselectThenReselectBeforeFlush_sendsOnlyFinalValue` |
| 수업 변경 후 겹친 공강 정리 | `MockAsyncTimetableRepositoryTest.replaceCourses_clearsOverlappingCells_andRefreshesAvailability`, `addCourse_keepsOverlappingCells_resavingThemIsRejected`, `TimetableDraftTest.discard_*` |
| 40개 상한 | `FreeSlotValidatorTest.limit_40ok_41rejected`, `limit_bridgingCellMerges41BlocksTo40_ok`, `replaceCourses_splittingBlockOver40_rejectedAndUnchanged`(위 한계) |

- **수정한 버그**: `TimetableDraft.discardOccupiedFreeSlots`가 토·일 수업을 건너뛰어, 주말 수업과 겹친 주말 공강 칸이 남았다. 주간 탭은 저장할 때 7일을 모두 보내므로 이후 칸 선택 저장이 계속 `INVALID_FREE_SLOT`으로 거부됐고, 주말은 화면에 없어 사용자가 고칠 수 없었다. 주말 수업도 정리하도록 고쳤다(`discard_weekendCourse_clearsWeekendCell_soNextSaveIsValid`).
- **수동 확인 항목**: 주간 탭에서 40개를 넘기는 칸을 누르면 안내 후 되돌리는 동작(`TimetableWeekFragment.onCellToggled`)은 Android Fragment라 JVM 단위 테스트로 검증하지 않는다.

## 범위 밖 후속 작업

- `timetable/TimetableDraft`의 `suggestGaps`·`nextFreeWindow`를 이 계산기로 연결 (시간표 화면 이슈). 공강 선택 저장은 이 계산기(`matchableFreeSlots`, `selectableCells`)로 연결했다.
- `TimeUtils`/`TimeSlot`의 09:00 기준 칸 메서드를 `SlotGrid`에 위임하거나 `@Deprecated` 처리 (BT-012 담당자와 합의 후 별도 PR).
- 날짜 기반 교집합·현재/가까운 미래 선택·양측 매칭 스위치·목적·차단 조건 (BT-017 / A 담당 `searchMatches`).
