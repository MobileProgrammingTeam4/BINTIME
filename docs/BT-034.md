# BT-034 / Issue #34 — 실제 매칭 채팅방 연결 인수인계

담당 E / P0. 실제 이슈 [#34](https://github.com/MobileProgrammingTeam4/BINTIME/issues/34). 선행 BT-022·033. 이 문서는 D의 [BT-033](./BT-033.md) 구현과 연결할 인수인계 문서다. 기존 구조는 [BT-021](./BT-021.md), 요청 정책은 [BT-031](./BT-031.md)·[BT-032](./BT-032.md)를 함께 확인한다.

**2026-11-17 작성. 정책은 사용자 승인, 아래 새 컴포넌트·연결 계약은 구현 중이다. 구현 확인 전 예정 경로를 동작 완료로 해석하지 않는다.**

## D가 제공할 것과 E가 연결할 것

| 구분 | D / BT-033 | E / BT-034 |
|---|---|---|
| 확정 매칭 | 요청 수락과 같은 Firestore 트랜잭션에서 matchId=requestId로 한 건 생성, 불변 스냅샷 보존 | 같은 데이터를 읽는 MatchInfoSource 연결. 시간표/현재 후보로 대체하지 않음 |
| 실제 방 연결 | 매칭과 실제 방의 참조·생성 작업·준비 상태 계약 제공 | RTDB 참여자·사용자별 목록·메시지·Firestore 매칭 데이터 합성 |
| 준비 실패 | 매칭을 유지하며 복구 가능한 연결 요청 제공 | chatReady=false의 준비/실패/재시도 표시. true 확인 후 전송 가능 |
| 약속 선택 UI | 재사용 가능한 선택 창·약속 모델·표시 정책 제공 예정 | 채팅 옵션의 종료와 후기 진입점에서 호출. 선택한 matchId를 후속 API에 전달 |

## 반드시 지킬 채팅 정책

| 상황 | 처리 |
|---|---|
| 같은 상대의 이전 방에 둘 다 남아 있음 | 기존 대화 재사용. 새 매칭의 참조만 연결하고 과거 매칭은 덮어쓰지 않음 |
| 한 명이 이전 방에서 나감 | 새 매칭에는 새 방 생성. 나간 사람에게 과거 메시지를 다시 공개하거나 새 방에 복사하지 않음 |
| 한 명이 나간 이전 방 | 기존 방은 재사용/전송 불가, chatReady=false. 남은 사람만 읽기 가능 |
| 새 방 생성 완료 | 새 매칭의 chatReady=true. 기존 방 false와 구분 |
| 둘 다 나감 | 해당 이전 방 삭제. 다른 새 방·매칭 스냅샷은 삭제하지 않음 |
| 둘 다 남은 ENDED 방 | 계속 대화 가능. ‘이전 대화’ 표시를 붙이지 않음 |
| 한 명이 나간 보관 방 표시 | 전체·매칭종료 탭에 ‘이전 대화’ 배지 / ‘상대가 나간 대화방이에요’ 표시 |
| 보관 방 내부 | ‘상대가 나간 대화방이에요. 이전 메시지만 확인할 수 있어요.’ 안내, 입력창 대신 ‘기록 열람만 가능해요’ |
| 권한 | hidden만 바꾸고 접근을 허용한 채 두지 않음. 나간 사람은 이전 기록 읽기/쓰기 거부, 남은 사람은 읽기만 허용. 현재 RTDB Rules는 멤버 쓰기를 허용하므로 함께 보완해야 함 |

실제 나가기·삭제 실행은 BT-043과 연결한다. 이번 BT-033/034에서 방 선택/권한 계약과 로컬 상태 주입 검증을 준비하더라도 BT-043 실제 E2E 완료로 보고하지 않는다.

## 여러 매칭과 방 식별자

- 현재 ChatRoom·ChatRepository·ChatRoomActivity의 matchId가 실제 메시지 방 키 역할도 한다. 재사용 후에는 두 값이 항상 같지 않으므로 단순히 모든 인자의 이름만 바꾸거나 새 매칭 ID로 새 메시지 경로를 만들지 않는다.
- `matches/{matchId}`는 약속 한 건의 진실 공급원이다. 실제 RTDB 방 키는 별도 연결한다. 구체적인 참조 필드/이벤트 스키마는 구현 결과로 확정하여 이 문서·BT-012·021·033에 함께 기록한다.
- 메시지·안읽음·목록·hidden·보관 상태는 실제 방에 귀속한다. 종료·후기·신고의 약속 선택과 후기 중복 제한은 해당 matchId에 귀속한다.
- 같은 방에 미종료 약속이 하나라도 있으면 방을 나갈 수 없다. 모두 종료된 뒤에만 허용한다. 예정 약속은 선택해 수동 종료할 수 있지만, 요청을 CANCELED로 되돌리지 않고 매칭을 ENDED로 바꾼다(BT-038).
- 방 재사용 직후 과거 매칭의 지연 이벤트가 새 연결을 종료/삭제하거나 chatReady를 false로 덮지 않도록 대상 방/매칭·세대 확인이 필요하다. Firestore와 RTDB를 원자적이라고 가정하지 않는다.

## 약속 선택 창 제공 위치와 사용 계약

현재 예정 경로(작성 후 실제 API/화면 증거로 갱신):

| 경로 | 용도 |
|---|---|
| `app/src/main/java/com/team4/bintime/request/MatchAppointment.java` | 약속의 ID·시간 스냅샷·상태·후기 자격 모델 |
| `app/src/main/java/com/team4/bintime/request/MatchAppointmentPolicy.java` | 현재/예정 대표 약속과 추가 건수·종료/후기 대상 판정 |
| `app/src/main/java/com/team4/bintime/request/MatchSelectionSheet.java` | 기존 바텀시트 스타일 재사용. 종료 대상/후기 대상 단일 선택 |

- 1건이면 해당 확인창/후기 화면으로 바로 이동, 여러 건이면 날짜·시간·목적·상태를 표시해 한 건 선택한다.
- 종료 선택 결과에는 선택한 matchId를 전달한다. 아직 시작하지 않은 예정 약속도 종료할 수 있다. 실제 종료는 BT-038 Callable이 검증하고 서버 응답 후 반영한다.
- 후기 목록은 종료된 약속만 대상이다. **시작 전에 수동 종료한 매칭은 영구적으로 후기 대상 제외**한다. 시간이 나중에 지나도 자격을 새로 만들지 않는다. 본인 미작성은 후기 작성, 작성 완료는 보기로 연결한다.
- E의 BT-044는 선택한 matchId로 매칭당 사용자당 한 건과 본인 작성 후 상대 후기 공개 정책을 서버에서 검증한다. 방 ID를 후기 키로 사용하지 않는다.
- 선택 중 서버 상태가 바뀌면 재검증해 중복 종료/후기를 막는다. 결과는 Fragment Result 등 생명주기를 따르는 방식으로 전달하고 회전 후 선택 대상이 바뀌지 않게 한다.
- Figma에 없던 선택 창은 사용자 요청에 따라 먼저 구현·Pixel 10 화면 증거를 제시한 뒤 사용자의 시각적 수정 의견을 반영한다.
