# BT-034 / Issue #34 — 실제 매칭 채팅방 연결 인수인계

담당 E / P0. [실제 이슈 #34](https://github.com/MobileProgrammingTeam4/BINTIME/issues/34), 선행 BT-022·033. 공통 계약 [BT-012](./BT-012.md), 기존 RTDB [BT-021](./BT-021.md), 대표 약속 [BT-035](./BT-035.md)를 함께 확인한다.

2026-11-17 기준 아래 코드는 로컬 구현·검증했다. 운영 배포·실제 두 계정 E2E와 D/E 리뷰는 남아 있으므로 #33·#34 전체 완료로 판정하지 않는다.

## 2. 식별자와 서버 데이터

| 식별자 / 경로 | 계약 |
|---|---|
| requestId = matchId | 개별 약속. 목적·날짜·시작/종료 스냅샷 원본 |
| matches/{matchId}.chatRoomId | 실제 RTDB 방 키. **재사용 시 matchId와 다름** |
| chatRooms/{chatRoomId} | 실제 메시지·멤버. 최초 매칭 ID를 안정적인 방 키로 유지 |
| userChatRooms/{uid}/{chatRoomId} | 방별 최근 메시지·안읽음·hidden·archived·chatReady. 새 약속 때 초기화 금지 |
| chatRoomLinks/{chatRoomId} | 현재 참여자·archived·chatReady·pairId. 현재 참여자 읽기만 허용 |
| chatPairs/{pairId} | 정렬한 두 UID의 JSON을 SHA-256. roomId·pendingMatchId의 서버 전용 조정 문서 |
| chatLinkJobs/{matchId} | PENDING/PREPARING/FAILED/READY, 영속 plan, workerId/leaseUntil, nextAttemptAt·updatedAt. 앱 접근 금지 |

기존 ChatRepository/ChatRoom/Activity API의 matchId 이름은 호환상 유지하지만 **RTDB 작업 인자는 roomId**다. ChatRoom.matchId로 종료/후기 API를 바로 호출하지 않는다. appointments[].matchId를 선택한다. 과거 매칭 시간·상태는 새 약속으로 덮지 않는다.

matches.chatReady는 해당 매칭의 연결 준비 결과다. 사용 가능 여부는 방 수준 상태도 확인한다. 한 명 이탈 후 보관 방은 chatRoomLinks.chatReady=false와 RTDB control의 chatReady/writable=false, archived=true다. 연결 완료된 과거 매칭 문서를 일괄 재작성하지 않는다. 새 매칭·새 방은 별도로 true가 된다.

## 3. 생성·재사용·실패 복구

이전 대화 상단은 기존 ‘종료된 매칭이에요 / 매칭 후기 보기’를 재사용한다. 상대 나감은 마지막 말풍선 다음 시스템 안내 행으로 표시한다. 후기 자격·서버 검증은 기존 정책을 유지하며 전송은 비활성이다. 간략형은 [Figma TimeMatch Compact](https://www.figma.com/design/jR1gI7EWb2WomXUuQvf67Z/2026?node-id=27-1875)를 기준으로 기존 컴포넌트를 재사용한다. common/ 확장은 A/SM과 함께 검토한다.

1. Firestore에서 참여자를 확인하고 pair 잠금을 잡는다. 다른 pendingMatchId가 있으면 새 연결은 재시도한다.
2. 둘 다 잔류하고 archived가 아니면 재사용. 한 명 이탈이면 새 matchId로 새 방을 준비하며 이전 방은 남은 사람만 읽는 보관 상태. 둘 다 이탈한 이전 방은 삭제한다. 운영 데이터 소급 삭제는 실행하지 않았다.
3. 선택 결과를 job.plan에 먼저 저장한다. 중단 후에도 같은 계획을 사용한다. RTDB 작업을 Firestore 트랜잭션 안에서 실행하지 않는다.
4. 멤버·control·양측 목록을 준비한다. 메시지/안읽음/최근 메시지/중복 처리 이력은 보존한다. 준비 전 control.writable=false로 전송을 막는다.
5. RTDB 준비 후 Firestore의 매칭 chatRoomId/chatReady·방 참조·job READY를 저장하고 pair 잠금을 해제한다. RTDB 성공 후 Firestore 완료 실패도 같은 방으로 복구한다.

Callable/이벤트 최대 실행 60초, 중복 worker 방지 lease 120초. 중단 작업은 lease 이후 재시도한다. 실패 후 명시적 재시도는 10초 간격이다(요청 취소 60초 제한과 별개). 자동 이벤트 재시도는 꺼 두었다. 실패/중단 작업은 참여자의 ensureMatchChat 재시도로 복구하며 자동 복구 완료를 보장하지 않는다. 영구 오류는 job/pair를 운영자가 확인해야 한다.

## 4. BT-043·BT-038과 공유할 잠금 및 권한

- 실제 나가기 API는 아직 없다. FirebaseChatRepository.leaveRoom은 실패를 반환한다. 이탈 상태 주입 테스트를 실제 BT-043 E2E로 보고하지 않는다.
- BT-043은 같은 chatPairs 문서에서 pendingMatchId를 확인해야 한다. 연결 중 나가기/멤버 변경을 하지 않는다. 연결된 ACTIVE 약속이 하나라도 있으면 나가기 금지라는 기존 조건을 여러 약속에 적용한다.
- 나가기가 먼저면 다음 연결은 새 방, 새 연결이 먼저면 미종료 약속 때문에 나가기 거절. hidden만 바꾸고 권한을 남겨 두면 안 된다.
- 첫 이탈 시 멤버 제거·나간 사람 목록 hidden·기존 방 읽기 전용을 복구 가능하게 처리한다. 둘째 이탈 시 해당 방만 삭제하고 다른 새 방·매칭은 유지한다.
- BT-038은 선택한 matchId만 ENDED로 전환한다. **시작 전 수동 종료는 reviewEligible=false를 영구 저장**한다. 이후 시간이 지나도 true로 바꾸지 않는다. 방 목록 status는 다른 ACTIVE 약속까지 집계한다.
- 지연된 과거 ENDED/나가기 이벤트가 새 방을 덮지 않게 대상 roomId·현재 연결·pair 상태를 검증한다.
- Rules: 보관 방 남은 멤버는 과거 읽기만 허용, 나간 멤버는 과거 읽기/쓰기 거부, 새 방은 새 멤버만 허용. 기존 control 없는 시연 방은 호환 유지하므로 BT-043은 이탈 시 control도 반드시 설정한다.

## 5. 약속 선택 창 API와 사용 예

| 파일 | 역할 |
|---|---|
| request/MatchAppointment.java | Serializable 불변 약속. matchId/chatRoomId/meetingDate/startMinute/endMinute/purpose/status/reviewEligible/reviewWritten |
| request/MatchAppointmentPolicy.java | targets(all, END 또는 REVIEW), representative(all, now), additionalCount(all, now) |
| request/MatchSelectionSheet.java | show(fm, resultKey, action, all, now), timeLabel(item) |
| res/layout/sheet_match_selection.xml, item_match_selection.xml | 기존 TimeMatch 간략형을 포함하는 리스트. 날짜·시간·겹침 시간·상태만 표시하고 목적 문구 생략. 공통 닫기 버튼 |

~~~java
// onCreate에서 매번 등록하여 회전 후에도 같은 결과를 받는다.
getSupportFragmentManager().setFragmentResultListener("selectAppointment", this, (key, result) -> {
    String matchId = result.getString(MatchSelectionSheet.MATCH_ID); // "matchId"
    String action = result.getString(MatchSelectionSheet.ACTION);   // "END" 또는 "REVIEW"
    // 최신 목록과 서버 자격을 다시 확인한 뒤 확인창/후기 화면으로 이동한다.
});
boolean available = MatchSelectionSheet.show(getSupportFragmentManager(), "selectAppointment",
        MatchAppointmentPolicy.Action.END, room.appointments, repository.nowMillis());
// 0건=false(빈 상태 안내), 1건=즉시 결과, 여러 건=시트
~~~

END는 예정 약속까지 ACTIVE를 대상으로 한다. REVIEW는 ENDED이면서 서버 reviewEligible=true만 대상이다. null/false를 단말 시계로 자격 부여하지 않는다. reviewWritten은 BT-044 본인 후기 조회 결과로 채운다. 실제 후기는 매칭당 사용자당 한 건·본인 작성 후 상대 후기 공개 정책을 서버에서 검증한다.

ChatRoomActivity에 선택→확인→개별 종료/후기 진입이 연결되어 있다. Firebase endMatch는 BT-038까지 실패, 실제 후기는 미연결 안내를 반환한다. Mock은 선택한 약속만 종료하고 다른 약속·대화를 보존한다. 실제 Firebase 화면에서 Mock 성공으로 대신하지 않는다.

## 6. E 후속 작업과 비용 제한

- PartnerSource.UNAVAILABLE을 B 공개 프로필 소스로 연결한다. 실제 화면에 Mock 프로필을 넣지 않았다.
- FirestoreMatchInfoSource는 비용을 제한하려고 최대 101건을 읽고 100건 초과/잘못된 데이터면 오류를 반환한다. 부분 목록으로 잘못된 ‘외 N건’을 계산하지 않는다. 과거 약속 페이지 조회·명시적 오류/재시도 UI를 확장해야 한다. 약속 생성의 제품 상한을 새로 정한 것은 아니다.
- 기존 fan-out과 새 생성 경로를 함께 배포·검증한다. 안읽음/재접속/여러 방 분리, 이탈 직전 전송·지연 이벤트를 확인한다.
- Rules·인덱스·Callable·트리거는 B/SM 승인과 무료 사용량 검토 후 운영에 적용한다. 앱의 Firebase 구성을 켠 것만으로 서버 기능 배포가 완료되지 않는다.
