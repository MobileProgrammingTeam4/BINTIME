# BT-047 (Issue #47)

## 목적

시간표·공강을 바꿔도 이미 만들어진 매칭 요청(`matchRequests`)과 확정 매칭(`matches`, 채팅방 포함)의 **시간 스냅샷은 바뀌지 않고**, 변경은 **새 검색 데이터(`availability`)에만** 반영됨을 확인하고 문서화한다.

완료 조건과 현재 상태:

| 완료 조건 | 상태 | 근거 |
|---|---|---|
| 변경 후 새 검색 갱신 | 충족 | 화면이 쓰는 `replaceCourses`·`saveFreeSlots`가 `availability`를 같은 트랜잭션에서 새 revision으로 갱신 |
| 보낸·받은 요청 유지 | 충족 | 시간표 저장 경로가 `matchRequests`를 읽거나 쓰지 않음. 요청 목록은 요청 문서의 스냅샷만 표시 |
| 진행 중 채팅과 확정 종료시각 유지 | 충족 | 수락 시 요청 스냅샷을 `matches`로 복사하고 시간표를 다시 읽지 않음. 채팅 상단은 `matches` 값만 표시 |

- 이번 이슈는 **프로덕션 코드를 바꾸지 않는다.** 테스트(`data/`)와 이 문서만 추가했다.
- 개별 수업 API(`addCourse`·`updateCourse`·`deleteCourse`)는 현재 동작을 유지한다(아래 "경로별 공강 재계산 규칙").

## 원칙: 스냅샷은 생성 시 1회 복사

```text
시간표·공강 (timetables, courses, availability)      ← 사용자가 계속 바꿈, 새 검색만 사용
        │  createMatchRequest 때 1회 검증·복사
        ▼
matchRequests/{requestId}  meetingDate, dayOfWeek, startMinute, endMinute, overlapMinutes, purpose
        │  respondToMatchRequest(ACCEPTED) 때 요청 문서에서 1회 복사 (시간표 재조회 없음)
        ▼
matches/{matchId = requestId}  같은 시간 필드 + status ACTIVE
        │  채팅 연결(chat/link.ts)은 시간 필드를 바꾸지 않음
        ▼
채팅 상단 시간·종료 시각 = matches 값
```

- 요청 생성: `functions/src/requests/service.ts:172-176`. 시간표 재검증은 생성할 때 한 번뿐이다(`requests/candidates.ts:24-52, 64-70`).
- 같은 `clientRequestId` 재시도는 시간표를 읽지 않고 저장된 원본을 돌려준다(`service.ts:137`).
- 수락: `service.ts:262-267`에서 요청 문서의 시간 필드를 `matches`로 복사한다.
- 표시: 요청 목록 `request/FirebaseRequestRepository.java:136-144` → `RequestTabsController.java:137,233`. 채팅 상단 `chat/FirestoreMatchInfoSource.java:28-30` → `ChatTimeFormatter.java:25-31`. 둘 다 현재 시간표를 다시 읽지 않는다.

## 경로별 공강 재계산 규칙

| 경로 | `freeCells` (선택 원본) | `availability` (새 검색 데이터) |
|---|---|---|
| `replaceCourses` | 새 수업과 1분이라도 겹치는 칸만 지움(`FreeCells.keepSelectable`). 수업이 사라져 빈 칸은 **자동 선택하지 않음** | 남은 선택으로 다시 계산(붙은 칸 병합 + 60분 이상), `sourceRevision` = 새 revision. 정리 후 매칭 대상이 40개를 넘으면 교체 전체를 `TOO_MANY_FREE_SLOTS`로 거부 |
| `saveFreeSlots` | 새 선택으로 교체(수업과 겹치면 `INVALID_FREE_SLOT`) | 새 선택으로 전부 교체, `sourceRevision` = 현재 revision(변경 없음) |
| `addCourse`·`updateCourse`·`deleteCourse` | **정리하지 않음**(겹친 칸이 원본에 남음) | **갱신하지 않음** → `sourceRevision < revision`(stale). 검색 서버(`matching/eligibility.ts:59`)는 이 사용자의 공강을 빈 목록으로 본다 |

- 개별 수업 API의 동작은 BT-015/016 문서와 BT-036 테스트(`courseChangeWithoutReplace_leavesAvailabilityStale`, `addCourse_keepsOverlappingCells_resavingThemIsRejected`)가 고정한 현재 동작이다. **현재 화면은 `replaceCourses`만 쓰므로**(`TimetableSaveViewModel.java:67`) 사용자 흐름에는 영향이 없다. 개별 API를 화면에 쓰게 되면 같은 정리를 추가해야 한다(BT-047에서 결정: 지금은 변경하지 않음).
- 주간 탭은 저장 전에 `TimetableDraft.discardOccupiedFreeSlots`로 수업과 겹친 칸을 지운다.

## Rules 확인 (변경 없음)

- `firestore.rules`: 앱이 쓸 수 있는 곳은 본인의 `timetables/{uid}`·`courses`·`availability/{uid}`(`sourceRevision` == 같은 쓰기 후 revision, :164-177)·`matchSettings`·`users`·`publicProfiles`뿐이다. `matchRequests`·`matches`·guard·job·`chatRoomLinks`는 `write: if false`(:180-208).
- `database.rules.json`: 앱은 멤버의 새 메시지와 본인 `unreadCount = 0`만 쓴다. `members`·`control`은 서버 전용이다.
- 따라서 시간표 변경 사용자가 다른 사용자의 문서나 요청·매칭 상태를 바꿀 경로는 없다.

## 한계

- 새 수업이 대기 중 요청·확정 매칭 시간과 겹쳐도 **알리지 않는다.** 요청·매칭은 생성 당시 스냅샷대로 유지된다(위 정책 결정 대기).
- 수락(`respondToMatchRequest`)은 시간표를 다시 확인하지 않으므로, 발신자가 그 시간에 수업을 넣은 뒤에도 수락될 수 있다(스냅샷 불변 원칙의 결과).
- **매칭 자동 종료 서버 코드는 아직 없다**(BT-038에서 구현 예정). 현재 `chat/link.ts:139`는 `userChatRooms` 상태만 `ENDED`로 바꾼다. 이번 이슈에서는 종료 시각 **표시**가 스냅샷을 쓰는 것만 확인했다.
- 개별 수업 API를 쓰면 availability가 stale이 되어 검색에서 빠진다(현재 화면 미사용).
- 수업을 지운 뒤 공강을 다시 고르지 않으면 빈 칸이 검색에 쓰이지 않는다(의도된 동작).
- `functions/` 에뮬레이터 테스트는 이번 작업에서 실행하지 않았다.

## AVD 확인 방법

두 계정(A·B), 에뮬레이터 또는 개발 Firebase 프로젝트.

1. A·B 모두 매칭 스위치 ON, 오늘 겹치는 공강을 선택한다. A가 B에게 요청을 보낸다.
2. A가 수업 직접 입력으로 요청 시간대에 수업을 넣고 저장한다.
   - A의 `보낸 요청`, B의 `받은 요청`에 원래 시간이 그대로 보인다.
   - Firestore 콘솔에서 `matchRequests/{id}`의 `meetingDate`·`startMinute`·`endMinute`·`overlapMinutes`·`updatedAt`이 바뀌지 않았다.
   - `availability/A`의 `sourceRevision`이 `timetables/A.revision`과 같고, 새 수업 시간이 slots에서 빠졌다.
   - B가 매칭 찾기를 다시 하면 A의 새 공강 기준으로 결과가 나온다.
3. B가 요청을 수락한다. 채팅 상단에 요청 당시 시간과 종료 시각이 보인다.
4. A가 시간표를 한 번 더 바꾸고 채팅방에 다시 들어가도 상단 시간과 종료 시각이 같다. `matches/{id}`의 시간 필드도 그대로다.
