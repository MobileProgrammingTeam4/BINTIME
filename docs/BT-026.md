# BT-026 / Issue #26 — 시간표 이미지 인식 결과 병합·검수

BT-025에서 올린 이미지를 analyzeTimetable(BT-024 AI 게이트웨이)로 인식하고, 여러 이미지의 결과를 합쳐 사용자가 검수·수정한 수업만 저장한다. 이 문서는 **현재 구현(P3, Mock·계약)**, 병합·판정 규칙, 오류 처리, **실제 연동(P4)에 남은 일**을 나눠 적는다.

> **P4 상태(앱): Firebase 빌드는 실제 analyzeTimetable Callable 을 부른다**(`FirebaseTimetableRecognitionRepository`, 11장). Firebase 설정이 없는 빌드만 Mock 이다. **서버 live 프롬프트(PR #112)가 배포되기 전에는 서버가 `AI_NOT_IMPLEMENTED` 를 돌려주므로 실제 인식 결과는 아직 확인하지 못했다.** (P3까지는 Mock 이었다. Mock 은 서버 `mock` 응답과 같은 데이터로 실제 인식이 아니다.)

## 1. 흐름

1. **업로드(BT-025)** → 업로드가 끝나면 `TimetableUploadController`가 바로 인식을 부른다. 버튼은 "시간표 분석 중…", 진행 막대는 무한 진행.
2. **인식 성공** → 결과를 한 번만 넘겨(`takeRecognition`) 검수 화면을 연다. `RecognitionDrafts.toDraft`가 병합(`RecognitionMerger`)한 뒤 draft 를 만든다.
3. **검수(`TimetableReviewActivity.forRecognition`)** → 수업(시간대)마다 신뢰도·병합·겹침·수정 필요·주말·강의실 없음을 표시한다. 수정·삭제·추가할 때마다 다시 판정한다. **겹침이나 수정 필요가 남아 있거나 수업이 0개면 확인 버튼이 꺼진다.**
4. **확인** → 기존 등록 화면(`TimetableRegistrationActivity`)에서 공강을 고르고 등록 완료 시 `replaceCourses` → `saveFreeSlots`. **검수 전에는 저장소에 쓰지 않는다.**
5. **교체 확인(결정 0-3)** → **저장 전 인터넷 확인(B 리뷰 제안 ②)**: 등록 완료("다음")·확인 창의 교체·[다시 확인]을 누르면 먼저 #101의 `NetworkStatus.isOnline`으로 연결을 본다(`TimetableReplaceCheck.begin`, 연결 확인은 `TimetableReplaceCheck.Network`로 주입). 오프라인이면 서버 읽기·확인 창·저장을 시작하지 않고 프로필 저장과 같은 톤의 "네트워크 연결을 확인해 주세요. 연결된 뒤 다시 저장할 수 있어요"만 안내하고 화면에 남는다(시간표 저장은 Firestore 트랜잭션이라 오프라인이면 기다리지 않고 바로 실패한다. 그 전에 연결을 확인해 서버 읽기·확인 창·저장을 아예 시작하지 않고 연결 안내만 보여 준다). 연결된 뒤 다시 누르면 아래 흐름대로 진행한다. 새 시간표(이미지 인식, 직접 입력 새로 시작)는 `TimetableDraft.replacesExisting()`이 true 다. 등록 완료를 누르면 기존 수업 수를 **서버에서만** 읽어(`AsyncTimetableRepository.countCoursesFromServer`, Firestore `Source.SERVER` — 기기 캐시를 쓰지 않음) **수업이 있으면** "기존 수업이 새 시간표로 교체됩니다 — 지금 등록된 수업 N개는 모두 지워지고…" 확인을 띄운다. 서버에 기존 수업이 없을 때만 바로 저장한다. 온라인인데 서버 읽기가 실패하면(시간 초과·권한 거부·로그아웃 등. 오프라인은 위 연결 확인에서 먼저 막는다) **수를 아는 경우와 다른 확인 창**(`ReplaceCheckFailedDialog`: "기존 시간표를 확인하지 못했어요 — 저장된 수업이 있으면 모두 지워지고 새 시간표로 바뀌어요…", [다시 확인]·[취소]·[교체하기])을 띄운다(캐시의 0개를 믿고 확인 없이 지우지 않기 위해, `TimetableReplaceCheck`). [다시 확인]은 서버에서 다시 읽어 성공하면 수를 보여 주는 확인(0개면 바로 저장)으로, 실패하면 같은 창을 다시 띄운다. 읽기 실패는 사용자가 [교체하기]를 누르지 않는 한 저장으로 이어지지 않는다(B 리뷰 제안 ①). AVD 확인 뒤 캐시 첫 값을 쓰던 방식을 바꿨다. 기존 시간표 수정(주간 탭 → 시간표 관리)은 확인하지 않는다.
6. **다시 분석** → 검수에서 뒤로 와서 같은 선택으로 분석하면 업로드·인식을 다시 하지 않고 같은 결과로 검수를 연다(AI 하루 10회 절약). 선택을 바꾸면 결과·실패를 버리고 올린 이미지를 지운다.

## 2. 데이터 계약 (`data/recognition/`)

| 클래스 | 역할 |
|---|---|
| `RecognizedCourse` | 서버 출력 수업 하나: `name`, `dayOfWeek`(1~7), `startMinute`, `endMinute`, `building`/`room`(null 가능), `confidence`(0~1), `sourceImageIndex` |
| `RecognitionResult` | `courses`, `warnings`(서버 안내 문장), `droppedCount`(형식이 틀려 뺀 수), `imageCount` |
| `RecognitionParser` | Callable 응답(Map) 검사. 응답 형식 자체가 틀리면 null → `AI_INVALID_OUTPUT`. 수업 하나가 틀리면 그 수업만 빼고 센다 |
| `RecognitionMerger` | 완전 중복 병합, 같은 이름 시간대 묶기(아래 3장) |
| `RecognitionReview` | 행별 판정(겹침·수정 필요·낮은 신뢰도·병합·주말·강의실 없음), 확인 가능 여부 |
| `RecognitionFailure` | 서버 사유(reason) + retryable + requestId, 앱 전용 `NETWORK` |
| `TimetableRecognitionRepository` | `analyze(imagePaths, Callback)`, Registration. 콜백은 main 스레드 |
| `MockTimetableRecognitionRepository` | 동기 Mock. 서버 `authorize`처럼 경로가 `timetableImages/{uid}/` 아래인지, 1~5개인지 검사 |
| `TimetableRecognitionRepositories` | P3 은 항상 Mock |

파서 범위는 서버 스키마(`functions/src/ai/tasks/analyzeTimetable.ts`)와 같다: 이름 1~60자, 건물·강의실 1~40자 또는 null(키는 반드시 있음), 요일 1~7, `0 ≤ start < end ≤ 1440`, `0 ≤ sourceImageIndex < 이미지 수`, 수업 60개·안내 20개. 정수 필드는 Firebase 가 Integer·Long·Double 로 줄 수 있어 정수 값인지 본다. 문자열은 앞뒤 공백을 지운다.

## 3. 병합 규칙 (`RecognitionMerger`)

- **이름 정규화(비교용)**: 모든 공백 제거 + 소문자. 표시 이름은 앞뒤 공백 제거 + 연속 공백 하나로 줄인 값(신뢰도가 가장 높은 항목의 표기).
- **완전 중복**: 정규화 이름·요일·시작·끝이 같으면 한 시간대. 신뢰도는 큰 값, 건물·강의실은 신뢰도 높은 쪽 값, null 이면 다른 쪽 값으로 채움, 출처 이미지 목록(`sourceImages`)과 합친 수(`mergedCount`)를 남긴다.
- **같은 이름의 다른 시간대**: 한 수업(같은 courseId 행들)으로 묶는다. 수업당 최대 7개(`CourseValidator.MAX_SLOTS_PER_COURSE`), 넘으면 다음 수업으로 나눈다.
- **강의실이 다른 같은 이름**: 저장 모델이 수업당 강의실 하나라서 둘 다 값이 있고 다르면 다른 수업으로 둔다(한쪽이 null 이면 묶는다). 계획에 없던 보완이다(아래 9장).
- **자르지 않는다**: 이름·강의실이 앱 제한(30자)을 넘어도 그대로 두고 검수에서 "수정 필요"로 표시한다.
- 결과 순서: 첫 시간대의 요일·시작 시각.

Mock(2장) 결과: 컴퓨터 구조론(월 10:00~11:30) · 자료구조(수 13:00~14:30, 0·1번 이미지에서 합침) · 확률과 통계(목 09:00~10:30, 신뢰도 52%, 강의실 없음).

## 4. 검수 판정 (`RecognitionReview`)

| 판정 | 조건 | 확인 막음 | 표시 |
|---|---|---|---|
| `CONFLICT` | 같은 요일 `[s,e)` 겹침(다른 수업, 또는 같은 수업의 시간대끼리). **끝과 시작이 맞닿으면 충돌 아님** | 예 | 시간 겹침 |
| `NEEDS_EDIT_NAME_EMPTY` / `_NAME_LENGTH` | 이름 비었음 / 30자 초과 | 예 | 수정 필요 |
| `NEEDS_EDIT_CLASSROOM_LENGTH` | 강의실 30자 초과 | 예 | 수정 필요 |
| `NEEDS_EDIT_TIME` | 요일·시간 범위 밖(충돌 판정에서는 뺌) | 예 | 수정 필요 |
| `NEEDS_EDIT_TOO_MANY_SLOTS` | 같은 수업 시간대 7개 초과 | 예 | 수정 필요 |
| `LOW_CONFIDENCE` | 신뢰도 < 0.7 (인식 행만) | 아니오 | 확인 필요 · 신뢰도 N% |
| `MERGED_DUPLICATE` | 합친 수 > 1 | 아니오 | 여러 이미지에서 합침 |
| `WEEKEND` | 토·일 | 아니오 | 주간 표에는 안 보여요 |
| `NO_CLASSROOM` | 강의실 없음 | 아니오 | 강의실 없음 |

- 수업 0개면 확인할 수 없다(빈 시간표로 기존 수업을 지우지 않도록).
- 사용자가 행을 수정하면 새 행이 되어 신뢰도·병합 표시가 사라진다(검수했다는 뜻). courseId 는 유지된다.
- **주말**: BT-036(PR #99)과 같게 토·일 수업은 저장하지만 주간 시간표(월~금)에는 보이지 않는다. 주말 수업과 겹친 주말 공강 칸은 저장 전에 지운다(`discardOccupiedFreeSlots`). 수정 화면의 요일 선택은 월~금만 있으므로 주말 수업을 고치면 평일로 바뀐다(기존 BT-006 화면 한계).
- 확인 버튼은 판정만 보며, 저장 직전 `CourseValidator.validateAll`(저장소)이 다시 검사한다.

## 5. 오류 처리

서버 사유(docs/BT-024.md "오류")와 같다. `retryable`은 서버 값이 있으면 그것을 따른다(예: `AI_UNAVAILABLE` 이 설정 문제면 false).

| reason | 다시 시도 | 문구(`strings_timetable.xml`) |
|---|---|---|
| `UNAUTHENTICATED` | 아니오 | 로그인이 필요해요 |
| `PERMISSION_DENIED` | 아니오 | 분석할 권한이 없어요. 직접 입력해 주세요 |
| `INVALID_INPUT`, `INTERNAL` | 아니오 | 분석하지 못했어요. 직접 입력해 주세요 |
| `QUOTA_EXCEEDED` | 아니오 | 오늘 AI 사용 횟수를 모두 썼어요. 직접 입력해 주세요 |
| `AI_RATE_LIMITED` | 예 | AI 요청이 많아요. 잠시 후 다시 시도 |
| `AI_TIMEOUT` | 예 | 분석 시간이 초과됐어요 |
| `AI_INVALID_OUTPUT` | 예 | 분석 결과를 읽지 못했어요 |
| `AI_BLOCKED` | 아니오 | 이 이미지는 분석할 수 없어요 |
| `AI_UNAVAILABLE` | 서버 값(기본 예) | 지금은 이미지 분석을 쓸 수 없어요 |
| `AI_NOT_IMPLEMENTED` | 아니오 | 이미지 분석은 아직 준비 중이에요. 직접 입력해 주세요 |
| `NETWORK`(앱 전용) | 예 | 네트워크 연결을 확인한 뒤 다시 시도 |

- **다시 시도**는 이미 올린 이미지로 인식만 다시 한다(재업로드 없음). 다시 시도할 수 없는 실패면 선택을 바꿀 때까지 분석 버튼이 꺼진다.
- **대체 흐름**: 어떤 실패든 업로드 화면에 "직접 입력하기"가 보인다 → 직접 입력(새 시간표, 교체 확인 대상) → 등록. BT-024 원칙 "시간표 인식 실패 → 수동 입력".

## 6. 보안·개인정보

- 앱은 Gemini 를 직접 부르지 않고 API 키를 다루지 않는다. 인식은 analyzeTimetable Callable 만 부른다(P4).
- 로그에 이미지 바이트·URI·파일명·인식된 수업명·건물·Callable 응답 원문·requestId 를 남기지 않는다. 이 단계는 새 로그가 없다. `RecognizedCourse`·`RecognitionResult`·`RecognitionFailure`의 `toString()`도 값·requestId 를 담지 않는다.
- 서버 안내 문장(`warnings`)은 검수 화면에 그대로 보여 준다(모델 출력이므로 로그에는 남기지 않는다).

| 이름 31자 → 빨간 "수정 필요 · 강의명 30자 초과", 확인 버튼 꺼짐, 고치면 다시 켜짐 | 통과(수정 화면에는 글자 수 제한이 없어 31자가 들어간다) |

| 썸네일 모서리 자르기 | 정상 이미지만 확인. 빨간 테두리(오류 이미지) 상태는 P4에서 확인 |

**한계(화면으로 확인하지 못한 것)**
- **겹침 표시는 단위 테스트로만 확인했다.** 수정·추가 화면(`CourseFields.validated`)이 "같은 요일에 시간이 겹치는 수업이 있어요."로 겹치는 저장을 막아, 화면에서 겹침 상태를 만들 수 없다. 검수의 겹침 표시는 인식 결과 자체가 겹칠 때만 나오는데 Mock 데이터에는 겹침이 없다.
- **"직접 입력하기"·인식 실패 문구·다시 시도는 단위 테스트로만 확인했다.** Mock 에 실패를 넣을 방법이 화면에 없다. P4 에서 live 응답(`AI_NOT_IMPLEMENTED` 등)으로 확인한다.
- 기존 수업이 없을 때 확인 없이 저장되는 경로는 실제 계정 데이터를 지우지 않으려고 AVD 에서 확인하지 않았다(단위 테스트로 확인).
- 강의실 없는 인식 수업을 수정할 때 강의실 입력을 요구하던 문제는 2번 안으로 고쳤다(아래 9장).

## 9. 계획과 달라진 점·남은 일

- **강의실이 다른 같은 이름은 나눈다**: "같은 이름 다른 시간대 → 한 수업"을 따르되, 둘 다 강의실이 있고 다르면 저장 모델(수업당 강의실 하나) 때문에 한쪽 강의실이 말없이 사라지므로 다른 수업으로 둔다.
- **인식 후 이미지 삭제(P4 연결)**: 서버는 분석 후 이미지를 지우지 않는다(E 확인). 인식에 성공한 묶음은 검수가 끝나면(저장·뒤로) 앱이 `deleteBatch`로 지운다(11.3). 그 밖에는 지금처럼 선택 변경·화면 종료 시 `deleteImages`로 지운다(BT-025).
- **강의실 없는 인식 수업의 수정(결정: 2번 안)**: 수정하지 않고 확인하면 강의실 없이 저장된다(`validateAll`·Rules·`replaceCourses` 모두 허용). 수정 화면은 **원래 강의실이 없던 수업**(인식 building·room null, 기존 null 수업)을 고칠 때만 강의실을 비워 둘 수 있다(`CourseFormRules.classroomOptional` → `CourseFields.allowEmptyClassroom`). 직접 입력·수업 추가·원래 강의실이 있던 수업의 강의실 비우기는 지금처럼 막는다. 강의실 ""·공백·null 은 같은 값으로 보고(`CourseFormRules.sameAsOriginal`), 바꾼 게 없으면 수정 버튼이 꺼진다. 빈 강의실은 null 로 저장한다(문서에 키 없음). 테스트: `CourseFormRulesTest`.
- **P4 실제 연동**: 구현했다(11장). `FirebaseTimetableRecognitionRepository`(region `asia-northeast3`, `analyzeTimetable` Callable, `FirebaseFunctionsException.getDetails()`의 `reason`·`retryable`·`requestId` → `RecognitionFailure.fromServer`, 네트워크 오류 → `NETWORK`, 응답 → `RecognitionParser`), `TimetableRecognitionRepositories`에서 Firebase 빌드면 실제 구현 선택. 타임아웃은 서버 120초 + 응답 여유로 130초.
- **서버 프롬프트(functions/)**: E 와 합의한 대로 `analyzeTimetable.ts`에 `buildRequest`와 Storage 이미지 검사를 구현했다(10장, PR #112). 운영 배포 전에는 live 환경이 `AI_NOT_IMPLEMENTED` 를 돌려주며, 앱은 위 표대로 "직접 입력하기"로 안내한다.
- Gemini 무료 등급 키 사용 중에는 실제 연동 검증에 테스트용 시간표 이미지만 쓴다(BT-024.md).
- 병합 기준(신뢰도 0.7)은 실제 인식 결과를 보고 P4에서 조정할 수 있다.

## 10. 서버 analyzeTimetable live 구현 (`functions/`, 배포 전)

E 와 합의한 범위: `functions/src/ai/tasks/analyzeTimetable.ts`, `AiDeps.readImage` 하나 추가(`types.ts`·`deps.ts`), 테스트 기본값 한 줄(`test/helpers.ts`). `gateway.ts`·`gemini.ts`·`callable.ts`·`index.ts`·`firebase.json`·`storage.rules` 는 고치지 않았다. **운영 배포와 실제 Gemini 호출은 아직 하지 않았다.**

### 10.1 순서와 검사 (모두 횟수 차감 전, gateway 의 authorize 단계)

| # | 검사 | 실패 reason | 모드 |
|---|---|---|---|
| 0 | 1~5장, 경로 300자 이하(입력 스키마) | INVALID_INPUT | 모두 |
| 1 | 본인 접두사 `timetableImages/{uid}/`, `..` 없음 | PERMISSION_DENIED | 모두 |
| 2 | 형식 `timetableImages/{uid}/{batchId}/{0~4}.jpg`(batchId `^[A-Za-z0-9-]{1,64}$`, storage.rules 와 같음), 한 묶음, 중복 경로 없음 | INVALID_INPUT(`fields` 에 위치) | 모두 |
| 3 | 파일 있음(없으면 404) | INVALID_INPUT | live |
| 4 | 메타데이터 contentType `image/jpeg`, 내용 앞 3바이트 `FF D8 FF` | INVALID_INPUT | live |
| 5 | 한 장 5MiB 미만(메타데이터 크기가 넘으면 내려받지 않음, 내려받은 길이로 다시 확인) | INVALID_INPUT | live |
| 6 | 전체 원본 14MiB 이하(base64 약 4/3배 + 프롬프트가 Gemini 인라인 요청 20MB 안) | INVALID_INPUT | live |

- mock 모드(에뮬레이터·앱 개발)는 Storage 를 읽지 않는다. 로컬 에뮬레이터 실행 스크립트(`serve`)에는 Storage 가 없다.
- **에뮬레이터 운영 버킷 차단(PR #112 리뷰 A)**: `deps.ts` 의 `readStorageImage`(실제 `readImage`)는 `FUNCTIONS_EMULATOR=true` 인데 `FIREBASE_STORAGE_EMULATOR_HOST` 가 없으면 파일을 열기 전에 `AI_UNAVAILABLE`(retryable=false)로 거부한다. 에뮬레이터에서 `AI_MODE=live` 로 돌리면 Admin SDK 가 운영 버킷의 실제 사용자 이미지를 읽게 되기 때문이다. authorize 단계라 횟수 차감·Gemini 호출도 없다.
- **크기를 모르면 받지 않는다(리뷰 B)**: 메타데이터에 `size` 가 없으면 0 으로 두지 않고 내려받지 않는다. 결과는 5번 검사와 같은 INVALID_INPUT 이다.
- 이미지는 authorize 에서 `readImage` 로 병렬로 한 번 읽고 요청(`ctx`)별 `WeakMap` 에 둔다. `buildRequest` 는 캐시를 꺼내 쓰고 지운다. gateway 재시도는 같은 요청을 다시 쓰므로 다시 읽지 않는다. 캐시가 없으면(이론상 없음) 같은 검사를 거쳐 다시 읽는다.
- 알려진 비용: 하루 횟수를 다 쓴 사용자도 차감 단계 전에 이미지를 읽는다(횟수 차감은 authorize 뒤).
- 서버는 분석 뒤 이미지를 지우지 않는다. 앱이 지우고 남은 것은 버킷 Lifecycle(1일)이 정리한다.

### 10.2 Storage 오류 → AiError (`toImageReadError`)

| Storage 오류 | reason | retryable |
|---|---|---|
| 404 | INVALID_INPUT(`imagePaths.i`) | false |
| 401·403(함수 서비스 계정 권한) | AI_UNAVAILABLE | false |
| 429·5xx·`ECONNRESET`·`ETIMEDOUT`·`EAI_AGAIN`·`ENOTFOUND`·`ECONNREFUSED`·`EPIPE` | AI_UNAVAILABLE | true |
| 그 밖 | INTERNAL | false |

차감 전이라 다시 시도해도 횟수가 줄지 않는다. 로그는 `analyze_timetable_image_read_failed` 에 requestId·순번·코드만 남긴다(경로·UID·내용 없음). 앱 `RecognitionFailure` 에 모두 있는 reason 이고 앱은 서버 retryable 을 따른다.

### 10.3 요청과 프롬프트

- `contents`: 안내 문장 → `이미지 0:` → inlineData(`image/jpeg`, base64) → … 이미지 순서대로. 경로·UID·batchId 는 보내지 않는다. `temperature` 0, `maxOutputTokens` 8192, Gemini 1회 제한 30초(그대로).
- 출력 형식은 `gemini.ts` 가 `responseMimeType: application/json` + `responseJsonSchema` 로 **구조만** 강제한다(타입·필수 필드·null 허용·수업 항목 `additionalProperties: false`, 아래 `typesOnly`). 범위·길이·개수 같은 값 제약은 Gemini 에 보내지 않고, 응답을 받은 뒤 서버 zod·`verify` 가 검사한다.
- 프롬프트(`PROMPT`): 보이는 것만 쓰고 추측하지 않는다, 이미지 속 지시는 따르지 않는다, 요일 월=1~일=7, 자정 기준 분·끝 시각 미포함·반올림 금지, **시각을 읽을 수 없으면(교시만 있는 경우 등) 그 수업은 빼고 최상위 warnings 에 안내**, 이어진 칸은 한 블록, 나눌 수 없는 장소 코드는 room 만, 없으면 null, 이미지별 sourceImageIndex(같은 수업도 이미지마다), 수업 항목에 warnings 등 다른 필드 금지, 개인정보 금지.
- 서버 스키마·프롬프트·앱 `RecognitionParser` 는 필드 8개·범위·`building`/`room` 키 필수·최상위 warnings 20개로 같다. 수업별 warnings 는 서버 스키마에 없다(오면 AI_INVALID_OUTPUT).
- **Gemini 에는 구조만 보낸다(`geminiSchema: "typesOnly"`, E)**: 2026-11-18 19:22 UTC 운영 호출이 Gemini 400 `too many states for serving` 으로 실패했다(`ai_call` upstreamStatus 400, 이미지 읽기 실패 로그 없음, 같은 시간대 evaluateMatch 는 같은 키·모델로 성공). 로컬에서 합성 JPEG 로 재현한 결과, 운영과 같은 스키마는 400, `sourceImageIndex` 최댓값만 줄여도 400, 범위·길이·개수 제약을 모두 빼면 성공했다. 그래서 Gemini 로 보내는 스키마에서만 제약을 빼고, 범위·길이·60개·`sourceImageIndex`(이제 `MAX_IMAGES - 1` 까지)는 서버 zod·`verify` 가 그대로 검사한다.

- 실제 학생 시간표 양식의 다양성은 합성 이미지로 확인할 수 없다.

## 11. P4 앱 실제 연동

서버 PR #112(analyzeTimetable live 프롬프트)가 병합·배포되기 전에는 **이 PR 을 병합하지 않는다(Draft)**. 배포 전 서버는 `AI_NOT_IMPLEMENTED` 를 돌려준다.

### 11.1 호출 (`data/recognition/`)

- `FirebaseTimetableRecognitionRepository`: region `asia-northeast3`, `analyzeTimetable`, 입력 `{imagePaths}` 하나(UID 안 보냄), **앱 타임아웃 130초**(서버 함수 120초 + 응답 여유). 보내기 전에 Mock 과 같은 규칙(로그인, 1~5장, 길이, 본인 접두사)을 보고 틀리면 서버를 부르지 않는다(횟수 차감 없음). `cancel()`은 결과만 버리고 콜백 참조를 지운다(서버 호출은 계속된다).
- 응답: 서버는 `{task, data:{courses, warnings}, meta}` 로 감싸 준다. `RecognitionParser.parseCallable`이 `data`를 꺼내 기존 `parse`로 검사한다. **수업이 0개인데 버린 수업이 1개 이상이면 AI_INVALID_OUTPUT(다시 시도 가능)**, 원래 0개면 빈 결과. 수업별 `warnings` 키는 서버 스키마에 없으므로 무시한다(최상위 warnings 만 쓴다).
- 오류(`RecognitionCallableErrors`): details 의 `reason`·`retryable`·`requestId` 를 그대로 따른다(`RecognitionFailure.fromServer`). details 가 없으면 `DEADLINE_EXCEEDED`(앱 130초 초과) → AI_TIMEOUT, `UNAVAILABLE`·네트워크 원인 → NETWORK, `UNAUTHENTICATED` → UNAUTHENTICATED, 그 밖 INTERNAL.
- 팩토리: `TimetableRecognitionRepositories` 가 이미지 저장소와 같은 기준(`AuthRepositories.isFirebaseEnabled`)으로 Firebase/Mock 을 고른다.
- 문구: `INVALID_INPUT`(서버가 이미지 문제로 거부) → "이미지를 확인할 수 없어요. 다른 사진으로 다시 시도해 주세요." 다시 시도 버튼은 서버 retryable 을 따른다.

### 11.2 장수별 압축 상한

서버는 원본 합계 14MiB 를 넘으면 INVALID_INPUT 으로 거부한다. 앱은 한 장 상한을 `min(5MiB, 14MiB ÷ 장수)`(`TimetableImageValidator.uploadLimit`)로 정해 압축기 품질 반복(90→40)에 넘긴다. 품질 40으로도 안 되면 지금처럼 그 이미지에 `COMPRESSED_TOO_LARGE`. 장수는 `TimetableUploadController.analyze()`에서 선택을 고정할 때 확정되고, 압축은 그 뒤 업로더가 백그라운드에서 하므로 압축 시점에 장수가 항상 정해져 있다(업로드·인식 중에는 선택을 바꿀 수 없다). 범위 밖 장수는 가장 엄격한 5장 기준을 쓴다.

| 장수 | 한 장 상한(미만) |
|---|---|
| 1·2 | 5MiB |
| 3 | 약 4.67MiB |
| 4 | 3.5MiB |
| 5 | 2.8MiB |

### 11.3 인식 후 이미지 삭제

- 인식에 **성공**한 묶음은 **검수 화면이 끝나면(저장하든 뒤로 나가든)** `TimetableUploadActivity` 의 검수 결과 콜백 → `TimetableUploadController.onReviewFinished()` → `TimetableImageUploader.deleteUploadedBatch()` → `deleteBatch(batchId, null)`. 실패는 저장소가 코드만 로그로 남기고 사용자에게 보이지 않는다(남은 파일은 버킷 Lifecycle 1일).
- 검수 화면은 이미지를 쓰지 않고, 돌아와 다시 열어도 저장된 인식 결과를 쓰므로 지운 뒤에도 동작이 같다.
- 인식 실패(다시 시도 대기)·인식 중에는 지우지 않는다. 그 이미지는 선택 변경·화면 종료 때 기존 `deleteImages`로 지운다.
- 중복 없음: `deleteBatch` 뒤에는 올린 경로를 잊으므로 이후 화면 종료·선택 변경이 같은 묶음을 다시 지우지 않는다(테스트로 고정).

### 11.7 남은 위험

- **하루 10회 차감**: 서버는 `authorize` 뒤 실제 호출 전에 횟수를 차감한다. `AI_NOT_IMPLEMENTED`·형식 오류·뒤로가기로 버린 호출도 1회로 센다.
- **앱 타임아웃 뒤에도 서버는 계속 돈다**: 130초가 지나 앱이 끝내도 서버 함수는 끝까지 실행될 수 있고 차감된 횟수는 돌아오지 않는다. 다시 시도하면 1회 더 쓴다. 분석 중 뒤로가기도 같다.
- **무료 Gemini 키**: 실제 학생 시간표 이미지는 쓰지 않는다. 합성 이미지(가짜 과목·강의실)로만 확인한다.
- 앱이 지우지 못한 이미지(오프라인 정리 실패, 프로세스 종료, 검수 중 프로세스 종료)는 버킷 Lifecycle(1일)이 정리한다.
