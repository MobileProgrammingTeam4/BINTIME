- 네트워크 오류 뒤 **같은 버튼 리스너에서 재시도할 때만** 같은 draft/UUID를 유지한다. 카드 재바인딩·화면 재생성·상세 재진입 및 완료된 시도 뒤의 새 신청은 새 UUID이며, 서버의 같은 방향 PENDING 잠금은 동일 UUID 재시도의 멱등 보장과 구분한다. 중복 진행 호출도 오류 콜백을 반환한다. 실제 수락/거절은 BT-031 범위다.
- #94 D 후속: 버튼마다 현재 후보 UID·저장소를 포함한 바인딩 객체를 두고, 재바인딩 때 객체를 교체한다. 이전 응답은 과거 후보의 안내·클릭 리스너를 적용하지 않고 **현재 바인딩의 저장소 상태만** 다시 표시한다. 같은 후보 재바인딩 중 신청이 끝나도 버튼이 신청 중으로 남지 않는다. 종료된 Activity나 분리된 View는 갱신하지 않는다.
- 생성 API의 성공 콜백은 멱등 재시도 또는 지연 응답 병합으로 이미 처리된 요청을 반환할 수 있다. PENDING만 기존 신청 완료 팝업을 표시하고, ACCEPTED/REJECTED/CANCELED는 각각 수락/거절/취소 안내를 표시한다. 콜백이 요청 상태를 바꾸거나 스냅샷을 다시 계산하지 않는다. 취소·거절 뒤 사용자가 새로 신청하면 새 UUID를 사용한다.

## Callable API

리전 `asia-northeast3`. `createMatchRequest({ candidateId, clientRequestId })`.
인증 UID는 Callable 토큰에서만 읽는다. 요청 본문에 UID/목적/날짜/시간을 추가하면 입력 오류다.

`candidateId`는 A가 확정한 상대 UID(별도 토큰 없음)이며 길이 1~200의 `A-Z a-z 0-9 : _ -` 형식, `clientRequestId`는 UUID다.
응답은 요청 문서 ID `id`, 참여자·목적·시간 스냅샷·상태, `createdAtMillis`/`updatedAtMillis`다.
오류는 `HttpsError`와 `details.{reason,retryable,requestId}`로 반환하고 내부 예외나 개인정보를 노출하지 않는다.

### BT-017 연결과 요청 경계

`CandidateResolver.resolve(transaction, fromUid, candidateId, now)`는 **서버 내부 전용**이다.
`SearchCandidateResolver`가 A의 `resolveCandidate(new FirestoreMatchStore(db, ref => tx.get(ref)), fromUid, candidateId, now)`를 호출한다. slots 조회만 검증 래퍼로 감싸 `timetables.freeCells`·courses·sourceRevision으로 다시 확인하고, 후보가 null이면 거절한다.
동일 트랜잭션에서 양측 ON·검색자가 선택한 최소 겹침·목적·양방향 차단·신청자 프로필 완료·수신자 공개 프로필 존재·ACTIVE 매칭 충돌을 재검사한다. A가 최초 전달한 양측 최댓값은 최신 정정에 따라 적용하지 않는다. 부모 revision과 공강 sourceRevision이 다르거나 선택 원본/수업과 맞지 않는 슬롯이면 거부한다. #89 검색은 revision·슬롯 경계를 검사하지만 수업과의 대조는 아직 없으므로 D의 요청 직전 원본 검증은 유지한다.
반환 값은 `{toUid,purpose,meetingDate,startMinute,endMinute}`이며 검사가 끝난 실제 교집합이어야 한다. 날짜는 KST `YYYY-MM-DD`, 분은 자정 기준 정수, 반열린 구간이다.
서비스도 자기 자신·잘못된 날짜/시간·60분 미만·이미 종료된 공강을 다시 거절한다.

기본 Callable은 실제 `SearchCandidateResolver`를 사용한다. `checkSchoolEmail`(#87)을 재사용해 검증된 학교 이메일과 `ALLOWED_EMAIL_SUFFIXES`를 검사하며 설정이 비면 거절한다. 테스트 전용 후보를 배포 기본값으로 쓰지 않는다.
`INVALID_CANDIDATE`는 재검색, `MATCH_CONFLICT`는 확정 매칭 충돌 안내다. 멱등 재시도는 기존 요청을 먼저 반환하므로 이후 공강·프로필 변경으로 과거 스냅샷을 재작성하지 않는다.

## Firestore 계약

`matchRequests/{sha256([authUid,clientRequestId])}`:

| 필드 | 내용 |
|---|---|
| `fromUid`, `toUid` | 토큰 사용자, 서버가 해석한 후보 |
| `candidateId` | 서버 후보 식별자, 멱등 키 재사용 충돌 검사 |
| `purpose` | 생성 당시 목적 |
| `meetingDate`, `dayOfWeek` | 날짜, 월=1~일=7 |
| `startMinute`, `endMinute`, `overlapMinutes` | 변경하지 않는 시간 스냅샷, 마지막 값은 종료-시작 |
| `status` | 최초 `PENDING` |
| `createdAt`, `updatedAt` | 서버 Timestamp |

`matchRequestGuards/{sha256([fromUid,toUid])}`는 서버 전용 중복 잠금이다.
필드는 `fromUid`, `toUid`, `pendingRequestId`. 같은 방향의 한 쌍에는 PENDING 한 건만 허용한다.
잠금 문서와 요청을 한 트랜잭션으로 생성한다. 다른 UUID를 사용한 동시 클릭도 중복을 막는다.
동일 UUID 재시도는 기존 요청을 반환한다. 시간표/후보가 나중에 바뀌어도 기존 스냅샷을 다시 계산하지 않는다.
취소된 뒤 새 UUID로 재신청할 수 있으며 기존 요청 문서는 남긴다.

`firestore.rules`는 요청 참여자의 읽기만 허용하고 클라이언트 생성·수정·삭제 및 잠금 접근을 거절한다.
선행 PR의 users/publicProfiles·timetables/courses/availability·matchSettings 규칙과 요청 규칙을 모두 보존했다. `aiUsage`·matches 등 별도 허용이 없는 경로는 앱 접근 기본 거부를 유지한다. 실제 배포 전 B/A/SM이 전체 Rules를 통합 검토해야 한다.
확정 매칭 충돌 조회에는 `matches(participantUids ARRAY_CONTAINS, meetingDate ASC)` 인덱스가 필요하다(`firestore.indexes.json`). 운영 인덱스 생성 완료는 Emulator로 검증할 수 없으며 B의 승인된 배포 후 확인한다. #85의 발신·수신 목록 인덱스 2개도 함께 보존한다.
