# BT-025 / Issue #25 — 시간표 이미지 다중 선택·업로드·오류 처리

시간표 이미지 여러 장을 고르고, 검사·압축한 뒤 Cloud Storage에 올려 BT-026 인식(analyzeTimetable)에 넘기기까지를 다룬다. 이 문서는 **현재 구현(P1, Mock)**, **합의할 계약**, **실제 연동(P2)에 필요한 B 요청**을 나눠 적는다.

> **P1 상태: 업로드 저장소는 Mock이다.** Firebase 빌드에서도 실제 Storage에 올리지 않는다(`TimetableImageRepositories`). Mock 업로드 성공은 실제 업로드 성공이 아니다. 인식은 아직 BT-006 고정 예시(`TimetableDraft.mockRecognition()`)다. 이슈 완료는 B의 Storage Rules 게시 후 P2 실제 연동 검증으로 판정한다.

## 1. 흐름

1. **선택**: 포토 피커 다중 선택(최대 5장), 다시 선택, 개별 삭제, 중복 URI 제거. 5장보다 많이 고르면 앞의 5장만 담고 안내한다.
2. **선택 시 검사(백그라운드, 디코딩 없음)**: 고르자마자 이미지마다 형식 → 원본 크기 → 헤더 해상도를 검사해 문제 있는 이미지에 오류 표시를 한다. 검사 중이거나 오류 이미지가 하나라도 있으면 분석 버튼이 꺼진다. 오류 이미지를 빼면 다시 켜진다.
3. **분석 시작은 한 경로**: 버튼 → `TimetableUploadViewModel.analyze()` → `TimetableUploadController.analyze()`. "분석 가능"(업로드 중 아님 + 1~5장 + 모든 이미지 검사 완료 + 오류 이미지 없음)이 아니면 무시하고 압축기·업로더로 아무것도 넘기지 않는다. 버튼 활성 상태도 같은 판정(`TimetableUploadScreen.canAnalyze`)만 쓴다.
4. **준비(백그라운드)**: 선택 시 검사를 다시 통과해야만 디코딩·압축한다. **모든 이미지를 먼저 준비해 문제 있는 이미지를 한 번에 표시**하고, 하나라도 문제면 업로드하지 않는다. 여기서 찾은 오류(예: 5MB 미만으로 안 줄어듦)도 그 이미지에 남는다.
5. **업로드**: 묶음(batch) 하나로 순서대로 올린다. 전체 바이트 기준 진행률을 버튼과 진행 막대에 보여 준다.
6. **인식으로 이동**: 업로드가 끝나면 검수 화면으로 넘어간다. 검수 화면에서 뒤로 와서 다시 분석하면 같은 선택은 다시 올리지 않는다.
7. **정리**: 선택을 바꾸거나 이미지를 빼거나 화면을 떠나면(ViewModel 종료) 진행 중인 업로드를 취소하고 올린 이미지를 지운다(최선 시도).

회전해도 선택·검사 결과·진행 상태는 `TimetableUploadViewModel`에 남는다(프로세스 종료 뒤에는 저장한 선택을 다시 검사). 업로드 중에는 다시 선택·삭제·분석 버튼이 막힌다(중복 클릭 방지).

## 2. 검사·압축 규칙

| 항목 | 규칙 | 실패 코드 / 안내 |
|---|---|---|
| 개수 | 1~5장 (서버 `MAX_IMAGES`=5) | `INVALID_COUNT` |
| 형식 | `image/jpeg`·`png`·`webp`·`heic`·`heif`. MIME을 모르면 디코딩 결과로 판단 | `UNSUPPORTED_TYPE` "JPG·PNG·WEBP·HEIC 이미지만…" |
| 원본 크기 | 20MB 이하 (디코딩 메모리 보호). 메타데이터 SIZE → 파일 설명자 길이 → 직접 세기(상한+1바이트까지) 순서로 구해, **크기를 모른 채 디코딩하지 않는다** | `SOURCE_TOO_LARGE` |
| 디코딩 | 열 수 없거나 손상, 크기 0 | `CORRUPT` "손상되었거나 열 수 없는 이미지예요." |
| 해상도 | 긴 변 320px 이상(선택 시 헤더만 읽어 확인) | `TOO_SMALL` |
| 읽기 | 권한 해제·삭제된 파일 | `READ_FAILED` |
| 압축 | 긴 변 2048px로 축소, EXIF 방향을 픽셀에 반영한 뒤 JPEG로 다시 인코딩(위치 등 EXIF 메타데이터 제거). 품질 90→80→70→60→50→40으로 낮추며 **5MB 미만**이 되는 첫 결과 사용 | 모두 넘으면 `COMPRESSED_TOO_LARGE` "용량을 줄여도 5MB를 넘어요…" |

업로드 단계 실패: `NOT_SIGNED_IN`, `PERMISSION_DENIED`(재시도 버튼 없음), `NETWORK`·`UNKNOWN`(같은 선택으로 "다시 시도"). 네트워크·권한 실패는 특정 이미지 탓으로 표시하지 않는다.

업로드 화면 안내에 **"이름·학번이 보이지 않게 가려 주세요"**를 표시한다(`strings_timetable.xml`).

## 3. Storage 경로 계약 (제안, B·E와 확정 필요)

```text
timetableImages/{uid}/{batchId}/{index}.jpg
  uid     : Auth UID (앱은 AuthRepositories.get(context).getCurrentUid())
  batchId : 앱이 만든 UUID, [A-Za-z0-9-]{1,64}
  index   : 0..4, 선택 순서 = analyzeTimetable imagePaths 순서 = 인식 결과 sourceImageIndex
  contentType: image/jpeg, size < 5MB
```

- 코드상 단일 출처: `data/repository/TimetableImagePaths` (경로·5장·5MB·content type).
- 서버 `functions/src/ai/tasks/analyzeTimetable.ts`의 `timetableImagePrefix(uid)` = `timetableImages/{uid}/`, `MAX_IMAGES = 5`, 경로 300자 이하와 맞다. 서버 `authorize`는 접두사·`..`만 보므로 이 경로 형식을 그대로 받는다(서버 변경 불필요).

## 4. B 요청 — Storage Rules·설정 (B 영역, 이 PR은 수정하지 않음)

### 4.1 `storage.rules`에 추가할 규칙 (제안)

```text
// BT-025: 시간표 이미지. 본인만 읽기·생성·삭제, 덮어쓰기(update) 없음.
match /timetableImages/{uid}/{batchId}/{file} {
  allow read: if request.auth != null && request.auth.uid == uid;
  allow create: if request.auth != null
      && request.auth.uid == uid
      && batchId.matches('^[A-Za-z0-9-]{1,64}$')
      && file.matches('^[0-4][.]jpg$')
      && request.resource.size < 5 * 1024 * 1024
      && request.resource.contentType == 'image/jpeg';
  allow delete: if request.auth != null && request.auth.uid == uid;
}
```

- 다른 계정은 읽기·쓰기·삭제 모두 거부해야 한다(이슈 완료 조건 "다른 계정 파일 접근 차단").
- 서버 analyzeTimetable은 Admin SDK로 읽으므로 Rules와 무관하다. 대신 서버 `authorize`가 경로 소유를 확인한다(구현돼 있음).
- 학교 이메일 인증 여부(`request.auth.token.email_verified`)를 함께 볼지는 B가 프로필 사진 규칙과 맞춰 결정한다.

### 4.2 그 밖의 요청

| 요청 | 대상 | 이유 |
|---|---|---|
| `firebase.json` emulators에 `storage`(예: 9199) 추가 | B(공용 파일) | Rules를 에뮬레이터에서 계정 2개로 확인하기 위해. 없으면 게시된 Rules로 AVD에서만 확인 가능 |
| 버킷 Lifecycle: `timetableImages/` 접두사 1일 후 삭제 | 관리자 | 앱이 지우지 못한 이미지(프로세스 종료, 네트워크 끊김) 정리용 안전장치 |
| Rules 게시 일정 공유 | B | 게시 후 P2(실제 업로드)를 연결하고 AVD에서 검증 |
| `ProfilePhotoCompressor` 공용화 여부 | B | 이번 PR은 수정하지 않고 `timetable/TimetableImageCompressor`를 따로 만들었다(해상도 2048px·5MB 품질 루프가 달라서). 공용화하면 합친다 |

## 5. E 확인 사항 (BT-026 연결 전)

- `analyzeTimetable` 입력 경로 형식을 3장 계약으로 확정(BT-024.md의 "제안" 표시 해제).
- live 프롬프트 작업 주체: C가 `analyzeTimetable.ts`만 수정하는 안(a)으로 E 동의 대기 중. 동의 전에는 `functions/`를 수정하지 않는다.
- 분석 후 서버가 이미지를 지울지 여부. 지우지 않으면 앱 삭제 + Lifecycle에 맡긴다.

## 6. 보안·개인정보

- 업로드 JPEG는 다시 인코딩해 EXIF(위치 등)를 남기지 않는다. 화면 안내로 이름·학번 가림을 요청한다.
- 로그에 **이미지 바이트, content URI, 파일명, Storage 경로, 인식 결과를 남기지 않는다.** 이 PR은 새 로그를 추가하지 않았다. 실패 객체의 `detail`도 URI·파일명을 담지 않는다.
- 앱은 Gemini를 직접 부르지 않으며 API 키를 다루지 않는다. 인식은 `analyzeTimetable` Callable만 호출한다(BT-026).
- Gemini 무료 등급 키 사용 중에는 실제 연동 검증에 **테스트용 시간표 이미지만** 쓴다(BT-024.md).
- 이미지 보관: 인식이 끝나거나 선택을 바꾸거나 화면을 떠나면 앱이 지운다(최선 시도). 남은 것은 Lifecycle(요청)로 정리한다.

## 9. 장수 규칙 (결정)

- **1~5장**으로 확정했다. 서버 analyzeTimetable `imagePaths` 1..5와 같다.
- 이슈 BT-025 완료 조건의 "**2장 이상 업로드**·미리보기 성공"은 최소 장수 규칙이 아니라 **여러 장 업로드를 확인하는 완료 조건**으로 해석한다. P2 실제 업로드 검증에서 2장 이상으로 확인한다.
