# BT-025 / Issue #25 — 시간표 이미지 다중 선택·업로드·오류 처리

시간표 이미지 여러 장을 고르고, 검사·압축한 뒤 Cloud Storage에 올려 BT-026 인식(analyzeTimetable)에 넘기기까지를 다룬다. 이 문서는 **현재 구현(P1, Mock)**, **합의할 계약**, **실제 연동(P2)에 필요한 B 요청**을 나눠 적는다.

> **상태(2026-11-22): P1(#106)·P2(#111)가 develop에 병합됐다.** Firebase 빌드는 실제 Cloud Storage에 올린다(`FirebaseTimetableImageRepository`, #107 Rules 게시 후). Firebase 설정이 없는 빌드만 Mock이다(`TimetableImageRepositories`). Mock 업로드 성공은 실제 업로드 성공이 아니다. 인식도 BT-026 P3(#108)·P4(#113)가 develop에 병합돼 Firebase 빌드는 실제 analyzeTimetable을 부르며, 업로드 → 인식 → 검수 → 저장까지의 전체 흐름을 실제 서버에서 합성 이미지로 확인했다(docs/BT-026.md 11.8.3). 이슈 완료는 B의 Storage Rules 게시 후 P2 실제 연동 검증으로 판정한다. P2 구현·검증은 아래 11장.

## 1. 흐름

1. **선택**: 포토 피커 다중 선택(최대 5장), 다시 선택, 개별 삭제, 중복 URI 제거. 5장보다 많이 고르면 앞의 5장만 담고 안내한다.
2. **선택 시 검사(백그라운드, 디코딩 없음)**: 고르자마자 이미지마다 형식 → 원본 크기 → 헤더 해상도를 검사해 문제 있는 이미지에 오류 표시를 한다. 검사 중이거나 오류 이미지가 하나라도 있으면 분석 버튼이 꺼진다. 오류 이미지를 빼면 다시 켜진다.
3. **분석 시작은 한 경로**: 버튼 → `TimetableUploadViewModel.analyze()` → `TimetableUploadController.analyze()`. "분석 가능"(업로드 중 아님 + 1~5장 + 모든 이미지 검사 완료 + 오류 이미지 없음)이 아니면 무시하고 압축기·업로더로 아무것도 넘기지 않는다. 버튼 활성 상태도 같은 판정(`TimetableUploadScreen.canAnalyze`)만 쓴다.
4. **준비(백그라운드)**: 선택 시 검사를 다시 통과해야만 디코딩·압축한다. **모든 이미지를 먼저 준비해 문제 있는 이미지를 한 번에 표시**하고, 하나라도 문제면 업로드하지 않는다. 여기서 찾은 오류(예: 5MB 미만으로 안 줄어듦)도 그 이미지에 남는다.
5. **업로드**: 묶음(batch) 하나로 순서대로 올린다. 전체 바이트 기준 진행률을 버튼과 진행 막대에 보여 준다.
6. **인식으로 이동**: 업로드가 끝나면 검수 화면으로 넘어간다. 검수 화면에서 뒤로 와서 다시 분석하면 같은 선택은 다시 올리지 않는다.
7. **정리**: 선택을 바꾸거나 이미지를 빼거나 화면을 떠나면(ViewModel 종료) 진행 중인 업로드를 취소하고 올린 이미지를 지운다(최선 시도).

회전해도 선택·검사 결과·진행 상태는 `TimetableUploadViewModel`에 남는다(프로세스 종료 뒤에는 저장한 선택을 다시 검사). 업로드 중에는 다시 선택·삭제·분석 버튼이 막힌다(중복 클릭 방지).

## 2. 검사·압축 규칙

| 항목 | 규칙 | 실패 코드 / 안내 |
|---|---|---|
| 개수 | 1~5장 (서버 `MAX_IMAGES`=5) | `INVALID_COUNT` |
| 형식 | `image/jpeg`·`png`·`webp`·`heic`·`heif`. MIME을 모르면 디코딩 결과로 판단 | `UNSUPPORTED_TYPE` "JPG·PNG·WEBP·HEIC 이미지만…" |
| 원본 크기 | 20MB 이하 (디코딩 메모리 보호). 메타데이터 SIZE → 파일 설명자 길이 → 직접 세기(상한+1바이트까지) 순서로 구해, **크기를 모른 채 디코딩하지 않는다** | `SOURCE_TOO_LARGE` |
| 디코딩 | 열 수 없거나 손상, 크기 0 | `CORRUPT` "손상되었거나 열 수 없는 이미지예요." |
| 해상도 | 긴 변 320px 이상(선택 시 헤더만 읽어 확인) | `TOO_SMALL` |
| 읽기 | 권한 해제·삭제된 파일 | `READ_FAILED` |
| 압축 | 긴 변 2048px로 축소, EXIF 방향을 픽셀에 반영한 뒤 JPEG로 다시 인코딩(위치 등 EXIF 메타데이터 제거). 품질 90→80→70→60→50→40으로 낮추며 **5MB 미만**이 되는 첫 결과 사용 | 모두 넘으면 `COMPRESSED_TOO_LARGE` "용량을 줄여도 5MB를 넘어요…" |

업로드 단계 실패: `NOT_SIGNED_IN`, `PERMISSION_DENIED`(재시도 버튼 없음), `NETWORK`·`UNKNOWN`(같은 선택으로 "다시 시도"). 네트워크·권한 실패는 특정 이미지 탓으로 표시하지 않는다.

업로드 화면 안내에 **"이름·학번이 보이지 않게 가려 주세요"**를 표시한다(`strings_timetable.xml`).

## 3. Storage 경로 계약 (제안, B·E와 확정 필요)

```text
timetableImages/{uid}/{batchId}/{index}.jpg
  uid     : Auth UID (앱은 AuthRepositories.get(context).getCurrentUid())
  batchId : 앱이 만든 UUID, [A-Za-z0-9-]{1,64}
  index   : 0..4, 선택 순서 = analyzeTimetable imagePaths 순서 = 인식 결과 sourceImageIndex
  contentType: image/jpeg, size < 5MB
```

- 코드상 단일 출처: `data/repository/TimetableImagePaths` (경로·5장·5MB·content type).
- 서버 `functions/src/ai/tasks/analyzeTimetable.ts`의 `timetableImagePrefix(uid)` = `timetableImages/{uid}/`, `MAX_IMAGES = 5`, 경로 300자 이하와 맞다. 서버 `authorize`는 접두사·`..`만 보므로 이 경로 형식을 그대로 받는다(서버 변경 불필요).

## 4. B 요청 — Storage Rules·설정 (B 영역, 이 PR은 수정하지 않음)

### 4.1 `storage.rules`에 추가할 규칙 (제안)

```text
// BT-025: 시간표 이미지. 본인만 읽기·생성·삭제, 덮어쓰기(update) 없음.
match /timetableImages/{uid}/{batchId}/{file} {
  allow read: if request.auth != null && request.auth.uid == uid;
  allow create: if request.auth != null
      && request.auth.uid == uid
      && batchId.matches('^[A-Za-z0-9-]{1,64}$')
      && file.matches('^[0-4][.]jpg$')
      && request.resource.size < 5 * 1024 * 1024
      && request.resource.contentType == 'image/jpeg';
  allow delete: if request.auth != null && request.auth.uid == uid;
}
```

- 다른 계정은 읽기·쓰기·삭제 모두 거부해야 한다(이슈 완료 조건 "다른 계정 파일 접근 차단").
- 서버 analyzeTimetable은 Admin SDK로 읽으므로 Rules와 무관하다. 대신 서버 `authorize`가 경로 소유를 확인한다(구현돼 있음).
- 학교 이메일 인증 여부(`request.auth.token.email_verified`)를 함께 볼지는 B가 프로필 사진 규칙과 맞춰 결정한다.

### 4.2 그 밖의 요청

| 요청 | 대상 | 이유 |
|---|---|---|
| `firebase.json` emulators에 `storage`(예: 9199) 추가 | B(공용 파일) | Rules를 에뮬레이터에서 계정 2개로 확인하기 위해. 없으면 게시된 Rules로 AVD에서만 확인 가능 |
| 버킷 Lifecycle: `timetableImages/` 접두사 1일 후 삭제 | 관리자 | 앱이 지우지 못한 이미지(프로세스 종료, 네트워크 끊김) 정리용 안전장치. **설정 완료(B, 2026-11-18)** |
| Rules 게시 일정 공유 | B | 게시 후 P2(실제 업로드)를 연결하고 AVD에서 검증 |
| `ProfilePhotoCompressor` 공용화 여부 | B | 이번 PR은 수정하지 않고 `timetable/TimetableImageCompressor`를 따로 만들었다(해상도 2048px·5MB 품질 루프가 달라서). 공용화하면 합친다 |

## 6. 보안·개인정보

- 업로드 JPEG는 다시 인코딩해 EXIF(위치 등)를 남기지 않는다. 화면 안내로 이름·학번 가림을 요청한다.
- 로그에 **이미지 바이트, content URI, 파일명, Storage 경로, 인식 결과를 남기지 않는다.** P1은 새 로그를 추가하지 않았고, P2는 정리 실패 로그 하나(오류 코드만, 11장)를 추가했다. 실패 객체의 `detail`도 URI·파일명을 담지 않는다.
- 앱은 Gemini를 직접 부르지 않으며 API 키를 다루지 않는다. 인식은 `analyzeTimetable` Callable만 호출한다(BT-026).
- Gemini 무료 등급 키 사용 중에는 실제 연동 검증에 **테스트용 시간표 이미지만** 쓴다(BT-024.md).
- 이미지 보관: 인식이 끝나거나 선택을 바꾸거나 화면을 떠나면 앱이 지운다(최선 시도). 남은 것은 버킷 Lifecycle(설정 완료, 1일 후 삭제)로 정리한다.

## 11. P2 — 실제 Storage 업로드 (2026-11-18)

### 11.1 구현

- **저장소 선택(`TimetableImageRepositories`)**: `TimetableRepositories`와 같은 기준(`AuthRepositories.isFirebaseEnabled`)으로 Firebase 빌드면 `FirebaseTimetableImageRepository`, 아니면 Mock. 둘 다 앱 전역 하나다.
- **로그인 UID 없음**: Mock으로 바꾸지 않는다(가짜 성공 방지). 호출마다 `AuthRepositories.get(context).getCurrentUid()`를 확인해 없으면(또는 경로로 쓸 수 없으면) 업로드·삭제를 시작하지 않고 `NOT_SIGNED_IN`("로그인이 필요해요…").
- **업로드**: 이미지마다 순서대로 `putBytes`(contentType `image/jpeg`). 경로는 `TimetableImagePaths.imagePath(uid, batchId, i)`로만 만든다. 진행률은 이미지별 `onProgress`로 알리고 화면은 전체 바이트 기준으로 합친다(기존 Uploader).
- **새 batchId**: Rules가 같은 경로 덮어쓰기(update)를 허용하지 않으므로, 분석(재시도 포함)마다 `TimetableImageUploader.start`가 새 UUID batchId를 만든다(기존 동작, 테스트로 고정).
- **재시도 상한**: `FirebaseStorage.setMaxUploadRetryTimeMillis(20초)`. #101(BT-030) 프로필 저장과 같은 값이다(B의 상수는 package-private이라 같은 값을 주석과 함께 다시 적음). 인스턴스가 앱 전역 하나라 프로필 업로드에도 같은 값이 적용된다. 삭제 등 다른 작업의 재시도 시간은 바꾸지 않았다.
- 순서·취소·정리 판단은 `FirebaseTimetableImageRepository`(가짜 Store로 JVM 테스트), Storage 호출은 `FirebaseTimetableImageStore`(얇은 연결층)가 한다.

### 11.2 오류 매핑 (`TimetableImageStorageErrors`)

| StorageException | 실패 코드 | 안내 |
|---|---|---|
| `ERROR_NOT_AUTHORIZED` | `PERMISSION_DENIED` | Rules 거부(다른 계정 경로, 5MB 이상, image/jpeg 아님, 덮어쓰기). 재시도 버튼 없음 |
| `ERROR_NOT_AUTHENTICATED` | `NOT_SIGNED_IN` | |
| `ERROR_RETRY_LIMIT_EXCEEDED` | `NETWORK` | 20초 재시도 뒤 "네트워크 연결을 확인한 뒤 다시 시도해 주세요." |
| `ERROR_UNKNOWN` + 원인 IOException | `NETWORK` | |
| `ERROR_CANCELED` | `CANCELED` | 사용자 취소는 콜백을 부르지 않아 화면에 나오지 않는다 |
| `ERROR_QUOTA_EXCEEDED` | `QUOTA_EXCEEDED`(신규) | 버킷 할당량 초과. "지금은 이미지를 올릴 수 없어요. 잠시 후 다시 시도해 주세요." 재시도 대상 아님 |
| 그 밖·StorageException 아님 | `UNKNOWN` | "다시 시도" |

파일 하나의 5MB 초과는 업로드 전에 `COMPRESSED_TOO_LARGE`로 막는다(`ERROR_QUOTA_EXCEEDED`와 다름).

### 11.3 실패·취소 정리, 삭제

- **실패**: i번째 이미지에서 실패하면 먼저 실패를 한 번 알린 뒤, 이번 묶음에서 시도한 0..i번 경로를 최선 시도로 지운다(실패한 i번도 서버에 남았을 수 있어 포함, 없는 파일은 성공). 정리 실패는 사용자에게 보이지 않고 `Log.w`에 오류 코드만 남긴다(경로·UID 없음).
- **취소**(`Registration.cancel`, 업로드 중 화면을 떠나거나 선택을 바꿀 때): 진행 중 업로드를 취소하고 이미 올라간 이미지를 지운다. 취소 뒤에는 콜백을 부르지 않는다. 취소 직전에 서버에 다 올라간 업로드는 결과가 도착하면 지운다.
- **`deleteBatch(batchId)`(신규)**: 목록 조회(`listAll`) 없이 알려진 경로 `0.jpg`~`4.jpg`를 지운다. 없는 파일은 성공(멱등).
- **분석 후 삭제 호출: 연결하지 않음 — E 답변 대기.** 서버가 분석 후 이미지를 지우는지(5장) E의 답을 받은 뒤 BT-026에서 연결한다. 지금은 기존대로 선택을 바꾸거나 화면을 떠날 때 `deleteImages`로 지운다.
- 오프라인이라 정리까지 실패하거나 프로세스가 끝나면 이미지가 남는다. 버킷 Lifecycle(`timetableImages/` 1일 후 삭제, 설정 완료(B, 2026-11-18))이 안전장치다.

### 11.4 검증

### 11.5 AVD 확인 (2026-11-18, emulator-5554, 실제 Firebase, 개인정보 없는 합성 테스트 이미지 1.6MB)

설치 빌드가 최신인지 먼저 확인했다(기기 base.apk SHA-256 = 빌드 APK, 커밋 `258ed05` 뒤 `assembleDebug` UP-TO-DATE). 업로드 경로는 확인용으로 기기에서만 Firebase SDK 디버그 로그(`log.tag.NetworkRequest`)를 켜서 봤고, 끝난 뒤 되돌리고 logcat을 지웠다. 앱 코드는 경로를 로그에 남기지 않는다.

| 시나리오 | 결과 | 근거 |
|---|---|---|
| 정상 업로드(2장) | 통과 | "업로드 중… 0%" → 검수 화면으로 이동. `{batchId}/0.jpg`·`1.jpg` 요청 모두 200 |
| 업로드 중 취소(2장, 1번 업로드 중 뒤로) | 통과 | 오류 안내 없이 방식 선택 화면으로 돌아감. 진행 중 1번 업로드 취소(`The operation was cancelled`, 세션 취소 요청), 올라간 0번 DELETE 204. 앱 비정상 종료 없음 |
| 비행기 모드에서 분석 | 통과 | 약 20초 뒤 `-13030`(RETRY_LIMIT_EXCEEDED) → "네트워크 연결을 확인한 뒤 다시 시도해 주세요." + [다시 시도], 화면 유지. 요청이 나가지 않아 서버에 남은 것 없음 |
| 업로드 중 비행기 모드(0번 업로드 뒤, 1번 중) | 통과 | 약 20초 뒤 같은 네트워크 안내. 정리 삭제는 오프라인이라 실패 → `W TimetableImages: image cleanup failed: NETWORK` 2건(코드만, 경로·UID 없음), 사용자 안내 없음. 콘솔에는 이 batchId 폴더가 없었다(11.6) |
| 실패 후 재시도 | 통과 | 연결 복구 뒤 [다시 시도] → 실패한 묶음과 다른 새 batchId로 2장 200 → 검수 화면 |
| 업로드 후 화면 종료(1장) | 통과 | 검수 → 업로드 → 방식 선택으로 나가자 0번 DELETE 204 |
| 다른 계정 경로·덮어쓰기·5MB 이상·image/jpeg 아님 거부 | B가 규칙 테스트로 확인 | 앱이 그런 요청을 만들지 않아 AVD로는 확인하지 않았다. 운영 규칙을 B가 Rules 테스트 API로 판정(11.8), #107 Storage 에뮬레이터 테스트도 근거 |

- 정상 업로드와 재시도 묶음은 콘솔 확인을 위해 앱을 강제 종료해 남겨 두었다(화면 종료로 지우지 않음).

### 11.6 Firebase 콘솔 확인 (사용자 확인)

| 묶음 | 콘솔 결과 |
|---|---|
| 정상 업로드 | 폴더와 파일(`0.jpg`·`1.jpg`) 있음 |
| 실패 후 재시도 | 폴더와 파일 있음. 실패한 묶음과 다른 batchId |
| 업로드 중 취소 | 폴더가 없거나 비어 있음 |
| 업로드 중 비행기 모드(끊김) | 폴더 없음 |
| 업로드 후 화면 종료 | 폴더 없음 |

- 올라온 파일은 모두 `image/jpeg`였다.
- 끊김 묶음: 끊김 시점의 0번 업로드가 서버에 만들어지기 전이었던 것으로 보인다. 다만 앱 로그에는 0번의 마지막 업로드 요청 응답 200과 정리 실패 로그가 함께 있어 원인은 확정하지 못했다. **"정리 실패 시 파일이 서버에 남는 경우"는 이번에 직접 확인하지 못했다.**
- 테스트 파일은 확인 뒤 콘솔에서 삭제했다.

### 11.7 남은 위험

- 버킷 Lifecycle: 2026-11-18에 B(KH0110)가 설정했다. `timetableImages/` 아래 파일은 1일 후 자동 삭제되고, 프로필 사진 등 다른 경로는 영향이 없다. 오프라인 정리 실패·프로세스 종료로 앱이 지우지 못한 이미지도 이 규칙이 정리한다. 다만 "정리 실패 시 파일이 서버에 남는 경우"를 앱에서 직접 확인하지는 못했다(11.6).
- `FirebaseStorage.getInstance()`는 앱 전역 하나라, 업로드 재시도 상한 20초가 **프로필 업로드에도 적용된다**(#101 BT-030과 같은 값).
- 분석 후 `deleteBatch` 호출 연결은 E 답변 대기다.

### 11.8 두 계정 규칙 검증 (B, #111)

B가 운영에 게시된 Storage 규칙을 Firebase Rules 테스트 API로 직접 판정했다(실제 파일을 쓰거나 지우지 않음).

| 경우 | 결과 |
|---|---|
| 다른 계정의 읽기·쓰기·삭제·목록 | 모두 거부 |
| 비로그인 읽기 | 거부 |
| 같은 경로 덮어쓰기(기존 파일이 있을 때 쓰기, 본인·다른 계정) | 모두 거부 |
| 본인 create 5MB, `image/png` | 거부 |
| 본인 create/get/delete 기준선 | 허용 |

- 한계: 실제 기기 두 대나 실제 업로드로 덮어쓰기를 확인한 것은 아니다. 앱은 분석마다 새 batchId를 써서 같은 경로를 다시 만들지 않는다. 나중에 실기기로 한 번 더 볼 예정이다.
