## 3. API

```
deleteAccount()  // 입력 없음({} 또는 null만 허용)
→ { deleted: true, closedRequests, endedMatches, leftRooms }
```

- 리전 `asia-northeast3`, 제한 시간 120초. 토큰 UID와 학교 이메일만 신원으로 쓴다. 본문에 UID 등 다른 값이 있으면 `invalid-argument`.
- **순서**: 검색 제외(`matchSettings`·`publicProfiles` 먼저 삭제) → 대기 요청 정리 → 진행 매칭 종료 → 채팅방 나가기 → 개인 데이터 삭제 → Storage → Auth 삭제.
- **멱등·이어하기**: 각 단계는 다시 실행해도 같은 결과다. 실패하면 `unavailable`(retryable)을 돌려주고, 같은 사용자가 다시 부르면 남은 단계를 이어서 끝낸다. Auth 삭제가 마지막이라 실패해도 다시 부를 수 있다.
- **늦게 도는 채팅 연결(#130 리뷰 D)**: 탈퇴 첫 단계에서 `accountDeletions/{uid}`를 쓰면 `ChatLinkService.link`(E, BT-034)가 그 UID가 참여한 매칭의 새 연결을 `PARTICIPANT_DELETED`로 거부한다. 연결 마지막 단계에서도 다시 확인해, 도중에 탈퇴가 시작되면 완료로 표시하지 않는다. 탈퇴 전에 시작해 lease가 남은 연결이 있으면 탈퇴는 `unavailable/CHAT_LINK_BUSY`(retryAfterMillis)로 미루고, 다시 호출하면 그 연결이 쓴 방·목록까지 정리한다. `accountDeletions`는 지우지 않으므로 탈퇴 뒤에도 연결 거부가 유지된다.
- **진행 기록**: 서버 전용 `accountDeletions/{uid}` = `{uid, status: RUNNING|FAILED|DONE, attempts, startedAt, finishedAt, updatedAt}`. Rules에 경로가 없어 앱은 읽기·쓰기 모두 거부된다.
- 로그에는 UID·오류 메시지를 남기지 않고 오류 코드와 requestId만 남긴다.
- 요청 정리는 `requestUserGuards/{uid}.revision`을 올려 BT-031 생성·수락과 같은 문서에서 경합한다.

## 7. 남은 한계·후속

1. **운영 반영 전**: `deleteAccount` 배포와 Storage 삭제 권한(기본 서비스 계정) 확인은 SM 승인 후. 배포 전에는 실제 앱에서 탈퇴가 실패 토스트로 끝난다(데이터는 바뀌지 않음).
2. **남은 ID 토큰**: Auth 삭제 뒤에도 기기의 ID 토큰은 만료(최대 1시간)까지 Rules에서 유효하다. 앱은 성공 즉시 로그아웃하므로 정상 경로에서는 쓰지 않는다. 탈퇴 직후 같은 토큰으로 `users/{uid}`를 다시 쓰는 비정상 클라이언트는 막지 못한다.
3. **BT-038·043과의 잠금**: 지연 연결은 이번에 `accountDeletions` 확인으로 막았다(위 3장). 아직 develop에 없는 BT-038 `RoomStateService`·BT-043 나가기의 `chatPairs` lease는 #121·#128 병합 뒤 같은 잠금과 탈퇴 상태 확인을 쓰도록 맞춘다(D·E와 함께).
4. **새 값**: `matchRequests.terminalReason=ACCOUNT_DELETED`, `matches.endReason=ACCOUNT_DELETED`. BT-044 후기 화면은 `reviewEligible=false`라 대상이 아니지만, 종료 사유를 표시한다면 D·E 확인이 필요하다.
5. **BT-046 연결**: #129 병합 뒤 탈퇴 계정이 차단했던 방의 `chatRooms/{roomId}/blocks/{uid}`는 방이 보관되므로 그대로 둔다(전송은 이미 막힘).
6. 실제 계정 탈퇴 확인(테스트 계정 1개)은 배포 뒤 진행한다.
