| 사용자 화면·기기 종료 | 앱이 열려야만 만료되는 문제 | 서버가 만료 작업을 수행. Android 타이머나 화면의 임의 DB 쓰기로 구현하지 않음 |
| 수신 집중·기존 한도 초과 데이터 | 무제한 조회·대량 쓰기·호출 증가 | 인덱스·제한된 조회·재처리 가능한 정리 사용. 소급 데이터 마이그레이션은 별도 승인 없이 실행하지 않음 |
| 도입 전 상한 초과 대기 | 기존 요청 강제 취소 | 기존 요청 보존, 한도 미만까지 신규 생성 차단. 이후 정상적인 수락·거절·취소·만료로 자리 반환 |
| 정리 실패·중복 실행 | 일부 요청만 남거나 개수 중복 반환 | 요청별 상태 전환을 멱등 처리하고 재시도 시 미처리 항목만 반영. 실패 사실을 숨기지 않음 |

예: A–B의 13~14시 매칭이 확정되면 A→C, B→D 중 겹치는 요청은 취소하고 C→A, D→B 중 겹치는 요청은 거절한다. 다른 날짜/비겹침은 보존한다. 새로운 역방향 요청은 BT-031에서 미리 차단한다.

## 구현 계획

1. **공통 종료 경로를 만든다.** BT-031의 생성·취소·수락/거절과 같은 상태 전환·개수·잠금 처리기를 사용한다. 서버 전용 처리 사유로 직접 취소/상충 자동 취소/자동 거절/만료를 구분한다. reason 필드명·코드는 구현 PR에서 명세로 확정한다.
2. **수락 트랜잭션에 양측 정리를 통합한다.** 양측의 보낸/받은 유효 대기 요청을 조회하고 ID 중복을 제거한다. 수락 대상은 제외하고 동일 날짜의 실제 겹침만 정리한다. 한도 도입으로 정리량이 제한되는 정상 데이터는 같은 트랜잭션에서 처리하는 방향을 우선한다. 모든 필요한 읽기를 마친 뒤 상태·개수·잠금을 함께 쓴다.
3. **한도를 초과한 기존 데이터와 부분 실패를 처리한다.** 한 트랜잭션에 무제한 문서를 넣지 않는다. 제한된 단위로 복구해야 하면 재시작 후에도 남는 처리 위치·멱등성을 설계하고, 완료 전에도 BT-031의 확정 시간 보호가 신규 충돌을 막도록 한다. 무제한 재귀 호출·즉시 재시도 루프는 사용하지 않는다.
4. **서버 만료 정리를 구현한다.** 저장된 meetingDate/endMinute를 KST 종료 시각으로 해석하고 경계 시점부터 신규 생성 한도·수락 판정에서 지난 요청을 유효 대기로 취급하지 않는다. 서버 정리 작업으로 CANCELED와 만료 사유를 저장한다. 원본 시간 필드를 바꾸지 않는다.
5. **운영 실행 주기와 비용은 분리한다.** 앱이 닫혀도 실행될 서버 작업의 호출 방식·주기는 B/SM과 무료 사용량/비용을 검토해 구현 계약에 적는다. 이 계획 단계에서 Scheduler 활성화·운영 배포·결제 변경을 하지 않는다. 정리 작업이 늦어도 만료 요청이 수락되거나 상한 자리를 영구 점유하지 않게 한다.
6. **기존 실시간 목록을 재사용한다.** UID별 발신/수신 리스너와 `RequestItemCache` 병합 규칙을 유지한다. PENDING만 대기 탭에 표시하고 서버가 처리한 종결 상태가 양측에 반영되도록 한다. 오래된 PENDING 응답이 다시 카드를 살리지 않게 한다. 화면 안내만 명확히 하고 새 탭은 추가하지 않는다.

## 이번 계획 준비의 실행 상태

### 구현 연결

- `functions/src/requests/maintenance.ts`: 수락 트랜잭션의 읽기/쓰기 단계와 서버 만료·복구 처리기. 정상 한도 내 네 방향 상충 요청은 매칭 생성과 같은 트랜잭션에서 처리한다. 제3자 사용자 잠금도 함께 갱신하여 생성/수락과 경합을 보호한다.
- `matchRequests.terminalReason=MATCH_CONFLICT`는 상충 정리, `EXPIRED`는 저장된 종료 시각 경과다. 원본 시간·목적·참여자·생성 시각은 보존한다. 자동 정리는 `cooldownUntil`을 변경하지 않는다.
- 기존 대량 요청은 방향별 최대 40건씩 읽고 서버 전용 `matchCleanupJobs/{matchId}`에 `PENDING/DONE/FAILED`, `attempts`, `acceptedAt`, `updatedAt`을 남긴다. 수락 시각 이전 요청만 처리한다. 반복 실행은 미처리 PENDING만 정리하고 실패 3회 후 FAILED로 보존한다. 앱 읽기/쓰기는 금지한다.
- `maintainMatchRequests`: 사용자 선택대로 **5분 간격** 예약 코드. 실행당 지난 날짜 25건·오늘 만료 25건·미완료 정리 작업 2건 이내다. `maxInstances=1`, 자동 이벤트 재시도 없음. 각 작업의 실패 건수를 기록한다. 대량 적체 시 목록 반영은 여러 주기가 필요하다. 잘못된 과거 데이터의 실패 로그·FAILED 작업은 운영자가 확인해야 하며 자동 삭제/마이그레이션하지 않는다.
- 만료 요청은 정리 주기를 기다리지 않고 생성 한도/수락 판정에서 즉시 제외한다. 현재 검색을 다시 실행하면 수신 상한·역방향 요청·ACTIVE 시간 충돌을 반영한다. 이미 열린 검색 결과는 실시간 구독이 아니므로 자동 갱신을 보장하지 않는다. 신청 서버에서 다시 검사한다.
- 기존 UID별 요청 리스너와 `RequestItemCache`를 재사용해 종결 상태를 양측 요청 탭에 전파한다. Android 안내는 ‘겹치는 시간’ 조건을 명시한다. A 검색 경로, B/SM Rules/인덱스에 영향이 있으므로 PR에서 함께 검토해야 한다.
- 조회 인덱스 5개를 추가했다. 로컬 Emulator는 운영 복합 인덱스 생성을 검증하지 않으므로 승인된 배포 후 인덱스 준비와 실데이터 조회를 별도로 확인한다. Scheduler도 이 코드 작성만으로 활성화되지 않는다. 무료 사용량·비용 검토와 관리자 배포 승인이 필요하다.

### PR #104 재검수 보완 (2026-11-17)

수락의 만료 판정·상충 정리 기준 시각은 **양측 requestUserGuards 읽기를 완료한 뒤** 확보한다. 함수 진입 시각을 사용하면 잠금 대기 중 먼저 커밋한 새 요청이 정리 대상에서 누락되어 작업이 DONE이어도 PENDING으로 남을 수 있었다. 기존 생성 시각·확정 스냅샷과 대량 정리의 수락 후 생성 요청 보존 기준은 유지한다. 신규 필드·인덱스·운영 설정 변경은 없다.

실제 로컬 Firestore 트랜잭션의 잠금 읽기를 지연하고 그 사이 발신자의 다른 요청을 생성하는 회귀 테스트를 추가했다. 수정 전 PENDING 잔류 실패를 확인했고, 최종 `npm --prefix functions run build`·단위 테스트 **210개** 및 `firebase emulators:exec --project demo-bintime --only firestore "npm --prefix functions run test:emulator -- --maxWorkers=1 --no-file-parallelism"`의 Firestore **42개**가 통과했다(RTDB 26개 제외). 자동 취소 후 직접 취소 cooldown이 생기지 않는 것도 확인했다. 선행 #103의 프로필 재시도·확인창 보완을 일반 merge로 포함한다.
