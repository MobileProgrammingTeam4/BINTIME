# BT-012 / Issue #12 — 공통 계약·시간 규칙

## BT-039 알림 계약 (2026-11-24)

본인 `notifications/{uid}/items/{id}`만 구독·읽음 처리하고, 이벤트·수신자·기기 토큰·전송 작업은 서버에서 관리한다.
공강 알림은 한국 시간 공강 시작 기준이며 매칭 스위치와 독립적이다. 종류별 OFF는 푸시만 억제하고 앱 이력은 유지한다.
스키마·트리거·BT-044 연결 및 로컬/운영 검증 구분은 [BT-039](./BT-039.md)를 따른다.

## BT-038 종료 계약 (2026-11-24)

- `endMatch({matchId})`는 인증된 참여자만 개별 약속을 ENDED로 바꾼다. 자동 종료는 1분 주기 서버 작업이며 원래 종료 시각을 `endedAt`으로 보존한다.
- `endReason`, `endedBy`, `endProcessedAt`, `reviewEligible`는 서버 전용. 시작 전 수동 종료의 후기 제외는 영구 유지하고 중복 종료로 최초 결정을 덮지 않는다.
- `roomStateJobs`는 서버 전용 복구 작업. `chatPairs.roomStateOwner/roomStateLeaseUntil`을 연결·BT-043 나가기와 공유한다. 방 status는 연결된 ACTIVE 전체를 집계하며 종료로 메시지 권한을 바꾸지 않는다.
- API·스키마·기존 컴포넌트와 BT-043/044 인수인계는 [BT-038](./BT-038.md)를 따른다. 코드 준비와 운영 Scheduler 활성화·E 기능 통합은 구분한다.

## BT-033 추가 계약 (2026-11-17)

- 개별 `matchId=requestId`와 실제 `chatRoomId`를 구분한다. `matches.chatRoomId`가 RTDB `chatRooms/{chatRoomId}`, `userChatRooms/{uid}/{chatRoomId}`의 키다. 방 재사용 때 과거 약속 스냅샷을 덮지 않는다. 아래 기존 API의 RTDB 인자 이름 `matchId`는 호환상 남아 있지만 실제 방 키를 전달한다.
- `chatPairs`·`chatLinkJobs`는 서버 전용 조정/복구 데이터다. `chatRoomLinks`는 방 수준 현재 참여자·보관/준비 상태이며 현재 참여자만 읽는다. 매칭별 연결 완료와 현재 방 사용 가능 상태를 구분한다.
- `ensureMatchChat({matchId})`는 인증된 참여자가 멱등 준비/재시도한다. 반환은 `{matchId, chatRoomId, chatReady}`. 최초 자동 연결 이벤트와 명시적 재시도는 같은 서버 처리기를 사용한다. 운영 배포는 하지 않았다.
- `chatRooms.control`의 writable=false 또는 archived=true면 멤버도 메시지를 새로 쓸 수 없다. 한 명 이탈한 이전 방은 남은 사람만 읽고 새 매칭은 새 방으로 연결한다. 상세 경로·잠금·Rules·E 연동은 [BT-034](./BT-034.md), 표시 정책은 [BT-035](./BT-035.md)를 따른다.
- `control {chatReady,writable,archived}`은 서버 전용 읽기·쓰기다. 앱은 본인 `userChatRooms.chatReady/archived`와 참여자용 `chatRoomLinks`로 상태를 표시한다. 초기 쓰기 차단을 저장한 뒤 멤버 권한을 부여한다. 방의 명시적 준비 false는 이전 약속의 준비 true보다 우선한다.
- 둘 다 나간 방은 사용자 목록과 기록 접근을 막고 서버에만 보관한다. 메시지 자동 삭제는 하지 않으며 보관 기간·최종 삭제는 신고 담당·SM 후속 합의다. 기존 ‘둘 다 이탈 시 삭제’ 결정을 2026-11-17 사용자 승인으로 대체한다.
- `CHAT_PAIR_BUSY`의 `details.blockingMatchId`는 먼저 복구할 이전 매칭 ID다. 활성 lease·재시도 대기 오류는 `retryAfterMillis`를 반환한다. 실패 잠금을 임의로 해제하지 않고 기존 작업 복구 후 새 연결을 재시도한다.
- BT-038에서 `matches.reviewEligible`을 서버가 종료 시 확정해야 한다. 시작 전 수동 종료는 false로 영구 보존한다. 현재 선택 UI는 ENDED/true만 후기 대상으로 하고 미확인 null은 제외한다. 실제 종료/후기 API 완성을 뜻하지 않는다.
- 후기 대상 중 하나라도 미작성이면 방 버튼은 ‘매칭 후기 남기기’, 전부 작성하면 ‘매칭 후기 보기’이며 대상이 없으면 숨긴다. 보관 여부와 무관하게 같은 기준을 사용한다.

## BT-032 추가 계약 (2026-11-17)

- 수락 시 양측의 같은 날짜·겹치는 보낸 대기는 CANCELED, 받은 대기는 REJECTED로 전환한다. `terminalReason=MATCH_CONFLICT`. 저장된 종료 시각이 지난 PENDING은 CANCELED/EXPIRED이며 기존 종결 상태·시간 스냅샷은 보존한다.
- 서버 전용 `matchCleanupJobs/{matchId}`는 기존 대량 상충 요청의 제한 단위 복구를 기록한다. 앱 접근 금지. 자동 정리는 직접 취소의 `cooldownUntil`을 만들거나 지우지 않는다.
- `maintainMatchRequests`의 5분 주기 예약 코드는 운영 활성화와 구분한다. 한도/수락은 실제 종료 시각부터 만료를 제외하고 목록 상태 저장은 정리 작업 이후 반영된다. 구현·상한·실패 처리는 [BT-032](./BT-032.md)를 따른다.

## BT-031 추가 계약 (2026-11-17)

- `respondToMatchRequest({requestId, action})`: action은 `ACCEPTED` 또는 `REJECTED`. 토큰 UID가 수신자인 경우만 허용하며 추가 UID/시간 필드는 거부한다. 수락과 `matches/{requestId}` 생성은 같은 Firestore 트랜잭션이다.
- 서버 전용 `requestUserGuards/{uid}`의 `revision`은 생성·취소·수락/거절의 공통 경합 지점, `cooldownUntil`은 직접 취소 후 신규 생성 제한의 서버 Timestamp다. 앱 읽기/쓰기를 모두 거부한다. 실제 대기 개수는 유효 PENDING 조회로 판정하며 별도 차감 카운터를 중복 갱신하지 않는다.
- 보낸 유효 대기는 3개·받은 유효 대기는 5개까지이며 기존 초과 요청은 보존한다. 직접 취소로 60초간 모든 상대에게 신규 신청을 제한하고 동일 UUID 재시도는 기존 결과를 먼저 반환한다. 자동 취소는 제한을 만들거나 기존 제한을 지우지 않는다.
- 반대 방향 PENDING을 검색·생성에서 차단한다. `matchRequests.terminalReason`은 서버 처리 사유(`MANUAL_CANCEL`, `EXPIRED`, `RECIPIENT_REJECTED`, `ACCEPTED`)다. 기존 문서에서 생략 가능하다.
- `matches`는 참여자만 읽고 앱 쓰기는 금지한다. 새 매칭은 원래 요청의 참여자·목적·날짜·요일·시작/종료·겹침을 복사하며 초기 `ACTIVE`, `chatReady=false`다. 방 생성·재사용은 BT-033/034 후속이며 준비 전 상태를 성공한 채팅 연결로 보고하지 않는다.
- 자세한 범위와 검증은 [BT-031](./BT-031.md)을 따른다. 아래 기존 모델의 구현 당시 설명과 최신 계약을 구분한다.

### 칸 번호는 화면 내부 값

칸 번호(행/슬롯 인덱스)는 **화면 그리기용 내부 값이며 계약이 아니다.** 저장·전달·서버 계약에는 분(minute)만 사용한다. 현재 코드에는 칸 번호 기준이 두 가지 있고, 이번 PR에서 코드는 바꾸지 않았다.

A의 자정 기준 통일 의견은 후속 BT-016의 `SlotGrid`에 팀 기준으로 반영되었다. `SlotGrid`는 하루 48칸(`minute / 30`), `cellsToSlots`는 자정 기준 비트마스크를 분 단위 `TimeSlot`으로 변환한다. 기존 09:00 기준 유틸은 남아 있으므로 아래 두 기준을 구분한다. `TimeUtils`/`TimeSlot` 메서드의 위임·폐기는 후속 작업이다. 상세 API는 [BT-016](./BT-016.md)을 따른다.

| 기준 | 칸 0 | 계산식 | 범위 |
|---|---|---|---|
| **BT-012 행 번호** (`TimeSlot.getStartSlotIndex`, `TimeUtils.minutesToSlotIndex`) | 09:00 | `row = (minute - 540) / 30` | 0~17. `TimeUtils.minutesToSlotIndex`는 0~17로 clamp하고, `TimeSlot.getStartSlotIndex`는 09:00 이전만 0으로 clamp한다(18:00 이후는 18 이상). 09:00~18:00 밖은 행으로 표현되지 않음 |
| **develop 칸 번호** (`TimetableDraft`, `TimetableWeekView`) | 00:00 | `slot = minute / 30` | 0~47. 기본 표시 18~36(09:00~18:00), 범위 밖 수업이 있으면 시간축이 확장됨 |

```text
develop 칸 번호 = BT-012 행 번호 + 18        (09:00~18:00 범위, 행 0~17에서만 성립)
minute         = develop 칸 번호 × 30
               = 540 + BT-012 행 번호 × 30
```

## ② Class / FreeSlot 모델

수업(Class)은 `Course` + `TimeSlot`, 공강(FreeSlot)은 `Timetable.freeSlots`의 `TimeSlot`으로 표현한다. 공강 전용 클래스는 따로 두지 않는다.

| 클래스 | 필드 | 규칙 |
|---|---|---|
| `TimeSlot` (Parcelable) | `dayOfWeek`, `startMinute`, `endMinute` | equals는 세 값 비교. `getDurationMinutes`, `overlapMinutes`, `overlaps` 제공 |
| `Course` (Parcelable) | `courseId`, `name`, `professor`, `classroom`, `colorCode`, `timeSlots` | `courseId`는 생성 시 UUID, **equals/hashCode는 courseId만 비교**. 한 수업이 여러 슬롯(예: 월·수)을 가질 수 있다. `createSingle()`은 요일·시간 파싱 실패 또는 종료 <= 시작이면 슬롯 없이 반환한다 |
| `Timetable` (Parcelable) | `timetableId`, `userId`, `semester`, `revision`, `courses`, `freeSlots` | `addOrUpdateCourse`/`removeCourse`는 courseId 기준이며 변경 때마다 `revision` +1. 생성 시 revision 1 |

### develop `timetable.Course`와의 변환

develop 시간표 화면은 `timetable.Course`(Serializable, `day` 문자열, `"HH:mm"` 시간)를 계속 사용한다. 이번 PR은 그 클래스를 수정하지 않고 `data.model.Course`에 변환 메서드만 추가했다.

| 메서드 | 동작 |
|---|---|
| `Course.fromLegacy(legacy)` | `legacy == null`이면 **null 반환**. 레거시에 ID가 없으므로 **호출마다 새 courseId**를 만든다. 요일·시간이 잘못됐거나 종료 <= 시작이면 슬롯 없이 반환한다. professor·colorCode는 null이다 |
| `course.toLegacy()` | **슬롯이 여러 개면 첫 슬롯만 변환**하고 나머지는 버린다. **슬롯이 없으면 day·startTime·endTime이 null인 객체**를 반환한다(반환값 자체는 null이 아니며, 기본 시간을 지어내지 않는다). 레거시는 null 요일을 "월", null 시간을 0분으로 해석하므로 호출측이 슬롯 유무를 먼저 확인해야 한다. courseId·professor·colorCode는 전달되지 않는다 |

develop의 공강은 `TimetableDraft.freeSlots`(`long[5]`, 월~금 요일별 비트마스크, 비트 i = 자정 기준 칸 i)로 표현된다. `TimeSlot`으로 바꿀 때는 연속 비트 `[i, j)`를 `TimeSlot(day + 1, i × 30, j × 30)`으로 묶는다. develop 공강 표현은 토·일을 지원하지 않는다. 이 변환 코드는 이번 PR에 포함하지 않았다.

### RTDB `chatRooms/{matchId}` 식별자 계약

- `ChatRepository`의 `observeRoom`, `observeMessages`, `sendMessage`, `markRead`, `endMatch`, `leaveRoom`은 모두 **`matchId`를 채팅방 식별자**로 받는다. AGENTS.md의 `chatRooms/{matchId}` 규칙과 일치한다. 별도 roomId는 없다.
- `ENDED` 방에서도 전송할 수 있고, 나가기는 `ENDED`에서만 허용된다(`ACTIVE`는 거절). 수동 종료는 멱등이다(인터페이스 주석, Mock 구현).
- 아래는 **E의 제안 구조**다. 실제 노드/Rules는 BT-021에서 확정하고 요청 수락 후 생성 경계는 BT-034에서 D·E가 맞춘다.

```text
chatRooms/{matchId}/members/{uid}:     { joinedAt }
chatRooms/{matchId}/messages/{pushId}: { senderId, content, createdAt }
userChatRooms/{uid}/{matchId}:         { otherUid, lastMessage, lastMessageAt, unreadCount, status, hidden }
```

> BT-022에서 `userChatRooms/{uid}/{matchId}`에 서버 전용 필드 `lastMessageId`, `recentMessageIds`가 추가됐다. 위 블록은 최초 제안이며 현재 필드 목록은 [BT-021](./BT-021.md)을 따른다.

## BT-017·019 연결 결정 및 구현 경계 (2026-11-12)

- A의 전달 계약: `candidateId = 상대 UID`, 별도 후보 토큰은 없다. 앱은 `{candidateId, clientRequestId}`만 전송하며 시간·목적은 보내지 않는다. 요청 재시도에는 같은 UUID를 유지한다.
- 검색은 먼저 현재/가장 가까운 **내 기준 공강 하나**를 정하고 그 안에서만 후보를 찾는다. 결과가 없다고 다음 공강으로 자동 이동하지 않는다.
- 최소 겹침은 README 원계약과 A의 최신 정정대로 **검색자의 `minOverlapMinutes`** 이상이다. 처음 전달된 양측 최댓값은 적용하지 않으며 검색과 요청 생성 모두 같은 A 판정을 재사용한다.
- #88의 `timetables.freeCells`는 월~일 7개 48비트 정수, `availability`는 `{slots, sourceRevision, updatedAt}`다. 공강만 저장할 때 revision은 유지하고 수업 변경 때 증가시킨다. 서버는 원본·수업·revision을 검증한다. #88·#89의 develop 병합 및 실데이터 검증 완료와 D 브랜치의 선행 코드 통합은 구분한다.
- D의 `SearchCandidateResolver`는 같은 트랜잭션의 `tx.get`을 A의 `FirestoreMatchStore`에 주입해 `resolveCandidate`를 재사용한다. null은 실패이며 `{toUid, purpose, meetingDate, startMinute, endMinute}`만 반환한다.
- 신규 요청은 신청자 `users.profileCompleted`, 수신자 공개 프로필, 양측 최소 겹침·공강 원본·차단·ACTIVE 매칭 충돌을 확인한다. 같은 방향 PENDING은 기존 중복 잠금으로 막고, 반대 방향 PENDING의 수락 시 정리는 BT-031에 남긴다. BT-031은 요청의 `purpose`·`dayOfWeek`도 매칭에 복사한다.
- Firebase용 공통 신청 버튼은 verified draft를 받는 오버로드를 제공한다. 실제 검색 후보를 이 진입점에 전달하는 BT-018 화면 연결은 A 영역이다. Mock 후보를 Firebase 요청으로 자동 변환하지 않는다.
- 실제 두 계정 앱 E2E 전에는 #17·#19·#20을 완료 처리하지 않는다.
