# BT-012 / Issue #12 — 공통 계약·시간 규칙

[PR #77](https://github.com/MobileProgrammingTeam4/BINTIME/pull/77)은 공통 데이터 모델(`data.model`), 시간표 Repository 계약(`data.repository`), 시간 유틸(`util.TimeUtils`)을 추가했으며 develop에 병합되었다. 해당 PR은 시간표 화면(`timetable/`), Manifest, strings, layout을 변경하지 않았다.

2026-11-11에 PR #77의 A·B·D·E 의견을 반영했다. 이 문서는 **현재 코드**, **합의한 연동 계약**, **후속 이슈에서 확정할 제안**을 구분한다. 합의한 계약도 각 담당 이슈에서 구현하기 전에는 동작 완료를 뜻하지 않는다. 아래의 develop 기준은 BT-012와 BT-013(#78)이 병합된 `649555b`이며, 아직 병합되지 않은 BT-014(#79)와 BT-019/020 작업은 별도로 표시한다.

의견 근거: [D 요청·매칭](https://github.com/MobileProgrammingTeam4/BINTIME/pull/77#issuecomment-6736156504), [E 채팅](https://github.com/MobileProgrammingTeam4/BINTIME/pull/77#issuecomment-6739857760), [A 공통·매칭](https://github.com/MobileProgrammingTeam4/BINTIME/pull/77#issuecomment-6761024150), [B 인증·프로필](https://github.com/MobileProgrammingTeam4/BINTIME/pull/77#issuecomment-6765950870).

### 칸 번호는 화면 내부 값

칸 번호(행/슬롯 인덱스)는 **화면 그리기용 내부 값이며 계약이 아니다.** 저장·전달·서버 계약에는 분(minute)만 사용한다. 현재 코드에는 칸 번호 기준이 두 가지 있고, 이번 PR에서 코드는 바꾸지 않았다.

A는 화면 내부 칸도 develop의 자정 기준 `minute / 30`으로 통일하자고 제안했다. 분 단위 계약은 합의 사항이며, 칸 번호 유틸 통일은 후속 구현 전까지 아래 두 기준을 구분한다. 이 문서 수정에서는 코드나 기존 칸 번호를 바꾸지 않았다.

| 기준 | 칸 0 | 계산식 | 범위 |
|---|---|---|---|
| **BT-012 행 번호** (`TimeSlot.getStartSlotIndex`, `TimeUtils.minutesToSlotIndex`) | 09:00 | `row = (minute - 540) / 30` | 0~17. `TimeUtils.minutesToSlotIndex`는 0~17로 clamp하고, `TimeSlot.getStartSlotIndex`는 09:00 이전만 0으로 clamp한다(18:00 이후는 18 이상). 09:00~18:00 밖은 행으로 표현되지 않음 |
| **develop 칸 번호** (`TimetableDraft`, `TimetableWeekView`) | 00:00 | `slot = minute / 30` | 0~47. 기본 표시 18~36(09:00~18:00), 범위 밖 수업이 있으면 시간축이 확장됨 |

```text
develop 칸 번호 = BT-012 행 번호 + 18        (09:00~18:00 범위, 행 0~17에서만 성립)
minute         = develop 칸 번호 × 30
               = 540 + BT-012 행 번호 × 30
```

### develop `timetable.Course`와의 변환

develop 시간표 화면은 `timetable.Course`(Serializable, `day` 문자열, `"HH:mm"` 시간)를 계속 사용한다. 이번 PR은 그 클래스를 수정하지 않고 `data.model.Course`에 변환 메서드만 추가했다.

| 메서드 | 동작 |
|---|---|
| `Course.fromLegacy(legacy)` | `legacy == null`이면 **null 반환**. 레거시에 ID가 없으므로 **호출마다 새 courseId**를 만든다. 요일·시간이 잘못됐거나 종료 <= 시작이면 슬롯 없이 반환한다. professor·colorCode는 null이다 |
| `course.toLegacy()` | **슬롯이 여러 개면 첫 슬롯만 변환**하고 나머지는 버린다. **슬롯이 없으면 day·startTime·endTime이 null인 객체**를 반환한다(반환값 자체는 null이 아니며, 기본 시간을 지어내지 않는다). 레거시는 null 요일을 "월", null 시간을 0분으로 해석하므로 호출측이 슬롯 유무를 먼저 확인해야 한다. courseId·professor·colorCode는 전달되지 않는다 |

develop의 공강은 `TimetableDraft.freeSlots`(`long[5]`, 월~금 요일별 비트마스크, 비트 i = 자정 기준 칸 i)로 표현된다. `TimeSlot`으로 바꿀 때는 연속 비트 `[i, j)`를 `TimeSlot(day + 1, i × 30, j × 30)`으로 묶는다. develop 공강 표현은 토·일을 지원하지 않는다. 이 변환 코드는 이번 PR에 포함하지 않았다.

E는 현재 필드명(`messageId`, `senderId`, `content`, `createdAt`)과 서버 타임스탬프 사용을 제안했다. 실제 RTDB/Rules 적용은 BT-021에서 수행한다. `senderId`는 필수이며 메시지 작성 시 Rules에서 `senderId === auth.uid`를 검증해야 한다. 본문 최대 길이(예: 1000자)는 제안 단계이며 BT-021에서 확정한다. 시스템 메시지 `type`은 BT-043에서 필요 시 따로 제안한다. AI 답장은 사용자가 선택 후 직접 전송하는 일반 메시지다.

### RTDB `chatRooms/{matchId}` 식별자 계약

- `ChatRepository`의 `observeRoom`, `observeMessages`, `sendMessage`, `markRead`, `endMatch`, `leaveRoom`은 모두 **`matchId`를 채팅방 식별자**로 받는다. AGENTS.md의 `chatRooms/{matchId}` 규칙과 일치한다. 별도 roomId는 없다.
- `ENDED` 방에서도 전송할 수 있고, 나가기는 `ENDED`에서만 허용된다(`ACTIVE`는 거절). 수동 종료는 멱등이다(인터페이스 주석, Mock 구현).
- 아래는 **E의 제안 구조**다. 실제 노드/Rules는 BT-021에서 확정하고 요청 수락 후 생성 경계는 BT-034에서 D·E가 맞춘다.

```text
chatRooms/{matchId}/members/{uid}:     { joinedAt }
chatRooms/{matchId}/messages/{pushId}: { senderId, content, createdAt }
userChatRooms/{uid}/{matchId}:         { otherUid, lastMessage, lastMessageAt, unreadCount, status, hidden }
```

| 쓰기/갱신 항목 | E가 제안한 책임 |
|---|---|
| 최초 `members`·`userChatRooms`, `matches.chatReady` | 수락 후 채팅방 생성 서버 함수가 같은 `matchId`로 멱등 생성하고 완료 시 `chatReady = true` |
| `lastMessage`, `lastMessageAt`, 상대 `unreadCount` | 메시지 생성 트리거 함수 |
| `unreadCount = 0` | 클라이언트가 자기 노드의 해당 값만 쓰도록 Rules 제한. `lastReadAt`은 현재 추가하지 않음 |
| 목록 `status` | 원본은 Firestore `matches.status`, 종료 서버가 RTDB에 미러링 |
| `hidden`(나가기) | RTDB Rules가 Firestore ENDED 여부를 직접 조회할 수 없으므로 BT-043 Callable에서 검사. 수동 종료는 D의 BT-038 함수 |

| `ChatRoom` 필드 | 데이터 출처 (E 제안, 공개 프로필 매핑은 B 확인) |
|---|---|
| `matchId`, `participantUids`, `status`, `meetingDate`, `startMinute`, `endMinute`, `chatReady` | Firestore `matches/{matchId}` 확정 스냅샷 |
| `otherName` | `publicProfiles/{otherUid}.nickname` |
| `otherInfo` | 공개 프로필 `department` + `grade` + `gender` (학과 학년 · 성별) |
| `otherHasPhoto` | 공개 프로필 `photoPath != null`, Storage `profileImages/{uid}/profile.jpg` |
| `otherUid`, `lastMessage`, `lastMessageAt`, `unreadCount` | RTDB `userChatRooms/{uid}/{matchId}` |
| `recommendedPlace` | BT-042에서 결정. 그 전에는 null을 허용 |

`ChatRoom`은 Repository에서 위 출처를 합치는 화면용 모델로 유지한다. `ChatRepository`의 콜백 + `Registration` 인터페이스는 유지하고 RTDB 구현체로 연결한다(BT-021/022).

`users`/`publicProfiles`의 전체 필드·권한은 B의 `docs/BT-014.md`를 따른다. 기준 develop에는 아직 해당 파일이 없으므로 [PR #79의 BT-014 문서](https://github.com/MobileProgrammingTeam4/BINTIME/blob/e40c3c395b630ad68957b78b13f085fc6ea06d81/docs/BT-014.md)를 참고하고, 병합 후 로컬 문서를 확인한다. 공개 프로필에는 이메일을 포함하지 않는다.

기준 develop의 Mock 요청(`"received-1"`)과 Mock 채팅(`"match-jimin"`)은 독립 데이터라 수락해도 채팅방이 생기지 않는다. 실제 연결은 합의한 `matchId = requestId` 기준으로 BT-034에서 수행한다. 채팅/후기의 현재 사용자 고정값 `"me"`도 각 Firebase 연동 때 `AuthRepositories` 출처로 전환한다.
