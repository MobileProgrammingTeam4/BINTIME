# BT-014 Firestore 프로필 저장·조회 및 사진 업로드 (Issue #14)

담당: B (인증/프로필) · 선행: BT-004, BT-012, BT-013

## 동작
- `app/google-services.json`이 있으면 `FirebaseProfileRepository`, 없으면 `MockProfileRepository` (`ProfileRepositories.get`).
- 프로필 생성/수정 저장 시 `users/{uid}`와 `publicProfiles/{uid}`를 한 번의 WriteBatch로 저장한다.
- UID는 항상 Firebase Auth 현재 사용자 기준이다. 다른 UID 프로필 저장 요청은 앱에서 거부하고 Rules에서도 막는다.
- 사진: 시스템 사진 선택기(권한 불필요) → 긴 변 512px JPEG로 재인코딩(EXIF 제거) → `profileImages/{uid}/profile.jpg` 업로드 → 경로를 프로필에 저장.
- 로그인 후 라우팅: `users/{uid}.profileCompleted == true`면 메인, 아니면 가입 단계(시간표 → 프로필).
  - 이메일 인증 직후: 링크 검증과 프로필 완료 여부 조회를 `EmailAuthViewModel`이 이어서 처리한다. 조회 중 화면이 회전해도 결과가 새 Activity에 전달되어 이동이 누락되지 않는다.
  - 앱 재실행(로그인 상태): 조회하는 동안 온보딩 문구·버튼을 숨기고 배경만 보여, 가입한 사용자에게 가입 화면이 잠깐 보이지 않게 한다.
  - 프로필 조회 실패(네트워크·권한): 완료 여부를 알 수 없으므로 **메인으로 보내지 않는다.** 온보딩 문구·버튼을 다시 보여 주고 시작 버튼이 "다시 시도"로 바뀌어 재조회한다.
- 프로필 수정 화면: 기존 프로필 조회가 끝나기 전에는 저장하지 않는다(빈 값으로 소개·태그·사진·성별을 덮어쓰지 않도록). 조회 전 회전 시 다시 조회하고, 조회 후 기존 태그 칩을 선택 상태로 다시 그린다.
- 프로필 저장(사진 압축 → 업로드 → 프로필 저장)은 `ProfileSaveViewModel`이 진행한다. 업로드 중 회전해도 저장이 끝까지 진행되고, 새 화면이 결과를 받아 이동한다. 시작한 저장은 취소할 수 없으므로 저장 중에는 뒤로가기·수정 취소를 막고 "저장하고 있어요" 안내만 띄운다.
- 사진 방향: 재인코딩 전에 EXIF 방향(회전·반전)을 픽셀에 반영한다. API 28+는 `ImageDecoder`, API 26·27은 플랫폼 `ExifInterface`로 보정한다.
- 마이페이지 사진: 같은 경로에 덮어쓰므로, 프로필 수정이 저장(`RESULT_OK`)되면 표시 캐시를 비우고 다시 불러온다.

## 스키마 (팀 리뷰 필요, BT-012 계약과 동기화)

`users/{uid}` — 본인만 읽기/쓰기

| 필드 | 타입 | 설명 |
|---|---|---|
| uid | string | 문서 ID와 같음 |
| email | string | 인증 토큰의 이메일 (Rules에서 일치 검사) |
| nickname | string | 1~10자 |
| department | string | 필수 |
| grade | string | "1학년"~"4학년" |
| gender | string | "여성"/"남성", 생성 후 수정 불가(UI) |
| bio | string | 0~150자 |
| interestTags | array<string> | |
| photoPath | string? | `profileImages/{uid}/profile.jpg` 또는 null |
| profileCompleted | bool | 프로필 생성 완료 |
| updatedAt | timestamp | 서버 시간 |

`publicProfiles/{uid}` — 로그인 사용자 읽기, 본인 쓰기. 위 필드에서 `email`, `profileCompleted` 제외.

### 다른 사용자 프로필 조회 API
매칭 카드·요청 카드·채팅 상대처럼 **다른 사용자**를 보여 줄 때는 `ProfileRepository.getPublicProfile(uid, callback)`을 쓴다.
- Firebase: `publicProfiles/{uid}`를 읽는다(로그인 필요). Mock: 저장된 프로필 또는 `MockProfileRepository.putPublicProfile()`로 등록한 프로필.
- 결과의 `email`은 항상 null이다. 공개 문서에 이메일이 섞여 있어도 앱에서 한 번 더 지운다.
- 공개 프로필이 없으면(가입 미완료 등) `onSuccess(null)`. 화면은 "알 수 없는 사용자" 등으로 처리한다.
- 사진은 결과의 `photoPath`를 `loadProfilePhoto()`로 불러온다(Storage 규칙상 로그인 사용자 읽기 허용).
- `getProfile(uid)`는 본인 전용(`users/{uid}`)이다. 다른 UID로 부르면 Firebase에서는 Rules가 거부한다.

Storage `profileImages/{uid}/profile.jpg` — 로그인 사용자 읽기, 본인만 5MB 미만 JPEG(`image/jpeg`) 쓰기. 사용자당 1장을 같은 경로에 덮어쓰며, **다른 파일명은 Rules에서 거부**한다(여러 장 허용은 개수·정리 정책 합의 후).

## Rules
- `firestore.rules`, `storage.rules` (저장소 루트). `firebase.json`에 `storage` 규칙 경로가 있다. Firestore 규칙·인덱스(#84·#85)와 RTDB 규칙(#90) 경로는 각 PR이 추가한다.
- 게시는 B가 `develop`에 병합된 파일 기준으로 한다. 게시 전에 콘솔 규칙을 내려받아 비교하고(다른 영역 규칙이 빠지지 않는지), 게시 후 다시 내려받아 같은지 확인한다.
  - Storage: `firebase deploy --only storage --project bintime-mobile`
  - Firestore 규칙(#84 병합 후): `firebase deploy --only firestore:rules --project bintime-mobile`
- `firestore.rules`는 각 영역이 블록을 **추가만** 한다. 병합 충돌 시 한쪽 파일 전체를 고르지 말고 두 블록을 모두 남긴다.
