## 1. 사용자 확정 사항 (2026-11-24)

| 항목 | 기준 |
|---|---|
| 자동 종료 | 저장된 `meetingDate/endMinute`의 한국 시간 종료 시각. 1분 주기 정리. 정리 지연은 발생할 수 있고 앱 카운트다운이 직접 상태를 쓰지 않음 |
| 수동 종료 | 선택한 개별 `matchId`만 종료. 시작 전 예정 약속도 허용 |
| 조기 종료 후기 | 시작 전 수동 종료는 `reviewEligible=false`를 영구 보존. 이후 시간이 지나도 자격 복구 금지 |
| 종료 후 채팅 | 두 멤버가 남은 방은 계속 송수신. 종료는 나가기·메시지 삭제·보관 전환이 아님 |
| 여러 약속 | 다른 ACTIVE 약속(미래 포함)이 하나라도 있으면 방의 status는 ACTIVE. 모든 약속이 ENDED일 때만 방 표시도 ENDED |
| 나가기 | 연결된 ACTIVE가 하나라도 있으면 금지. 나가기와 신규 연결은 동일 pair에서 순서 보호 |
| 서버 보관 | 한 명 이탈 시 남은 사람만 읽기. 둘 다 이탈하면 양측 접근 차단·서버 보관. 자동 메시지 삭제 없음 |
| 알림 OFF (BT-040) | 해당 종류의 푸시만 억제. 앱 내 알림 이력 유지. 요청 팝업은 독립 스위치 |
| 오늘 팝업 숨김 | 한국 날짜 기준 당일만 자동 표시 억제. 수동 요청 조회는 허용 |
| 공강 알림 | 공강 시작 시점. 매칭 스위치와 독립적으로 공강 알림 설정 ON이면 수신 (BT-039·040에서 연결) |
| 후기 알림 | 후기 대상 매칭 종료 시 작성 안내, 상대 후기 작성 완료 시 수신 안내. 내용 공개 권한은 BT-044가 별도 검사 |

## 2. D 제공 코드와 API

- `functions/src/requests/endMatch.ts`: `MatchEndService.end(matchId, uid?)`, `runBatch()`.
- `functions/src/requests/endCallable.ts`: `endMatch({matchId})`, `maintainMatches`.
- `functions/src/chat/roomState.ts`: `RoomStateService.sync(roomId, participantUids)`, `retryBatch()`.
- `functions/src/chat/pair.ts`: 공통 `chatPairKey`. 기존 link.ts의 export도 유지.
- `chat/FirebaseChatRepository.endMatch`: 기존 `ChatRoomActivity`의 선택·확인 결과를 실제 Callable로 연결.

Callable 입력은 64자리 소문자 hex `matchId` 하나만 허용. UID·종료 시각·후기 자격·상태 입력은 거부한다.
인증된 학교 이메일 및 매칭 참여자만 호출 가능. 응답 `{matchId, status: "ENDED"}`.
오류는 `unauthenticated`, `permission-denied`, `invalid-argument`, `not-found`, 잘못된 기존 데이터의 `data-loss`.
이미 ENDED면 최초 종료 정보를 바꾸지 않고 성공한다. RTDB 갱신 실패도 Firestore 종료를 되돌리지 않는다.

`maintainMatches`는 오늘 만료 25건·과거 ACTIVE 25건 및 복구 작업 20건을 한 번에 제한 처리한다.
1분당 실행 코드를 준비하며 운영 배포·Scheduler 활성화는 별도 승인이다. 실제 비용은 Scheduler·Functions·DB 사용량을 함께 확인한다.

## 3. 종료 스키마 — BT-044가 읽을 계약

`matches/{matchId}`의 기존 참여자·시간 스냅샷·requestId·chatRoomId는 보존한다.

| 필드 | 형식 / 의미 |
|---|---|
| status | ACTIVE → ENDED, 클라이언트 직접 쓰기 금지 |
| endedAt | Timestamp. 자동은 원래 종료 시각, 수동은 서버 처리 시각 |
| endReason | AUTO 또는 MANUAL. 종료 시각 뒤 수동 호출도 AUTO로 분류 |
| endedBy | 수동이면 토큰 UID, 자동이면 null |
| endProcessedAt | 실제 서버가 상태를 확정한 Timestamp. 정리 지연과 약속 종료 시각을 구분 |
| reviewEligible | boolean. 시작 시각 이상에서 종료한 경우 true, 시작 전 수동 종료 false |

`start <= now < end`의 수동 종료는 후기 가능. `now == end`는 자동 종료 기준이다.
24:00은 다음 한국 날짜 00:00으로 해석한다. `ACCEPTED` 원본 요청을 CANCELED로 되돌리지 않는다.
이전 ENDED에 후기 필드가 없으면 임의 backfill하지 않는다. 현재 선택 정책은 ENDED/true만 후기 대상으로 한다.

## 4. BT-043 필수 인수인계: 나가기·신규 연결·방 집계

### 잠금 계약

공통 `chatPairs/{chatPairKey(participants)}`:

- `pendingMatchId`: 기존 채팅 연결 작업의 잠금. 나가기는 준비 중인 연결이 있으면 진행하지 않는다.
- `roomStateOwner`, `roomStateLeaseUntil`: 종료 상태를 RTDB 목록으로 반영하는 작업의 120초 lease. 나가기·멤버 변경도 유효 lease 동안 충돌을 거절/재시도해야 한다.
- `stateRevision`: 종료 트랜잭션에서 증가. 나가기 검사와 경합 시 해당 pair 문서를 같은 트랜잭션에서 읽고 갱신해야 한다.

D는 종료와 `roomStateJobs/{roomId}` 등록을 같은 Firestore 트랜잭션으로 처리한다.
방 상태 처리는 pair lease를 잡고 해당 방 ACTIVE 약속 유무를 다시 조회한 뒤 기존 목록 항목의 status만 바꾼다.
메시지·안읽음·멤버·hidden·control을 변경하지 않는다. 그 사이 새 종료가 생기면 generation 차이를 확인해 재실행한다.
Firestore와 RTDB의 단일 원자성을 보장하는 방식은 아니므로 durable job으로 실패를 복구한다.

### E가 구현할 사항

1. 나가기 Callable에서 해당 방에 연결된 ACTIVE 전체를 서버에서 재검사. 상단 대표 한 건만 보고 허용하지 말 것.
2. 위 pair 잠금과 준비 중 연결을 검사하고 멤버 제거·본인 hidden·읽기 전용 전환을 기존 BT-034 계약대로 한 번의 RTDB update로 적용.
3. 지연된 종료 작업이 새 방을 덮지 않도록 pair의 현재 roomId와 archived를 검사. D의 상태 작업도 같은 검사를 수행한다.
4. 종료만으로 `writable=false`, `chatReady=false`, `archived=true`로 만들지 말 것. 이 상태는 나가기/보관 정책에만 적용.
5. `functions/src/chat/link.ts`가 연결 완료 후 RoomStateService로 재집계하도록 변경됐다. E 수정 시 하드코딩 ACTIVE 반영을 되살리지 말 것.
6. 기존 `FirebaseChatRepository.leaveRoom` 실패 구현은 E가 실제 Callable로 연결. D는 endMatch만 연결한다.

## 5. BT-044 필수 인수인계: 후기 선택·공개

- 기준 식별자는 `matchId`. `chatRoomId`로 후기 중복 키를 만들지 말 것. 매칭당 사용자당 한 건.
- 서버에서 참여자, ENDED, `reviewEligible === true`를 다시 검사. 앱이 전달한 자격을 신뢰하지 않는다.
- `MatchAppointmentPolicy.targets(..., REVIEW)`와 `MatchSelectionSheet`를 재사용. 시작 전 종료·자격 미확인 약속은 제외한다.
- `ChatRoomActivity.refreshReviewStatus()`의 Firebase 미연결 분기를 실제 본인 후기 상태 조회로 교체하는 것은 E 범위.
- 후기 대상 중 하나라도 미작성이면 ‘매칭 후기 남기기’, 전부 작성하면 ‘매칭 후기 보기’. 대상이 없으면 숨김.
- 본인 작성 전 상대 후기 비공개. 후기 수신 알림에도 만족도·태그·한 줄 후기 내용을 노출하지 않는다.
- D의 BT-039 알림과 연결할 후기 이벤트 입력 계약은 `matchId/authorUid/targetUid`를 기준으로 검토하며, 실제 저장 API·Rules는 E가 확정한다. 문서만으로 BT-044 구현 완료를 뜻하지 않는다.
