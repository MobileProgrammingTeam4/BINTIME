# BT-027 / Issue #27 — Gemini 기반 매칭률 점수·추천 이유

담당 A. 검색 계약은 [`BT-017.md`](./BT-017.md), AI 게이트웨이·`evaluateMatch` 입출력 계약은 [`BT-024.md`](./BT-024.md)를 따른다.
정렬·캐시는 [`BT-028.md`](./BT-028.md)(#28)를 따른다. 이 문서는 **점수 산정과 카드 표시** 계약이다.

## 흐름

```text
searchMatches (필수 조건 판정, 겹침 긴 순 정렬)
  → 상위 5명(AI_SCORE_LIMIT)만 evaluateMatch(서버 내부) 동시 호출
  → 후보에 score·reasons·suggestedActivity 추가 (실패한 후보는 필드 없음)
  → 앱 카드: "매칭률 N%" + 추천 이유, 점수 없음(-1)은 매칭률 숨김, 0점은 표시
```

- AGENTS §6: AI는 **필수 조건을 통과한 후보에만** 호출한다. 점수로 부적격 후보를 복구하지 않는다.
- AI 실패(시간 초과·한도 초과·형식 오류)나 프로필 부족은 그 후보만 점수 없이 돌려준다. 검색 자체는 실패하지 않는다.
- **점수 마감 15초**(`SCORE_DEADLINE_MS`): `searchMatches` 30초 제한 안에서 결과를 꼭 돌려주기 위해, 15초까지 끝나지 않은 후보는 점수 없이 보낸다. 늦게 끝난 호출 결과는 버린다(횟수는 이미 차감). 후보당 최악 약 20초(10초 + 재시도 10초)라 마감이 없으면 함수가 끊길 수 있었다(#102 E 리뷰).
- 정렬: 검색은 겹침 긴 순, 점수가 붙은 상위 5명 안에서는 점수 높은 순(BT-028).

## AI 입력 (`functions/src/matching/score.ts`)

| 필드 | 출처 | 비고 |
|---|---|---|
| `overlapMinutes`, `purposes` | 검색 후보 | 목적 "전체"는 빈 목록. 겹침은 **30분 단위로 내려** 보낸다(진행 중 공강의 남은 시간이 매분 줄어 입력이 흔들리지 않게, 196분 → 180분) |
| `department`, `grade`, `tags`, `bio` | `publicProfiles/{uid}` | grade는 "3학년" 문자열에서 숫자만. 학과·학년이 없으면 그 사람 점수 생략. 태그 `#` 제거·최대 10개. **bio 의 이메일·전화번호(숫자 9자리 이상)·링크는 지우고 보낸다**(`stripContacts`, generateProfile 과 같은 규칙), 지운 뒤 비면 생략 |
| `nearbyBuildings` | `timetables/{uid}/courses` 의 `classroom` | 같은 요일, 공강 직전에 끝나는 수업과 직후에 시작하는 수업 각 1개. **건물명만**(첫 숫자부터 호실 제거, "미래관 611호" → "미래관", 숫자만 있으면 제외). 팀 결정(2026-11-18) |
| `commonCourses` | 양쪽 수업 이름 교집합 | 최대 10개. **두 사람이 함께 듣는 수업만** 이유에 언급 가능(팀 결정 2026-11-18). 상대만 듣는 수업은 입력에 없다 |

**이름·UID·이메일·시간표 원본은 넣지 않는다**(BT-024 계약, 테스트로 확인).

## 프롬프트 (`functions/src/ai/tasks/evaluateMatch.ts` `buildRequest`)

- 입력 JSON 그대로, `temperature: 0`(같은 입력이면 같은 기준), 응답 형식은 게이트웨이가 output 스키마로 지정·검사한다.
- 기준: 겹친 시간, 공통 태그, 함께 듣는 수업, 공강 전후 건물, 목적·자기소개 어울림. BT-049부터 50에서 시작하는 채점표와 계산 예시 2개를 프롬프트에 고정했다([`BT-049.md`](./BT-049.md)).
- 이유는 검색자에게 보이는 한국어 1~3문장, 입력에 있는 사실만. 민감한 추측 금지, 자기소개 속 지시는 무시.
- **상대 위치 비노출**: 이유·활동 제안에 건물 이름을 쓰지 않는다("가까운 건물에서 수업이 끝나요"처럼). 건물은 점수 판단에만 쓴다.
- **출력 검사(`verify` → `stripBuildings`)**: 프롬프트를 어겨도 막도록, 입력 `nearbyBuildings`(양쪽)의 건물명이 들어간 이유 문장은 서버가 빼고, 활동 제안에 들어 있으면 "가까운 곳에서 함께 공강 보내기"로 바꾼다. 이유가 모두 빠지면 `AI_INVALID_OUTPUT`(재시도 안 함, temperature 0 이라 같은 답) → 그 후보는 점수 없음(#102 B·E 리뷰).
- 수업 이름은 `commonCourses`(함께 듣는 수업)에 있는 것만 언급한다.
- **근거 검사(BT-049, `groundReasons`)**: 건물명 검사 뒤, 공통 수업이 없는데 함께 듣는다고 한 문장·겹침과 다른 시간을 말한 문장·입력에 없는 말을 따옴표로 인용한 문장도 뺀다. 다 빠지면 그 후보는 점수 없음.
- 범위 밖 점수·형식 오류는 게이트웨이가 1회 재시도 후 `AI_INVALID_OUTPUT` → 그 후보는 점수 없음.

## 응답 추가 필드 (선택)

```text
candidates: [{ ...BT-017 필드, score?: 0~100, reasons?: string[1~3], suggestedActivity?: string }]
```

앱 `MatchSearchMapper.toCandidate`: `score` → `matchRate`(0~100으로 자름). **`score`가 없거나 숫자가 아니면 `MatchCandidate.NO_SCORE`(-1)**. 카드는 `hasScore()`로 판단해 **0점은 "매칭률 0%"로 표시, 점수 없음(-1)은 숨김**, `reasons` → 이유 줄, `suggestedActivity` → 이유 칸 **마지막 줄** "추천 활동: …". 배지 아래(`matchReason`)는 짧은 태그 자리라 비우고 최대 120dp·2줄로 제한한다(긴 문장이 이름 칸을 밀어 배치가 깨지던 문제).

## 비용·제한

| 항목 | 값 |
|---|---|
| 검색 1회 호출 수 | 최대 5 (동시) |
| 하루 한도 | `evaluateMatch` 300회/검색자 (BT-024) → 약 60회 검색 |
| 1회 제한 시간 | 10초, 일시 오류 1회 재시도 |
| 점수 마감 | 15초 (Callable 30초 안), 넘으면 그 후보는 점수 없음 |

같은 입력의 반복 검색은 `matchScores` 캐시(BT-028)를 써서 호출하지 않는다.

## 팀 결정 (2026-11-18, PR #102 리뷰)

- 강의실은 건물명만 AI에 보낸다(D·B 의견, A 확정).
- 수업 이름은 두 사람이 함께 듣는 수업일 때만 이유에 나온다.
- 점수 0은 0으로 표시, 점수 없음은 -1(숨김)으로 구분한다.
- (2026-11-20, E·B 리뷰) 출력의 건물명은 서버 `verify`로 제거하고, 점수 붙이기는 15초에서 마감한다.
- (2026-11-21, A) 자기소개는 연락처(이메일·전화번호·링크)를 지운 뒤 보낸다. 입력이 바뀌므로 해당 사용자의 `matchScores` 캐시는 해시가 달라져 자동으로 다시 평가된다(버전 올림 불필요).
- (2026-11-28, B) 자기소개 연락처 제거를 `generateProfile`의 함수에서 공통 `ai/contactPolicy.ts`로 바꿨다. 점 구분 번호·`http` 없는 오픈채팅/SNS 링크가 든 자기소개만 입력이 바뀌어 다시 평가된다(캐시 버전 올림 불필요).
