## Firestore 구조

```text
timetables/{uid}
  uid: string            (== 경로 uid)
  semester: string       (≤20자)
  revision: int          (수업 쓰기마다 +1. 처음 만들 때 1)
  updatedAt: timestamp   (serverTimestamp)

timetables/{uid}/courses/{courseId}
  courseId: string       (== 문서 ID. 비어 있지 않음, '/' 없음, ≤128자, '.'·'..' 불가)
  name: string           (공백 제거 후 1~30자)
  professor: string?     (≤30자, 비면 필드 생략)
  classroom: string?     (≤30자, 비면 필드 생략)
  colorCode: string?     ("#RRGGBB")
  timeSlots: list<map>   (1~7개) { dayOfWeek: 1..7, startMinute: int, endMinute: int }
                         0 <= startMinute < endMinute <= 1440, 30분 단위가 아니어도 됨
  createdAt, updatedAt: timestamp
```

- Firestore는 정수를 `Long`으로 돌려주므로 `toObject()` 대신 `TimetableDocuments`로 변환한다(`ProfileDocuments`와 같은 방식). 형식이 깨진 수업 문서는 `null`로 건너뛴다.
- 수업당 시간대 상한 7개는 규칙에 반복문이 없어 칸을 풀어서 검사해야 하기 때문이다(팀 결정).

### 위치·저장 방식 비교 결론

- **위치: `timetables/{uid}` 별도 컬렉션.** AGENTS.md §5 계약과 같고, 규칙 블록을 C가 따로 관리할 수 있다. `users/{uid}`에 넣으면 B의 `validProfile()` 검사와 섞여 시간표 쓰기가 막히고 revision이 프로필 문서와 섞인다.
- **저장 방식: 수업마다 문서 1개.** 수정·삭제가 문서 하나 단위이고, 다른 기기와의 덮어쓰기 위험이 없고, 규칙에서 필드 검증이 가능하다. 배열 방식은 매번 전체를 다시 써야 하고 규칙으로 항목 검증을 할 수 없다. 겹침 검증은 두 방식 모두 규칙으로 불가능하다.

## 인터페이스 요약

`TimetableRepository`(동기)는 그대로 두고, 옆에 비동기 계약 `AsyncTimetableRepository`를 둔다. Firestore 구현이 동기 조회를 메인 스레드에서 할 수 없으므로 상속하지 않는다.

| 메서드 | 동작 |
|---|---|
| `Registration observeTimetable(Listener<Timetable>)` | 등록 직후 현재 값, 이후 바뀔 때마다 전달. 미등록이면 `onData(null)` |
| `addCourse(Course, Callback<Course>)` | 겹침이면 `OVERLAP`, 같은 courseId가 있으면 `INVALID_COURSE` |
| `updateCourse(Course, Callback<Course>)` | 없으면 `NOT_FOUND`. 자기 자신과의 겹침은 제외 |
| `deleteCourse(String, Callback<Void>)` | 이미 없으면 성공(멱등) |
| `replaceCourses(List<Course>, Callback<Void>)` | 전체 교체(이미지 인식 검수 결과 등). courseId 중복·수업끼리 겹침 거부 |

- `Registration`, `Listener`, `Callback`은 `ChatRepository`와 같은 형태지만 `chat/`(E)에 의존하지 않도록 이 인터페이스 안에 정의했다. `common/`으로 합치는 일은 A에게 제안할 후속 작업이다.
- `TimetableFailure.Code`: `NOT_SIGNED_IN`, `INVALID_COURSE`, `OVERLAP`(겹친 수업 ID 포함), `NOT_FOUND`, `PERMISSION_DENIED`, `NETWORK`, `CONFLICT`, `UNKNOWN`. `getDetail()`은 로그·테스트용이며 화면에는 코드로 문구를 고른다.
- **UID 원칙:** 메서드는 UID를 인자로 받지 않는다. 구현체가 저장소 안에서 현재 로그인 UID를 얻는다. Firestore 구현(②)은 `AuthRepositories.get(context).getCurrentUid()`를 쓰고, 정적 `currentUid()`는 쓰지 않는다. `MockAsyncTimetableRepository`는 생성자로 받은 `Supplier<String> uidSupplier`에서 매 호출마다 얻는다.
- 리스너는 등록 시점의 UID에 묶인다. 로그아웃·계정 전환 시 화면이 `remove()` 후 다시 구독한다.
- 콜백 스레드: Firestore 구현은 메인 스레드, Mock 어댑터는 호출한 스레드에서 즉시.
- `MockAsyncTimetableRepository`는 기존 `MockTimetableRepositoryImpl`(동기)을 감싼다. 리스너에는 깊은 사본을 전달하고, 저장 전 `CourseValidator.sanitize`로 공백을 정리한다. 메모리 저장이라 앱 재실행 시 사라진다.

## 겹침 검증 방침

| 위치 | 역할 |
|---|---|
| 클라이언트 `CourseValidator` | 주 검증. 필드 형식, 수업 하나 안의 시간대 겹침, 다른 수업과의 같은 요일 겹침(같은 courseId 제외). `TimeSlot.overlaps`만 사용하며 끝=시작으로 맞닿는 경우는 허용 |
| 클라이언트 트랜잭션 (②) | 트랜잭션에서 `timetables/{uid}`를 읽어 리스너로 받은 목록의 `revision`과 같을 때만 수업과 `revision+1`을 함께 쓴다. 다르면 `CONFLICT`로 끝내고 최신 목록으로 다시 검증한다. Android 트랜잭션은 쿼리를 못 하므로 부모 revision을 잠금으로 쓴다 |
| Rules | 겹침 검증 불가(쿼리·반복문 없음). 필드 검증과 "수업 쓰기 시 부모 revision 정확히 +1"만 강제 |

- **오프라인 쓰기는 포기한다.** 트랜잭션은 오프라인에서 실패하므로 `NETWORK`로 안내한다. 겹침·동시성 보장을 우선했다.
- 서버가 겹침을 보장해야 한다면 나중에 callable 함수로 옮길 수 있다. 매칭 적격성은 어차피 서버가 다시 판단한다.

## 시간표 규칙 초안 (B에게 전달용)

**`firestore.rules` 파일은 수정하지 않았다.** #79(`feature/profile-BT-014`)의 `signedIn()`·`isOwner()`를 재사용하며, `users`/`publicProfiles` 블록 아래에 추가하는 형태다.

```
    // ── BT-015 시간표: 본인만 읽고 쓴다. 겹침 검증은 클라이언트(규칙으로 불가). ──
    function timetablePath(uid) {
      return /databases/$(database)/documents/timetables/$(uid);
    }

    function validSlot(s) {
      return s is map && s.keys().hasOnly(['dayOfWeek', 'startMinute', 'endMinute'])
          && s.dayOfWeek is int && s.dayOfWeek >= 1 && s.dayOfWeek <= 7
          && s.startMinute is int && s.endMinute is int
          && s.startMinute >= 0 && s.startMinute < s.endMinute && s.endMinute <= 1440;
    }

    // 규칙에는 반복문이 없어 최대 7칸을 풀어서 검사한다.
    function validSlotAt(slots, i) {
      return slots.size() <= i || validSlot(slots[i]);
    }

    function optionalText(d, key, max) {
      return !(key in d) || d[key] == null || (d[key] is string && d[key].size() <= max);
    }

    function validCourse(courseId) {
      let d = request.resource.data;
      return d.keys().hasOnly(['courseId', 'name', 'professor', 'classroom',
                               'colorCode', 'timeSlots', 'createdAt', 'updatedAt'])
          && d.courseId == courseId
          && d.name is string && d.name.size() >= 1 && d.name.size() <= 30
          && optionalText(d, 'professor', 30) && optionalText(d, 'classroom', 30)
          && (!('colorCode' in d) || d.colorCode == null
              || (d.colorCode is string && d.colorCode.matches('^#[0-9A-Fa-f]{6}$')))
          && d.timeSlots is list && d.timeSlots.size() >= 1 && d.timeSlots.size() <= 7
          && validSlotAt(d.timeSlots, 0) && validSlotAt(d.timeSlots, 1)
          && validSlotAt(d.timeSlots, 2) && validSlotAt(d.timeSlots, 3)
          && validSlotAt(d.timeSlots, 4) && validSlotAt(d.timeSlots, 5)
          && validSlotAt(d.timeSlots, 6)
          && d.updatedAt == request.time;
    }

    function validTimetable(uid) {
      let d = request.resource.data;
      return d.keys().hasOnly(['uid', 'semester', 'revision', 'updatedAt'])
          && d.uid == uid && d.revision is int
          && d.semester is string && d.semester.size() <= 20
          && d.updatedAt == request.time;
    }

    // 수업 쓰기는 같은 트랜잭션/배치에서 부모 revision 을 정확히 +1 해야 한다.
    function revisionBumped(uid) {
      return getAfter(timetablePath(uid)).data.revision
          == (exists(timetablePath(uid)) ? get(timetablePath(uid)).data.revision : 0) + 1;
    }

    match /timetables/{uid} {
      allow read: if isOwner(uid);
      allow create: if isOwner(uid) && validTimetable(uid) && request.resource.data.revision == 1;
      allow update: if isOwner(uid) && validTimetable(uid)
          && request.resource.data.revision == resource.data.revision + 1;
      allow delete: if false; // 탈퇴는 서버에서 처리

      match /courses/{courseId} {
        allow read: if isOwner(uid);
        allow create, update: if isOwner(uid) && validCourse(courseId) && revisionBumped(uid);
        allow delete: if isOwner(uid) && revisionBumped(uid);
      }
    }
```

다른 사용자는 시간표를 읽을 수 없다. 매칭 검색은 Admin SDK 서버 함수가 담당하므로 공개 읽기는 필요 없다.

### 에뮬레이터에서 먼저 검증할 위험

1. **`exists`/`get` 삼항 동작.** 처음 만들 때는 부모 문서가 없다. `exists(...) ? get(...).data.revision : 0`이 기대대로 0을 쓰는지, 없는 문서에 `get`이 평가되어 거부되지 않는지 확인한다.
2. **`get`/`getAfter` 호출 한도.** 트랜잭션·배치당 문서 접근 호출은 20회로 제한된다. 수업 문서 하나마다 `exists`·`get`·`getAfter`를 부르므로 **`replaceCourses`로 수업을 여러 개 한 번에 쓸 때 한도에 걸릴 가능성이 크다.** 같은 문서 호출이 한 번으로 세어지는지 확인하고, 걸리면 일괄 쓰기를 나누거나 규칙 구조를 바꾼다.
3. **`createdAt` 위조 가능성.** 초안은 `createdAt`을 검증하지 않아 클라이언트가 임의 값을 넣을 수 있다. 생성 시 `== request.time`, 수정 시 `== resource.data.createdAt`으로 고정할지 정한다.

추가 전제: 현재 `firebase.json`에는 Firestore 에뮬레이터 포트만 있고 `"firestore": {"rules": ...}` 항목이 없어 규칙 파일을 읽지 않는다. 규칙 테스트(`@firebase/rules-unit-testing`)를 둘 위치와 함께 B·A와 합의가 필요하다.

## BT-016 ③과의 연결 (공강 Firestore 저장)

```text
availability/{uid}
  uid, slots: list<{dayOfWeek, startMinute, endMinute}>, sourceRevision: int, updatedAt
```

- 인터페이스에 `saveFreeSlots(List<TimeSlot>, Callback<Void>)`를 추가한다. 트랜잭션에서 `timetables/{uid}.revision`을 읽고, 선택한 공강이 수업과 겹치지 않는지 확인한 뒤 정리한 공강과 `sourceRevision = revision`을 저장한다.
- 수업을 바꾸면 revision이 올라가 `sourceRevision < revision`이 된다. 이 상태로 "공강 다시 확인 필요"를 판단한다. 기존 `matchRequests`·`matches`는 별도 문서의 시간 스냅샷이라 영향을 받지 않는다(BT-047 원칙).
- 다른 사용자는 `availability`를 읽지 않는다. 매칭 검색 서버 함수가 Admin SDK로 읽는다.

미정 사항:

- 60분 미만 공강 제외(BT-016 `matchableFreeSlots`)를 저장할 때 적용할지, 검색할 때 적용할지 — A(BT-017)와 결정.
- `slots`는 길이가 정해지지 않은 목록이라 규칙 검증이 어렵다. 요일별 48비트 칸 마스크(`TimetableDraft`와 같은 표현)를 함께 저장하면 규칙 검증이 쉽지만 AGENTS 계약은 분 단위다 — ③ 설계 때 결정.
- BT-016 PR(공강 계산기)이 develop에 병합되어야 이 단계에서 재사용할 수 있다. 이번 PR은 BT-016에 의존하지 않는다.
