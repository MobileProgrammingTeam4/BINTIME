# BT-015 (Issue #15)

## 목적

시간표 수업의 추가·수정·삭제를 로그인 사용자 단위로 Firestore에 저장하고 실시간으로 갱신한다. 같은 요일 시간 겹침은 저장 전에 거부한다.

완료 조건: 추가·삭제가 앱 재실행 뒤에도 유지, 겹치는 수업 입력 거부, 두 계정 시간표 분리.

## Firestore 구조

```text
timetables/{uid}
  uid: string            (== 경로 uid)
  semester: string?      (≤20자, null 허용. 앱은 아직 쓰지 않아 필드를 생략한다)
  revision: int          (수업 쓰기마다 +1. 처음 만들 때 1)
  freeCells: list<int>?  (BT-016 공강 선택 원본. 아래 참고)
  updatedAt: timestamp   (serverTimestamp)

timetables/{uid}/courses/{courseId}
  courseId: string       (== 문서 ID. 1~128자, '/' 없음, '.'·'..'·'__.*__' 불가)
  name: string           (공백 제거 후 1~30자)
  professor: string?     (≤30자, 비면 필드 생략)
  classroom: string?     (≤30자, 비면 필드 생략)
  colorCode: string?     ("#RRGGBB")
  timeSlots: list<map>   (1~7개) { dayOfWeek: 1..7, startMinute: int, endMinute: int }
                         0 <= startMinute < endMinute <= 1440, 30분 단위가 아니어도 됨
  createdAt: timestamp   (생성 시 서버 시간, 이후 변경 불가)
  updatedAt: timestamp

availability/{uid}       (BT-016 ③, docs/BT-016.md)
  slots, sourceRevision, updatedAt
```

- Firestore는 정수를 `Long`으로 돌려주므로 `toObject()` 대신 `TimetableDocuments`로 변환한다. 형식이 깨진 수업 문서는 `null`로 건너뛰고 로그를 남긴다.
- 수업당 시간대 상한 7개는 규칙에 반복문이 없어 원소를 하나씩 풀어 검사해야 하기 때문이다(팀 결정).
- **위치·저장 방식**: `timetables/{uid}` 별도 컬렉션, 수업마다 문서 1개. `users/{uid}`에 넣으면 B의 `validProfile()`과 섞이고, 배열 방식은 매번 전체를 다시 써야 하며 규칙으로 항목 검증을 할 수 없다.

## 인터페이스 요약

`TimetableRepository`(동기)는 그대로 두고, 옆에 비동기 계약 `AsyncTimetableRepository`를 둔다.

| 메서드 | 동작 |
|---|---|
| `Registration observeTimetable(Listener<Timetable>)` | 등록 직후 현재 값, 이후 바뀔 때마다 전달. 미등록이면 `onData(null)`. `Timetable.freeSlots`는 공강 선택 원본 |
| `addCourse(Course, Callback<Course>)` | 겹침이면 `OVERLAP`, 같은 courseId가 있으면 `INVALID_COURSE` |
| `updateCourse(Course, Callback<Course>)` | 없으면 `NOT_FOUND`. 자기 자신과의 겹침은 제외 |
| `deleteCourse(String, Callback<Void>)` | 이미 없으면 성공(멱등) |
| `replaceCourses(List<Course>, Callback<Void>)` | 전체 교체. courseId 중복·수업끼리 겹침 거부. **같은 트랜잭션에서 새 수업과 겹치는 `freeCells`를 지우고 `availability`를 다시 저장**(sourceRevision = 새 revision) |
| `saveFreeSlots(List<TimeSlot>, Callback<Void>)` | BT-016 ③. 공강 선택 원본과 `availability` 저장. revision은 그대로 |

- 선택 클래스: `TimetableRepositories.get(Context)` — `AuthRepositories.isFirebaseEnabled`이면 `FirestoreTimetableRepository`, 아니면 `MockAsyncTimetableRepository`(앱 전역 한 인스턴스).
- **UID 원칙**: 메서드는 UID를 인자로 받지 않는다. Firestore 구현과 Mock 선택 모두 매 호출마다 `AuthRepositories.get(context).getCurrentUid()`를 쓴다. 정적 `currentUid()`를 쓰던 `timetable/MockTimetableRepository`는 삭제했다.
- `TimetableFailure.Code`: `NOT_SIGNED_IN`, `INVALID_COURSE`, `OVERLAP`, `INVALID_FREE_SLOT`, `TOO_MANY_FREE_SLOTS`, `NOT_FOUND`, `PERMISSION_DENIED`, `NETWORK`, `CONFLICT`, `UNKNOWN`. 화면은 코드로 문구를 고르고(`timetable/TimetableMessages`) `getDetail()`은 보여주지 않는다.
- Firestore 예외 변환은 `FirestoreFailures`. `PERMISSION_DENIED`→`PERMISSION_DENIED`, `UNAVAILABLE`·`DEADLINE_EXCEEDED`→`NETWORK`, `ABORTED`·`FAILED_PRECONDITION`→`CONFLICT`, `UNAUTHENTICATED`→`NOT_SIGNED_IN`.
- 콜백 스레드: Firestore 구현은 메인 스레드, Mock은 호출한 스레드에서 즉시.
- `observeTimetable`은 부모 문서와 `courses` 리스너 두 개를 묶어, 둘 다 첫 값을 받은 뒤부터 전달한다. 한 트랜잭션의 변경이 두 리스너로 나뉘어 와서 중간 상태가 한 번 전달될 수 있다(곧 다음 값으로 바로잡힌다).

## 겹침 검증과 동시성

| 위치 | 역할 |
|---|---|
| 클라이언트 `CourseValidator` | 주 검증. 필드 형식, 문서 ID, 수업 하나 안의 시간대 겹침, 다른 수업과의 같은 요일 겹침(같은 courseId 제외). `TimeSlot.overlaps`만 사용하며 끝=시작으로 맞닿는 경우는 허용. `validateFields`는 `sanitize`된 입력을 전제한다 |
| 클라이언트 트랜잭션 | **동시성 보호를 맡는다.** 쓰기 전에 부모 revision → 수업 목록 순서로 읽어 검증하고, 트랜잭션에서 부모 revision이 그대로일 때만 수업과 `revision+1`을 함께 쓴다. 다르면 `CONFLICT`. Android 트랜잭션은 쿼리를 못 하므로 부모 revision을 잠금으로 쓴다 |
| Rules | **수업 문서는 소유자 확인과 필드 검증만 한다.** 부모 revision 증가(`revisionBumped`)는 규칙에서 강제하지 않는다. 겹침 검증도 불가(쿼리·반복문 없음) |

- 규칙에서 `revisionBumped`를 뺀 이유: 수업 문서마다 `exists`/`get`/`getAfter`를 부르면 `replaceCourses`처럼 여러 수업을 한 번에 쓸 때 문서 접근 호출 한도(트랜잭션당 20회)에 걸릴 위험이 있고, 에뮬레이터로 확인할 수 없다(아래). 앱은 항상 부모 revision을 함께 올리지만, 규칙을 우회한 클라이언트가 revision을 올리지 않고 수업을 쓰는 것은 막지 못한다. 그 경우 `availability.sourceRevision`이 실제 수업과 어긋날 수 있으므로 매칭 서버(A)는 수업 원본이 아니라 `availability`만 신뢰하고 slots를 다시 정규화한다.
- 삭제는 다른 수업과 무관해 미리 읽은 revision과 비교하지 않는다. 트랜잭션에서 읽은 revision에 +1 한다.
- `createdAt`: 생성 시 서버 시간을 넣고 규칙이 `== request.time`을 검사한다. 수정 때는 보내지 않아(`merge`) 기존 값이 유지되고 규칙이 `== resource.data.createdAt`을 검사한다. 수정 때 비운 선택 필드는 `FieldValue.delete()`로 지운다(`hasOnly` 대응).
- **오프라인 쓰기는 포기한다.** 트랜잭션은 오프라인에서 실패하므로 `NETWORK`로 안내한다.
- 서버가 겹침을 보장해야 한다면 나중에 callable 함수로 옮길 수 있다. 매칭 적격성은 어차피 서버가 다시 판단한다.

## Rules (`firestore.rules`)

`signedIn()`·`isOwner()`(BT-014)를 재사용한다.

| 경로 | 읽기 | 쓰기 |
|---|---|---|
| `timetables/{uid}` | 본인 | 생성: `revision == 1`. 수정: `revision + 1`(수업 변경) **또는** revision 그대로이면서 `freeCells`·`updatedAt`만 바뀜(공강 선택 변경). 키 `uid, semester?, revision, freeCells?, updatedAt`만, `semester`는 null 허용, `freeCells`는 길이 7·각 0 ≤ x < 2^48. 삭제 불가 |
| `timetables/{uid}/courses/{courseId}` | 본인 | 생성: 문서 ID 검증, `validCourse`, `createdAt == request.time`. 수정: `validCourse`, `createdAt` 고정. 삭제: 본인 |
| `availability/{uid}` | 본인 | 키·개수(40 이하)·원소가 map·`sourceRevision`·`updatedAt`만 검사. 슬롯 상세는 검사하지 않음(아래). `docs/BT-016.md` 참고. 삭제 불가 |

다른 사용자는 시간표·공강을 읽을 수 없다. 매칭 검색은 Admin SDK 서버 함수가 담당한다. 콘솔 게시는 B와 함께 합친 규칙으로 한다(BT-014 문서의 통합 주의 참고).

### 규칙 식 평가 한도 (요청당 1000식)

규칙에는 반복문이 없어 목록 원소를 상한까지 하나씩 풀어 검사하는데, 원소 검사가 무거우면 평가식 수가 한도를 넘어 **정상 저장이 거부**된다.

- **B의 에뮬레이터 측정**: `availability.slots` 원소마다 `validSlot` + 30분 경계 + 60분 이상을 검사하던 이전 규칙은 **slots 6개 이상에서 한도를 넘어 거부**됐다(5개까지 통과).
- 조치: `availability`는 원소가 map인지만 검사한다. **슬롯 상세 검증(값 범위·30분 단위·60분 이상)은 규칙이 아니라 클라이언트(`FreeSlotValidator`·`FreeCells`)와 서버(`searchMatches`가 slots 재정규화, A)가 맡는다.** 규칙을 우회해 쓴 잘못된 slots는 서버 정규화에서 걸러져야 한다.
- 수업 문서(`validCourse`)의 `timeSlots`(최대 7개)는 아직 `validSlot` 전체 검사를 유지한다. 추정(아래)으로는 7개도 한도 안이지만 **측정값이 아니다**.

평가식 수 추정 (식별자·리터럴·멤버 접근·호출·연산자를 각각 1로 센 근사값):

| 항목 | 추정 |
|---|---:|
| `validSlot` 본문 (타입·범위 비교 11개 + `&&` 10개) | 약 50 |
| `validSlotAt` 래퍼: 원소 없음(`size() <= i`에서 끝남) | 약 10 |
| `validSlotAt` 래퍼: 원소 있음(호출·인덱스 + `validSlot`) | 약 10 + 56 |
| 이전 `validAvailSlot` 추가분 (`% 30` 2개, `>= 60`) | 약 22 |
| 이전 `availability` 전체: 고정 약 55 + 빈 칸 40×10 + 원소당 78 | 5개 845 / 6개 923 |
| `validCourse` 생성 전체: 고정 약 146 + 칸 7×10 + 원소당 56 | 7개 약 608 |
| 수정 후 `availability`: 고정 약 55 + 40×10 + 원소당 4 | 40개 약 615 |

- 보정: B 측정(5개 통과·6개 거부)을 맞추려면 실제 값은 이 근사의 약 1.08~1.18배다(923×k > 1000, 845×k ≤ 1000). 이를 적용하면 수업 7개 시간대는 약 660~720식, 수정 후 `availability` 40개는 약 670~730식이다. 이 근사로는 수업 시간대가 약 11개를 넘어야 한도에 닿는다.
- 한계: 근사 계산이며, 한도가 쓰기 문서별인지 트랜잭션 전체 합산인지 확인하지 못했다. 합산이라면 `replaceCourses`처럼 수업 여러 개를 한 트랜잭션으로 쓸 때 한도를 넘을 수 있다.

### 에뮬레이터 검증

- `firebase.json`에는 Firestore 에뮬레이터 포트(8080)만 있고 `"firestore": {"rules": "firestore.rules"}` 항목이 없어 에뮬레이터가 규칙 파일을 읽지 않는다. `firebase.json`은 이번 범위에서 수정 금지이고, 이 저장소에 규칙 테스트(`@firebase/rules-unit-testing`)도 없다. 위 평가 한도 측정은 B가 별도 환경에서 한 것이다.
- 확인이 필요한 위험:
  1. `availability`의 `existsAfter`/`getAfter`가 같은 트랜잭션의 부모 쓰기를 반영하는지(설계상 그렇다).
  2. 수정 후 `availability` 규칙이 slots 0·6·40개에서 통과하는지(B 재측정 필요).
  3. 수업 문서 `timeSlots` 7개, 그리고 `replaceCourses`로 7개 시간대 수업 여러 개를 한 트랜잭션에 쓸 때 한도 안인지(B 측정 필요). 넘으면 `validCourse`도 원소 map 검사로 줄이고 서버 검증으로 옮긴다.
  4. 부모 문서 `merge` 쓰기에서 `diff().affectedKeys()`가 `freeCells`·`updatedAt`만 잡는지(같은 값의 `uid`는 포함되지 않아야 함).
- 후속: `firebase.json`에 규칙 경로를 넣고 규칙 테스트를 둘 위치를 A·B와 합의.

## 화면 연결 (`timetable/`)

| 화면 | 변경 |

| `TimetableSelectModeActivity` | 저장 호출 제거(등록 화면이 저장). 가입 중 직접 입력은 저장된 시간표를 읽어 이어서 수정, 없으면 기존처럼 예시 수업 하나로 시작 |
| `TimetableWeekFragment` | onStart~onStop 구독. 칸 선택은 마지막 누름 후 0.8초 또는 탭을 벗어날 때(숨김·onStop·시간표 관리 진입) `saveFreeSlots`. 첫 값을 받기 전 누름은 무시, 실패 시 안내 후 서버 값으로 복원 |
| `CourseModifyActivity` | 수정 시 원래 courseId·교수·색상 유지 |
| `Course`(timetable) | `courseId`·`professor`·`colorCode` 추가. equals는 화면 입력값만 비교 |
| `TimetableDraft` | 공강 마스크를 7일로 확장(화면은 월~금, 토·일 값은 보존). 토·일 수업 행에서 칸 계산 오류 방지 |
| `TimetableDraftMapper` | `Timetable` ↔ `TimetableDraft`. 여러 시간대 수업은 같은 courseId의 여러 행으로 펼치고 저장할 때 묶는다. 저장된 시간표는 공강 자동 제안(`suggestGaps`)을 끈다 |

- 매칭 스위치(`MainActivity.matchingOn`, A 영역)는 바꾸지 않았다. 공강 저장은 스위치 상태와 무관하다.
- 알려진 제한: 주간 탭에서 칸을 누른 직후 바로 "시간표 관리"로 들어가면, 저장이 끝나기 전에 수정 화면이 이전 선택을 읽을 수 있다. 그 뒤 등록 완료하면 이전 선택으로 저장된다.

- `TimetableDraftMapperTest`: 여러 시간대 묶기, courseId·교수·색상 유지, 공강 선택 복원(30분·토/일 포함), 저장된 시간표 공강 재제안 없음, `TimetableLoader` 한 번만 읽기.

**실행하지 못한 것**: `FirestoreTimetableRepository`는 에뮬레이터·계측 테스트 환경이 없어 자동 테스트가 없다. `FirebaseFirestoreException.Code` 변환은 클래스 초기화에 Android가 필요해 JVM에서 검사하지 않았다. 규칙 에뮬레이터 검증 불가(위). 실기기 확인은 PR 본문의 체크리스트로 한다.

## 범위 밖 후속 작업

- `firebase.json` 규칙 경로와 규칙 테스트 환경(A·B 합의).
- 새 필드 `timetables.freeCells`, 새 컬렉션 `availability`를 AGENTS.md·README 스키마 표에 반영(A/SM에게 요청).
- `Registration`/`Listener` 공통 타입을 `common/`으로 합치는 일(A).
- 수업 개별 추가·수정·삭제(`addCourse` 등)는 `freeCells`·`availability`를 갱신하지 않아 `sourceRevision < revision`(stale)이 된다. 현재 화면은 `replaceCourses`만 쓰므로 영향이 없고, 개별 API를 화면에 쓰게 되면 같은 처리를 추가한다.
- Mock의 시연 데이터는 `MockTimetableRepositoryImpl.MOCK_USER_ID` 아래에 있어 MockAuth UID와 다르면 보이지 않는다(google-services.json이 없는 환경만 해당).
